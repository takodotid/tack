<h1 style="text-align: center;">[RFC#0003] The Ledger: Schema, Phases and Resuming</h1>

# Abstract

Each run is a `SiteFailover` object (`failover.tako.id/v1alpha1`). Its spec holds the whole plan and a copy of the workload's configuration; its status records each phase and step before it starts and after it ends, with the values later steps need. A run resumes from this object and nothing else. The schema is Tack's contract with its users and with a future controller.

# Overview

| Part | Holds | Written |
|---|---|---|
| `metadata` | name `<workload>-<UTC yyyymmdd-hhmmss>`, label `failover.tako.id/workload: <workload>`, namespace from the Workload (default `tack-system`) | at creation |
| `spec` | mode, `from`, `to`, the Workload snapshot, the steps | at creation, never after |
| `status` | state, reason, phases, steps, captured values, held objects, Git revisions, follow-ups | before and after every step |

# Motivation

| Choice | Reason |
|---|---|
| The plan lives in `spec` | Resume runs the plan that was approved, even if the Workload file changed since. |
| The Workload is copied into `spec` | Resume needs the sites, contexts and Git mapping of the run, not of today's file. |
| `spec` is immutable | A ledger that can be rewritten is not a record. |
| The ledger lives at `to` | `to` must answer for any run to succeed; in a site loss, `from` does not. |
| Optimistic concurrency on every write | Two `tack` processes on one run would interleave steps; the second write fails instead. |

# Requirements

1. The CRD MUST be generated from the Go types in `api/v1alpha1`. Checked by `make verify`.
2. `spec` MUST be immutable: the CRD carries the CEL rule `self == oldSelf` on `spec`.
3. `spec.steps` MUST hold every step of the run, and `spec.workload` the Workload's name and spec as they were when the run started.
4. Before a step starts, the ledger MUST record it `Running` with `startedAt` and its attempt count; after it ends, `Succeeded`, `Failed` or `Deferred` with `finishedAt` and a message, together with any value it produced (captured value, held object, Git commit) in the same write.
5. Every status write MUST carry the `resourceVersion` it read, so a concurrent writer makes it fail. A failed write MUST end the process without running further steps.
6. `tack resume` MUST take the plan from `spec.steps` and the progress from `status.steps`, and MUST NOT re-plan. A step recorded `Running` MUST run again ([RFC#0002] makes that safe).
7. The ledger MUST be created at the `to` site, in the Workload's ledger namespace. Creating it MUST fail if the name exists.
8. A run MUST NOT start while another run of the same workload, at any reachable site, is not `Succeeded`, unless the operator names it with `--take-over`.
9. The run's state MUST be one of:

| State | Meaning | Next |
|---|---|---|
| `Running` | a process runs the plan, or one was interrupted while it did | `tack resume` continues it |
| `Waiting` | the run waits for something outside it; only reason `GitUnreachable` | `tack resume` once it is back |
| `Stopped` | something unexpected; the operator decides | `tack resume` with the decision's flag |
| `Succeeded` | every step that could run has run | none; deferred steps run if their site answers on a later `resume` |

10. A `Stopped` or `Waiting` run MUST carry one reason:

| Reason | When | Operator's way on |
|---|---|---|
| `GitUnreachable` | Git cannot be fetched or pushed | resume when Git is back |
| `GitChanged` | the branch moved during the run, or Flux applied a revision other than the run's base | review, then `--accept-git-head <sha>` |
| `GitDiffersFromLive` | Git, as Flux renders it, differs from live before release | fix Git, then resume |
| `TokenMissing` | a captured value is empty or absent | inspect the workload, then resume |
| `FencedSiteIsPrimary` | a site whose steps were deferred came back answering as primary | `--fence <site>` |
| `HeldByAnotherRun` | an object is held by another run or by hand | finish that run, or `--take-over` |
| `FluxChanged` | Flux changed a released object | inspect; the switch may be undone |
| `StepFailed` | any other error, such as a timeout | fix the cause, then resume |

11. Each step's state MUST be one of `Pending`, `Running`, `Succeeded`, `Failed`, `Deferred`.
12. Each phase MUST be recorded with `startedAt` when its first step starts, and `finishedAt` once each of its steps is `Succeeded` or `Deferred`.
13. A change that would break a user of `v1alpha1` MUST be a new API version. Compatible additions MAY stay in `v1alpha1`.
14. A plan MUST read the earlier runs of the workload at every reachable site. When one of them recorded the follow-up `Rebuild` for the target site, and the target's member was created before that run started, a `Planned` run MUST be refused, and a `SiteLoss` plan MUST note it. A member's status cannot show that it diverged; the ledger can. Compatible additions MAY stay in `v1alpha1`.

# Design

**Spec.**

| Field | Content |
|---|---|
| `workload.name`, `workload.spec` | the Workload snapshot: driver, sites with kube contexts, Git, ledger namespace, routing, timeouts |
| `mode` | `Planned` or `SiteLoss` |
| `from`, `to` | site names |
| `steps[]` | `id`, `phase`, `type`, `site`, `description`, `deferrable`, and one member named by `type`: `hold`, `reconcile`, `patch`, `wait`, `capture`, `git`, `verifyGit`, `release`, `verifyNoop`, `routing` |

**Status.**

| Field | Content |
|---|---|
| `state`, `reason`, `message` | as in Requirements 9 and 10 |
| `phase`, `phases[]` | the current phase; each phase's start and end |
| `steps[]` | per step: `state`, `startedAt`, `finishedAt`, `attempts`, `message` |
| `captured` | values for later steps, such as `demotionToken` |
| `held[]` | site, object, its Kustomization, `heldAt`, `releasedAt`, `generation` at release |
| `git` | `baseRevision` (what live matched at Hold), `acceptedRevision` (operator's override), `commit` (the run's own) |
| `followUps[]` | site, action, reason: work left for the operator, such as `Rebuild` |
| `startedAt`, `finishedAt` | the run's start and success |

**Base revision.** The `Reconcile` steps of the Hold phase return the revision Flux applied at each site. The first becomes `git.baseRevision`; a different one at another site stops the run with `GitChanged`, unless the operator accepted a head.

**Resume.** The runner walks `spec.steps` in order: it skips `Succeeded` steps, re-checks the reachability of each site, runs `Deferred` steps whose site answers again (after the fence check of [RFC#0007]), and runs the rest.

# Security Considerations

- The ledger holds no secret. A CloudNativePG demotion token encodes checkpoint location, timeline, system identifier and operator version; it grants nothing. `tack status` prints captured values by name only.
- Writing a ledger needs `create`, `get`, `list` on `sitefailovers` and `update` on `sitefailovers/status` in the ledger namespace at each site.

# Limitations

| Limitation | Trigger to revisit |
|---|---|
| The ledger lives at one site. If `to` is lost mid-run, its ledger is out of reach; a new run toward a reachable site takes over the holds with `--take-over`. | A controller, or ledger copies at every reachable site. |
| A `Running` ledger does not tell a live process from a dead one. The concurrency check catches two writers, not a stale `Running`. | A lease held by the running process. |

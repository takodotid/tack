<h1 style="text-align: center;">[RFC#0006] The Git Change</h1>

# Abstract

After the switch, Tack writes one commit to the GitOps repository that makes Git equal the live state. Tack does not know the repository's layout, so the operator maps each field to a file and a path, or lets Tack find the manifest that defines the object. The commit lands only on top of the revision live matched when the run started.

# Overview

| Input | From |
|---|---|
| Fields and values | the driver's `GitChange` ([RFC#0002]) |
| Where each field lives | the Workload's `spec.git.fields` (mapping), or `spec.git.find` |
| The base commit | the revision Flux applied at Hold ([RFC#0003]), or the head the operator accepted |

# Motivation

| Choice | Reason |
|---|---|
| The system `git` binary | It uses the operator's credential helpers and SSH agent; Tack never handles a Git secret. |
| Byte-level edits | A reviewer sees only the changed values; comments and layout stay. |
| A deadline on every git command, and one fetch per plan | Found in a review (#35, row 12), reproduced in unit tests: a remote that accepted the connection and never answered hung the fetch until the run was cancelled, so the Git step never reached `Waiting`. Every Kubernetes request was bounded. A plan fetched once per optional change with a mapping, and once more, before the operator could confirm. |
| One commit per run, with a trailer | A run interrupted after its push finds and adopts its own commit instead of stopping on "Git changed". |
| Stop when the branch moved | A commit made during the run may conflict with the switch; the operator decides. |
| Refuse a credential in the URL | Found in a review (#31) and reproduced: only an empty URL was refused. The Workload is copied into the ledger's immutable spec, so a URL with a token stayed in every ledger for good, and `tack plan -o yaml` and `tack status -o yaml` printed it. |
| An empty hooks path, not only `--no-verify` | Found in a review (#35, row 13) and reproduced in a unit test: `--no-verify` skips only `pre-commit`, `commit-msg` and `pre-push`. A `prepare-commit-msg` hook in the operator's global `core.hooksPath` dropped the trailer, and a resumed run stopped with `GitChanged` instead of adopting its own commit. |
| A removal needs no parent | Found in a review (#35, row 56): Requirement 7 asked for the parent of every mapped path, while the plan checked it only for a path that sets a value. A removal of an absent key changes nothing. |
| The commit checks where each change is written | Found in a review (#35, row 11), inferred from the code, then shown in a unit test: the ledger records the file and path of each change, and the commit wrote the value, or removed the key, wherever the ledger said. Anyone who may write a ledger could point a removal at any key of the repository. [RFC#0003] Requirement 21 checks the rest of the Git step. |
| `--accept-git-head` names the commit the stop named | Found in a review (#35, row 37) and reproduced in a unit test: the flag took any value, and once set in Hold, Hold accepted any revision at the other sites. A head that Flux applied after the operator reviewed the stop went on unseen. `HEAD` stands for the named commit, as the runbook's way on uses it. |
| `--accept-git-head HEAD` is recorded as the commit it names | Found in PR #49 by reading the code (#46), then reproduced in a unit test: after a stop that named no commit, such as `FluxChanged`, whose runbook way on is `--accept-git-head HEAD`, the ledger recorded `HEAD` as the release revision. `HEAD` names no commit, so the check before the next release stopped with `GitChanged`. |
| `--accept-git-head` after the commit sets what the release checks | Found in a review (#29): after the run's commit, the flag set only the base and relaxed the checks before and after release. The steps after the commit still waited for the run's commit, so a run whose branch moved past it could not go on. |

# Requirements

1. Tack MUST run `git` with `GIT_TERMINAL_PROMPT=0` and `LC_ALL=C`, without `GIT_DIR` and its sibling variables, and MUST NOT print credentials embedded in a URL.
2. Tack MUST NOT run client-side hooks: every git command runs with `core.hooksPath` set to an empty directory that Tack creates. Its clone is temporary, and a hook that rewrites the message would drop the trailer that lets a resumed run adopt its commit. Server-side rules still apply.
3. Any failure to fetch, other than a missing branch, MUST count as unreachable, including a rejected credential or a wrong URL: Tack cannot tell them apart from git's messages reliably. A `Planned` plan then refuses to start ([RFC#0007]). Every git command MUST end within 2 minutes; a fetch or push that does not counts as unreachable, while a cancel of the run, such as Ctrl-C, stays a cancel. An HTTP transfer slower than 1 byte a second for 30 s MUST end before that. Over SSH, Tack MUST give up on a connection after 15 s, and after 3 keepalives 15 s apart get no answer, unless the operator chose the ssh command (`GIT_SSH_COMMAND`, `GIT_SSH` or `core.sshCommand`), whose options Tack does not know. A plan MUST fetch Git at most once. Checked by unit tests.
4. A field with a mapping MUST be written where the mapping says; a mapping matches on site, object kind, name (and namespace when given) and field.
5. A field without a mapping MUST be written into the manifest that defines its object when `spec.git.find` is set: the one YAML document, in the site's find paths or the whole repository, whose API group, kind, name and namespace match. None or several matches MUST fail the plan, naming the candidates.
6. A field with neither MUST fail the plan, except an optional removal ([RFC#0004]), which the plan leaves out and notes.
7. At plan time, when Git is reachable, each mapped file MUST exist, and so MUST the parent of each mapped path that sets a value. A removal passes without its parent: removing an absent key is a no-op (Requirement 8). Checked by unit tests.
8. An edit MUST change only the bytes of the value. A missing key MUST be inserted into its block mapping at that mapping's indentation. A removal MUST delete the key's lines, and MUST be a no-op when the key is absent. Flow-style containers, anchors and aliases on the path, and replacing a multi-line block scalar MUST be errors.
9. The commit MUST be based on the run's base commit. If the remote branch head differs:
   - when the head is this run's commit (trailer `Tack-Run: <run>`) on top of the base, Tack MUST adopt it;
   - otherwise Tack MUST stop with `GitChanged`, naming base and head.
10. Before the run's commit, `tack resume --accept-git-head <sha>` MUST record `<sha>` as the run's accepted revision (`status.git.acceptedRevision`) and use it as the base. After the run's commit, it MUST record `<sha>` as the release revision (`status.git.releaseRevision`), which the Release phase checks Git against ([RFC#0005] Requirements 8 and 12); a release revision that does not contain the run's commit MUST stop the run with `GitChanged`. When a `GitChanged` stop names one commit, the ledger MUST record it in `status.git.changedRevision`, until the run goes on. While it is recorded, `<sha>` MUST name that commit, or be `HEAD`, which stands for it; any other value MUST be refused before the operator is asked to confirm, with nothing written. A ledger without it takes `<sha>` as given, except `HEAD`, which then stands for the branch head: `tack resume` MUST read it before it asks the operator to confirm, print it, and record that commit, never `HEAD`; when Git cannot be read, it MUST refuse, with nothing written. Checked by unit tests.
11. The commit message MUST be `tack: <workload> primary <from> to <to> (<mode>)`, with `<mode>` the run's mode in lower case (`planned` or `siteloss`), a body naming the run, and the trailer `Tack-Run: <run>`. When `spec.git.author` is set, it is both author and committer; else git's own configuration is used with `user.useConfigOnly=true`, so git never guesses an identity. Checked by unit tests, and by golden tests of the dry run, which prints the message.
12. Tack MUST push without force. A rejected push MUST stop the run with `GitChanged`. A remote that cannot be reached MUST put the run in `Waiting` with `GitUnreachable` ([RFC#0007]).
13. If the edits change nothing, Tack MUST NOT commit, and the base is the run's commit.
14. The Workload's `spec.git.url` MUST NOT hold a password, nor a user in an `http` or `https` URL, which a Git host may take as a token: loading the Workload MUST fail, and the error MUST NOT repeat the URL. A user in an `ssh` URL or an scp-like address, such as `git@host:path`, MAY be given. Tack MUST print the ledger's copy of the URL with any user and password replaced by `***`, also in YAML. Checked by unit tests.
15. Before it writes a change, the commit MUST check where the change is written: with a mapping (Requirement 4) in the run's Workload snapshot, the file, path and document MUST be the mapping's; without one, the path MUST be the field's, and the file's document MUST define the change's object, by API group, kind, name and namespace, in the base commit. Any other change MUST stop the run with `StepFailed` before anything is committed, with a message that names the change and where its Workload puts it. A change without a file is found then (Requirement 5), so it passes. Checked by unit tests.

# Design

**Mapping.**

```yaml
spec:
  git:
    url: ssh://git@git.example.com/gitops.git
    branch: main
    fields:
    - site: a
      object: {kind: Cluster, namespace: db, name: pg-a}
      field: spec.replica.primary
      file: apps/db/site-a/values.yaml
      path: cnpg.replica.primary
    find:
      paths:
      - {site: a, path: clusters/site-a}
```

| Path syntax | Meaning |
|---|---|
| `a.b.c` | key `c` under `b` under `a` |
| `a[2].b` | key `b` of the third item of list `a` |

| Value | Written as |
|---|---|
| JSON string | a YAML string, plain when safe, else double-quoted |
| JSON number or boolean | plain |
| unset | the key is removed |

`document` selects a YAML document by index in a multi-document file when none is the object itself.

# Security Considerations

- Tack holds no Git credential. The operator's `git` configuration provides access.
- The Git URL in the Workload is a reference; a URL with an embedded secret is refused (Requirement 14).

# Limitations

| Limitation | Trigger to revisit |
|---|---|
| Keys that contain dots cannot be addressed. | A repository that needs them. |
| Flow-style YAML on a path cannot be edited. | A repository that uses it. |
| Commits are not signed by Tack; git's configuration decides. | A repository that requires signed commits. |
| A fetch that takes more than 2 minutes counts as unreachable, even while it makes progress. | A repository whose fetch takes that long. |
| Tack fetches with `--quiet`, so a server sends no progress while it packs. One that sends nothing for 30 s, such as one without git's keepalives (`uploadpack.keepAlive`, 5 s by default), ends the fetch, which counts as unreachable. | A fetch observed to end this way. |
| With the operator's own ssh command, only the 2-minute deadline ends a stalled connection. | A stalled SSH remote observed with such a command. |

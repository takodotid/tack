<h1 style="text-align: center;">[RFC#0003] The Ledger: Schema, Phases and Resuming</h1>

# Abstract

Each run is a `SiteFailover` object (`failover.tako.id/v1`). Its `spec` holds the plan and a copy of the workload's configuration, and its `status` records each phase and step before it starts and after it ends. A run resumes from this object and from nothing else; the schema is Tack's contract with its users and with a future controller.

# Overview

| Part | Holds | Written |
|---|---|---|
| `metadata` | name `<workload>-<UTC yyyymmdd-hhmmss>` from the plan's time (Requirement 7); label `failover.tako.id/workload`; namespace from the Workload | at creation |
| `spec` | mode, `from`, `to`, the Workload snapshot, the steps, the cluster of each site that answered the plan, the runs it takes over | at creation, never after |
| `status` | state, reason, phases, steps, captured values, held objects, Git revisions, follow-ups, the cluster of each site first read during the run, the run that took it over, an abandoned mark, the history of the run's state | before and after every step |
| The run's Lease, beside the ledger | the process that runs the run, and its last renewal (Requirement 28) | by that process, from its first status write to its end |

# Motivation

| Choice | Reason |
|---|---|
| `spec` holds the plan and a Workload copy, and is immutable | A resume runs the approved plan with the contexts and Git mapping the run started with. A rewritable ledger is not a record. |
| The ledger lives at `to` | A run can only succeed if `to` answers. In a site loss, `from` does not. |
| A take-over is in the new run's spec, and `--take-over` repeats | run-1 stopped at `promote-b`, b was lost, run-2 took it over and promoted c. When b came back, `tack resume run-1` promoted b: two primaries. The take-over lived only in run-2's process. The flag took one value, so taking over two runs was impossible. |
| The read of a site's cluster is repeated like the site's check | One connection reset right after a site answered stopped a run with `StepFailed`, instead of deferring that site's steps. |
| Each site's cluster is recorded and checked in every process | A resume used a kubeconfig whose context reached another cluster with the same object names, and held and demoted the Cluster there. |
| The first status write outlives an interrupt; a ledger without a state never resumes | An interrupt before it left no start and no `Rebuild` follow-up. The resume ended `Succeeded` without it, and a planned run onto the diverged member was allowed. |
| A dry-run create first | A CRD older than Tack drops unknown spec fields without an error, such as a take-over. |
| A taken name gets a suffix, unless its run may still run | The name holds the plan's time to the second, so a `--take-over` run planned in the same second failed with "already exists". A same-named run that may still run can be a second process starting the same switch. |
| After the run's commit, Hold accepts that commit | A lost site came back with Flux having applied the run's commit. The resume stopped in Hold with `GitChanged` that `--accept-git-head` did not clear. |
| Runs are ordered by each ledger's site clock, with a margin | `creationTimestamp` has whole seconds and comes from different API servers. A run a few seconds newer by a lagging clock did not count, so the older run resumed on a stale plan. |
| A 10 s clock margin across sites | Hosts whose clocks NTP keeps agree within 10 s. A run whose ledger is at the same site has the same clock, so no margin applies. |
| `tack resume` refuses a run taken over, abandoned or followed by a newer run | Its plan may no longer match the sites. |
| A resume composes the plan again | `tack resume` ran whatever steps a ledger held, with the operator's credentials. Ledgers of earlier releases have the same steps, so the check refuses none. |
| `tack resume` refuses before it asks, and searches again after | The refusal came after the operator typed the workload's name, and without a terminal exited 2 instead of 1. Another run can take this run over while the operator confirms. |
| A `Rebuild` follow-up is in the ledger | A member's status cannot show that it diverged. |
| `TokenMissing` is cleared by restoring the value | `capture-token` never runs again once it succeeded, so a value removed from `status.captured` stopped every resume. |
| `GitDiffersFromLive` and `FluxChanged` are cleared by `--accept-git-head` | A fix to Git moves the branch past the release revision, and after `FluxChanged` the generation stays changed, so a plain resume stops again. An accepted head turns that check into a report ([RFC#0005] Requirement 10). |
| A run that ends ends every phase whose steps are done | v1.2.0 left phases unfinished in a site-loss run whose lost site's steps came last. |
| A resume of a `Succeeded` run writes `Running` with its first step | Writing it earlier left a finished run `Running` when the process died or the site was down, and it refused every new run (Requirement 8). |
| A write with no answer is repeated with the same `resourceVersion` | A connection reset stopped a run with "another tack process may be running this run". A write can land and lose its answer; its repeat conflicts with itself, and the read after tells the cases apart. |
| A run searches again once its ledger exists | Two `tack run` processes both found no active run and both ran. The loser, left not `Succeeded`, refused every later run. |
| Field manager `tack` | Writes named none, so the API server used the binary's name, such as `tack.exe`. |
| The Reason, Abandoned and TakenOverBy columns | `kubectl get sfo` showed `Stopped` without why, and abandoned and taken-over runs by their last state, while `tack status` said `Abandoned` and `TakenOver`. `status.state` keeps its values (Requirement 9). TakenOverBy is last so that scripts that read Phase and Age by position keep working. |
| A build with no release counts as older than every release | A `dev` build, such as from `go install`, resumed, abandoned and marked a release's ledger, and its writes dropped status fields it did not know. A plain `go build` at `v1.4.0` reported `dev`, though Go had recorded `v1.4.0`. |
| Each write records the tack's version; an older release refuses the ledger | A status write replaces the whole status, so a tack drops the fields it does not know. A newer patch release is refused too, or a run in flight would follow older step rules. |
| A Lease that the running process renews | `tack abandon` marked a run a process still ran, and a new run took it over, so a step in flight could land after. A `Running` ledger cannot tell a live process from a dead one, and a heartbeat in the ledger would be a second writer (Requirement 5). Without a Lease (v1.4.0 and older), a `Wait` runs up to its timeout, 10 minutes by default, with no write, so the step's timeout judges. |
| A history, and Events | A resume cleared the reason and message, and each attempt overwrote the step's message, so an incident's timeline could not be rebuilt. The user comes from the API server, because a kubeconfig names it only for the operator's host. |
| The history records the decision flags | `--fence`, `--take-over`, `--accept-git-head` and who ran each process were recorded nowhere. |
| Messages are cut in the ledger; the CRD sets no maximum | Flux's messages had no limit. A `maxLength` would refuse the next status write of an older tack that records a longer one, and stop its run. |
| The history keeps its first entry, the newest and a count | One entry per state change makes its size follow stops and resumes, not the plan. |
| The history keeps its first entry and its newest | The first records the start, its `--take-over` and who started it. The newest record the current stop. |
| Events are best effort | An Event lives about an hour, and a site may refuse it. The history is the record. |
| Optimistic concurrency on every write | Two `tack` processes on one run would interleave steps. With it, the second write fails instead. |
| `v1` is stored; `v1alpha1` stays served and deprecated, as a copy of `v1` | v0.1.x ledgers are stored as `v1alpha1` and stay readable, and a v0.1.x CLI works while sites upgrade one by one. One schema needs no conversion webhook. The API server refuses a CRD that drops a version in its `status.storedVersions`. A copy cannot drift. |
| Pages of 100; an expired page lists again in one request | One answer for 1,000 ledgers was 13.5 MB ([Old ledgers](../docs/old-ledgers.md)). client-go's pager does the same on expiry. |
| A page bounds each answer | A page of 100 holds at most about 20 MB, from the largest ledger measured, 204 KB. The search still reads every ledger, so the total stays the same. |
| `tack prune`, run by the operator | Each search reads every ledger of the workload at each site, and ledgers were never deleted. The operator decides when, as for every other change Tack makes. |
| Prune deletes only when every site answers and every run is finished, and keeps what a later run needs | Deleting a newer run lets an older unfinished one resume. Deleting a run with a `Rebuild` lets a planned run go onto a diverged member. Deleting the run that took one over makes it block new runs again. A silent site may hold any of these. |
| Prune orders runs only where the clocks tell, and deletes a `Rebuild` run with a margin | A lagging clock made a run of another site look older than the newest, and it may have been the last switch. The run's start comes from the host's clock, which made a member created before the run look rebuilt. |
| Prune deletes a run whose `Rebuild` is done | It kept every run with a `Rebuild` follow-up, since it read no member, and operators deleted such runs by hand. |
| Prune keeps abandoned and taken-over runs | They record holds that may be left in the cluster, and the take-over that ended them ([abandon-run.md](../docs/runbooks/abandon-run.md)). Each needs an incident, so they are few. |
| Tack does not check who else may write ledgers | No other command needs the access that check needs. |

# Requirements

Unless a requirement names another check, unit tests check it.

1. The CRD MUST be generated from the Go types in `api/v1`. Checked by `make verify`.
2. `spec` MUST be immutable: the CRD carries the CEL rule `self == oldSelf` on `spec`.
3. `spec.steps` MUST hold every step of the run, and `spec.workload` the Workload's name and spec as they were when the run started.
4. Before a step starts, the ledger MUST record it `Running` with `startedAt` and its attempt count; after it ends, `Succeeded`, `Failed` or `Deferred` with `finishedAt`, a message, and any value it produced (captured value, held object, Git commit), in one write. A Release step also records the object's generation before it removes the hold ([RFC#0005] Requirement 9). The run's message and each step's MUST be cut to 8 KiB in the ledger, after the cleaning of [RFC#0009] Requirement 10; the progress line keeps the whole message.
5. Every status write MUST carry the `resourceVersion` it read. A write with no answer, or an answer 5xx or 429, MUST be repeated with the same `resourceVersion`, for up to 30 s. When a repeat conflicts, Tack MUST read the ledger, and count the write as done only when the ledger holds the status it sent. Any other failed write MUST end the process before further steps, and its message MUST name the failure: another writer on a conflict, the permission on a refusal, the missing ledger when it is gone.
6. `tack resume` MUST take the plan from `spec.steps` and the progress from `status.steps`, and MUST NOT re-plan. A step recorded `Running` MUST run again ([RFC#0002] makes that safe).
7. The ledger MUST be created at the `to` site, in the Workload's ledger namespace, and MUST NOT replace a ledger that exists. When a ledger has the run's name:

| Its run | `tack run` |
|---|---|
| is `Succeeded`, was taken over (`status.supersededBy`), is abandoned (`status.abandoned`), or is the run this run takes over | MUST try the name with `-2` appended, then `-3`, up to `-9` |
| is any other, or every name is taken | MUST fail and create nothing |

A dry-run create that shows that the site's CRD drops a field of the spec MUST also fail the create, creating nothing. The error MUST say to apply this version's CRD there.

8. A run MUST NOT start while another run of the same workload, at any reachable site, is not `Succeeded`, unless the operator names it with `--take-over`. A run that another run took over (Requirement 17), or that is abandoned, does not count. Once its ledger exists, before its first status write, `tack run` MUST search again with the same checks. When it finds such a run, or the search fails, the run MUST end before any step, and record `status.abandoned` with the time and the reason as its only status, with its entry in `status.history` (Requirement 22) and `status.writtenBy` (Requirement 24). `tack abandon` records the same mark ([RFC#0009] Requirement 15).
9. The run's state MUST be one of:

| State | Meaning |
|---|---|
| `Running` | a process runs the plan, or one was interrupted while it did |
| `Waiting` | the run waits for something outside it; only reason `GitUnreachable` |
| `Stopped` | something unexpected; the operator decides |
| `Succeeded` | every step that could run has run; deferred steps run on a later `resume` if their site answers |

A `tack resume` of a `Succeeded` run MUST leave it `Succeeded` until one of its steps starts, and record it `Running` in the write that records that step `Running`.

10. A `Stopped` or `Waiting` run MUST carry one reason. [Stopped and waiting runs](../docs/runbooks/stop-reasons.md) gives the way on for each.

| Reason | When |
|---|---|
| `GitUnreachable` | Git cannot be fetched or pushed |
| `GitChanged` | the branch moved during the run; Flux applied a revision other than the run's base or the head the operator accepted (after the run's commit: also that commit, or the head accepted after it); or the branch moved past the run's commit before a release ([RFC#0005] Requirement 8) |
| `GitDiffersFromLive` | Git, as Flux renders it, differs from live before release |
| `TokenMissing` | a captured value is empty or absent, or, before the promotion, differs from the value at its source ([RFC#0007] Requirement 9) |
| `FencedSiteIsPrimary` | a site whose steps are deferrable answers as primary, or declares itself primary, in the read before its steps ([RFC#0007] Requirement 6); or a site but `to` does so in the read before a Failover step after the demotion ([RFC#0007] Requirement 9) |
| `HeldByAnotherRun` | an object is held by another run or by hand |
| `FluxChanged` | Flux changed a released object |
| `SiteMismatch` | a site's context reaches another cluster than the run recorded (Requirement 19) |
| `StepFailed` | any other error, such as a timeout |

11. Each step's state MUST be one of `Pending`, `Running`, `Succeeded`, `Failed`, `Deferred`.
12. Each phase MUST be recorded with `startedAt` when its first step starts, and `finishedAt` once each of its steps is `Succeeded` or `Deferred`. A run that ends `Succeeded` MUST record the end of each such phase, also of one that a ledger of an earlier release left unfinished: at the last `finishedAt` of its steps, or at the run's end when a step records none.
13. A change that would break a user of `v1` MUST be a new API version. Compatible additions MAY stay in `v1`.
14. A plan MUST read the earlier runs of the workload at every reachable site. When one recorded the follow-up `Rebuild` for the target site, and the target's member was created before that run started (`status.startedAt`, or `metadata.creationTimestamp` when unset), a `Planned` run MUST be refused, and a `SiteLoss` plan MUST note it.
15. The CRD MUST serve and store `v1`. It MUST also serve `v1alpha1`, deprecated, with the same schema, subresources and printer columns, and no conversion webhook; the API server converts by changing only `apiVersion` ([Upgrade](../docs/guide/upgrade.md#upgrade-from-v01x)). The printer columns MUST be, in order: Workload, Mode, From, To, State, Reason, Abandoned (the date of `status.abandoned.at`), Phase, Age, TakenOverBy (`status.supersededBy`). Checked by `api/v1/crd_test.go`.
16. Tack MUST read and write ledgers as `v1`. When a site does not serve `v1`, the error MUST say to install or upgrade Tack's CRD there.
17. A run started with `--take-over RUN` MUST record `RUN` in `spec.takeOver`, and MUST take over the holds of `RUN` in every process that runs it. It MUST then try to write its own name into `status.supersededBy` of `RUN`'s ledger; when that ledger does not answer, the run MUST go on. `--take-over` MAY be repeated: the run then records the first run in `spec.takeOver` and every run in `spec.takeOvers`, in the order named, and acts as above for each. Every rule of this RFC about a run that another run takes over, or about the run a run takes over, MUST hold for each of them.
18. Before it asks the operator to confirm, and again after the confirmation before any step, `tack resume` MUST search the workload's runs at every reachable site of the run's Workload snapshot. It MUST refuse the run, changing nothing, when its `status.supersededBy` or `status.abandoned` is set, another run's `spec.takeOver` or `spec.takeOvers` names it, or another run was created after it. Each ledger's `metadata.creationTimestamp` comes from its site's API server, to the second. Another run counts as created after it when its ledger is:

| At | Created |
|---|---|
| the same site | in the same second or later |
| another site | less than 10 s before it, or later. This 10 s is the clock margin of this RFC |

An abandoned run that never recorded its start ran no step, and a run that this run takes over is older: neither counts.

19. The plan MUST record, for each site that answers, the UID of its cluster's `kube-system` namespace in `spec.fingerprints`. In each `tack run` and `tack resume`, before a site's first step, Tack MUST read that UID again, and stop with `SiteMismatch` before the step, which keeps its state, when it differs from the record. A site without a record, such as one lost at plan time, MUST be recorded in `status.fingerprints` on its first read, and checked against that record after. A read that gets no answer MUST be repeated as a site's checks are ([RFC#0007] Requirement 5), in the plan and in the run. When the last read got no answer, a deferrable step MUST be `Deferred`, as on an unreachable site, and any other step MUST stop the run with `StepFailed` before the step, which keeps its state.
20. Tack MUST write the ledger's first status, with every step `Pending`, `startedAt` and the follow-ups, before any step starts, in a write that an interrupt does not cancel. `tack resume` MUST refuse a ledger whose status has no state, before it asks the operator: none of its steps ran, and its follow-ups are not in it. The way on is a new run with `--take-over`.
21. Before it asks the operator to confirm, `tack resume` MUST compose the run's plan again, as [RFC#0002] Requirement 6 orders it, from the Workload snapshot, `spec.from`, `spec.to` and `spec.mode`; the driver's steps, objects and Git changes for them ([RFC#0002] Requirement 2); the Kustomization each `Hold` step names; and the file, path and document of each change of the `Git` step. The `Git` step's changes MUST be the driver's, in order, with the same values, except an optional removal that the Workload does not map ([RFC#0006] Requirement 6). The plan of the driver's `Steps` with `Legacy`, as v1.6.0 composed it, MUST also be accepted, so a ledger that v1.6.0 or earlier wrote resumes. A run whose `spec.steps` differ from both plans in anything but a step's description MUST be refused, changing nothing, with a message that names the first difference. A run that succeeded with no `Deferred` step is not checked. Checked also against the ledgers of earlier releases.
22. Tack MUST append one entry to `status.history` in each status write that changes the run's state, and MUST NOT change an earlier entry:

| Write | Entry |
|---|---|
| the first status write of `tack run` (Requirement 20) | `Running` |
| the write of `tack resume` that records the run `Running`; for a `Succeeded` run, the write that records its first step `Running` (Requirement 9) | `Running` |
| a stop, a wait | `Stopped`, `Waiting` |
| the end of a run (Requirement 12) | `Succeeded` |
| the abandonment by the search after the create (Requirement 8), or by `tack abandon` ([RFC#0009] Requirement 15) | `Abandoned` |
| the mark of a take-over (Requirement 17), in the ledger of the run taken over | `TakenOver` |

Each entry MUST hold: the time and state; the run's reason and message, or the reason of the abandonment, or the run that took it over; the version of the tack that wrote it; the user that the API server of the ledger's site names for that process's credentials, empty when it does not say; and the operator's decision flags of that process (`--take-over`, `--fence`, `--accept-git-head` with the commit it stands for, `--accept-behind`, `--yes`, `--force`; a `TakenOver` entry holds the `--take-over` that names its run). The message MUST be cleaned as [RFC#0009] Requirement 10 says, then cut to 1024 bytes. The history MUST hold at most 100 entries: before an entry that would make 101, Tack MUST drop the oldest entry but the first, and add one to `status.historyDropped`. A repeated write (Requirement 5) appends its entry once. `TestHistoryStaysWithinBound` stops and resumes a run 60 times, each stop with a message of about 4 KiB.

23. After each write of Requirement 22, and after each write that records a step `Running`, `Succeeded` or `Deferred`, Tack MUST create a Kubernetes Event on the ledger, in the ledger's namespace at its site, with the message cleaned and cut as in Requirement 22:

| Event reason | Type | When |
|---|---|---|
| `RunRunning`, `RunSucceeded`, `RunTakenOver` | Normal | the history entry of that state |
| `RunStopped`, `RunWaiting`, `RunAbandoned` | Warning | the history entry of that state |
| `StepStarted`, `StepSucceeded` | Normal | a step recorded `Running`, `Succeeded` |
| `StepDeferred` | Warning | a step recorded `Deferred` |

Tack MUST NOT repeat an Event, MUST wait at most 5 s for one, and after one fails MUST send no more in that process, print one progress line that says so, and go on.

24. Every status write MUST record the version of the tack that writes it in `status.writtenBy`. When `status.writtenBy` names a newer release than the tack's own, `tack resume` and `tack abandon` MUST refuse the run before they ask, and the mark of a take-over (Requirement 17) MUST NOT be written. Each changes nothing and names both versions; the run that takes over goes on, as when that ledger does not answer.
    - Versions compare as releases `vX.Y.Z`. A build after a release, as `git describe` (`v1.3.0-5-g1fda25c`) or Go's pseudo-version (`v1.3.1-0.20261111105842-d483d80abcde`) names it, counts as newer than that release and older than the next.
    - A tack whose version names neither, such as `dev` or `v1.3.0-rc.1`, counts as older than every release, and refuses a ledger that a release or a build after one wrote. A ledger whose `status.writtenBy` names neither is not refused.
    - A tack built without a version, such as by `go install`, MUST take the module version that Go recorded in the binary when that names a release or a build after one.
    - `tack status` MUST still read the ledger, and say which tack wrote it. A run that succeeded with no `Deferred` step is not checked.
    - Checked also against the ledgers of earlier releases.
25. Every write of a ledger (its dry-run create, create and each status write), the create of each of its Events, and each write of its Lease (Requirement 28), MUST name the field manager `tack`.
26. Every list of ledgers, each search for runs and `tack status --context` MUST ask for at most 100 ledgers per request, with the same namespace and label selector in each, and MUST follow the continue token until it gives none. When a page after the first answers 410 Expired, Tack MUST list the ledgers again in one request without a limit, and use only that answer.
27. `tack prune` MUST delete only the ledger of a run that is `Succeeded` with no `Deferred` step, and MUST keep, of the workload's runs at every site:

| Run kept | Goes once |
|---|---|
| each run that is abandoned or taken over (Requirement 17) | the operator deletes it by hand ([Old ledgers](../docs/old-ledgers.md#delete-a-run-by-hand)) |
| each run that `--keep` counts (`Succeeded` with no `Deferred` step, neither abandoned nor taken over), unless `--keep` counted runs were created certainly after it; `--keep` is 1 or more, so the record of the last switch stays | `--keep` newer runs succeeded |
| each run whose `spec.takeOver` or `spec.takeOvers` names a listed run that is neither abandoned nor marked by its own `status.supersededBy` | that run goes |
| each run whose `status.writtenBy` names a newer release than the tack's own (Requirement 24) | a tack of that release prunes |
| each run with a follow-up `Rebuild` (Requirement 14) whose site's member, as the Workload file names it and its driver reads it, was not created the clock margin or more after the run's ledger (`metadata.creationTimestamp`), cannot be read, or has no creation time; whose ledger has no creation time; or whose site the Workload file does not name | the member is created again that long after |

- A ledger is created certainly after another by the order of Requirement 18 seen from the other side: at the same site in a later second, at another site the clock margin or more later. Where the clocks cannot tell, neither counts as after the other.
- Prune MUST read the members only to decide on a run with a follow-up `Rebuild` that no other row keeps.
- Prune MUST delete nothing when a site of the workload gives no answer to its checks ([RFC#0007] Requirement 5), when a search fails, or when a run of the workload is not finished: `Succeeded` with no `Deferred` step, abandoned or taken over.
- After the operator confirms ([RFC#0009] Requirement 30), it MUST search again with the same checks, read the members again when it needs them, and delete nothing when a run appeared or went, a ledger was written, or what it does to a run changed, since the list.
- It MUST delete one ledger at a time, by name, oldest first by `metadata.creationTimestamp`, each with the UID and `resourceVersion` it read as preconditions, and MUST stop at the first delete that fails.

28. Each `tack run` and `tack resume` MUST hold the run's Lease, a `coordination.k8s.io/v1` Lease named after the run, in the ledger's namespace at its site, with the label `failover.tako.id/workload` and the ledger as its owner.
    - It holds the Lease from before its first status write (`tack run`, Requirement 20) or its first write (`tack resume`), until the process ends the run, when it MUST write the Lease with no holder.
    - The holder MUST name the tack's version, the process and its host. The duration MUST be 30 s, and the process MUST renew it every 10 s.
    - A process that cannot write the Lease MUST go on, and print one progress line that says so.
    - A process MUST take over a Lease that another process holds, and print a line that names that process when the Lease is fresh. A process whose Lease another took MUST stop renewing it, and say so at its end.
    - A Lease is fresh when it names a holder and was renewed within its duration and the clock margin (Requirement 18).
    - A tack process may still run a run when its Lease, owned by its ledger, is fresh; or when the run has no such Lease, or it cannot be read, and is `Running`, and the newest time its ledger records is within the timeout of its step recorded `Running` (none for a step without one) and 5 minutes.
    - `tack abandon` and `tack run --take-over RUN` MUST then refuse the run, changing nothing, unless the operator passes `--force` ([RFC#0009] Requirements 5 and 15 say when they check). The refusal MUST name the holder and when its Lease stops holding, or the ledger's newest time, its writer, and when the window ends.
    - With `--force`, the command MUST print what it would have refused, go on, and record `--force` in its history entry (Requirement 22).
29. Each run MUST record in `status.writes` when its workload stopped taking writes and when the new primary took them again, as the driver names the steps (`Writes`, [RFC#0002] Requirement 2): `stoppedAt` in the write that records the step that stops writes `Running`, and `resumedAt` in the write that records the step after which the new primary takes writes `Succeeded`; each the first time only. A `SiteLoss` run, whose mode cannot tell when writes stopped, MUST record its start as `stoppedAt`, with `stoppedEstimated: true`, in its first status write: writes stopped before the run started, so its start is the latest time they can have stopped. `tack status RUN` MUST print the window ([RFC#0009] Requirement 28).
30. Before a step starts again, Tack MUST move its last attempt (`startedAt`, `finishedAt`, state and message, the message cut to 1024 bytes) to the end of the step's `earlier`, in the same write, keeping the newest 10.

# Design

**Spec.**

| Field | Content |
|---|---|
| `workload.name`, `workload.spec` | the Workload snapshot: driver, sites with kube contexts, Git, ledger namespace, routing, timeouts |

**The Lease** is an object of its own, so its renewals do not change the ledger's `resourceVersion`. Its owner is the ledger, so deleting the ledger, such as by `tack prune`, deletes it. A Lease of the run's name that another ledger owns, or that no ledger owns, passes to the run's ledger when a process finds it. A process that ends records its end in the ledger, then writes the Lease with no holder. A killed process leaves it to expire, 30 s after its last renewal. Its times come from the clock of the host that renewed it.

**History and Events.** Each process reads its user once, with a `SelfSubjectReview` at the ledger's site, before its first write. Events carry what the history leaves out, the start and end of each step, for as long as the API server keeps them. `kubectl describe sfo RUN` lists them.

**Base revision.** The `Reconcile` steps of Hold return the revision that Flux applied at each site. The first becomes `git.baseRevision`. A different revision at another site stops the run with `GitChanged`, unless it is the head the operator accepted. After the run's commit, two more revisions pass: the commit, and the head accepted after it (`git.releaseRevision`). A site that comes back after the commit may have applied it ([RFC#0007] Design). This check reads no Git. The Release phase checks the branch before it releases the site ([RFC#0005] Requirement 8).

**Resume.** Before it asks, `tack resume` searches (Requirement 18) and composes the plan again (Requirement 21); it searches again after the confirmation. The runner then walks `spec.steps` in order. It skips `Succeeded` steps. It checks again that each site answers and is the same cluster (Requirement 19). Before each Failover step after the demotion that is not `Succeeded`, it reads every site but `to` ([RFC#0007] Requirement 9). Before each deferrable site's first step that is not `Succeeded`, it reads that site ([RFC#0007] Requirement 6). It runs the rest, `Deferred` steps whose site answers again among them. A site's `VerifyGit` that succeeded in an earlier process runs again before the site's first Release step ([RFC#0005] Requirement 8).

# Security Considerations

- Writing a ledger is a privilege. A ledger names the steps, the kube contexts and the Git URL that `tack resume` uses with the operator's credentials. Whoever may create `sitefailovers`, or update or patch `sitefailovers/status`, can plant a run or change one.
- Whoever may update, patch, delete or deletecollection `sitefailovers` can remove a run's label `failover.tako.id/workload`, or the run. Each search lists by that label, so the run drops out of the checks of Requirements 8, 14 and 18.
- Requirement 21 and [RFC#0006] Requirement 15 bind the steps and the Git files to the Workload snapshot and the request. The snapshot and `status` are taken as written. The operator restricts who may write them, and checks it at every site ([Who may write ledgers](../docs/permissions.md#who-may-write-ledgers)). RBAC only adds access: the chart's roles cannot take it from another subject, such as a GitOps controller bound to `cluster-admin`.
- The ledger holds no secret. A CloudNativePG demotion token encodes the checkpoint location, timeline, system identifier and operator version, and grants nothing.
- Whoever may write a Lease can make a run look alive, which blocks `tack abandon` and `--take-over` until `--force`, or dead, which lets them go on as without the Lease. The holder names the operator's host.
- Whoever may delete ledgers can delete any run's record outside Tack, including a run that is not finished: grant it to the operators only ([Permissions](../docs/permissions.md)).
- The history names the user of each process, so whoever may read a ledger sees who ran it.

# Limitations

| Limitation | Trigger to revisit |
|---|---|
| Tack does not check who else may write ledgers. That needs `create` on `subjectaccessreviews`, or a list of every RoleBinding and ClusterRoleBinding. The operator runs [the check](../docs/permissions.md#who-may-write-ledgers) at every site. | A controller whose service account alone may write ledgers, or an admission policy that refuses every other writer. |
| Requirement 21 binds the steps to the Workload snapshot, not the snapshot to the operator: a ledger planted with other contexts, Clusters or Git URL passes it. Check the confirmation, which prints each context, API server, recorded cluster and the Git URL ([RFC#0009] Requirement 4). `status` is taken as written. | A controller whose service account alone may write ledgers. |
| If `to` is lost during a run, its ledger is out of reach (Requirement 7). A newer run whose ledger is at a silent site is not found: `tack resume` runs the older run and names the site ([RFC#0009] Requirement 16), and the check before each patch ([RFC#0005] Requirement 11) still stops it at a held object. | A controller, or ledger copies at every reachable site. |
| Clocks that differ by more than 10 s (Requirement 18) can order two runs wrong, make a Lease look expired or an ended one fresh for longer (Requirement 28), or make a `Rebuild` look done (Requirement 14). Tack does not check the clocks ([Install](../docs/guide/install.md#what-else-tack-needs)); after a refused resume or a prune that keeps an older run, start a new run with `--take-over`. | A clock difference observed between sites or hosts, or a refusal of a run that should resume. |
| A site lost at plan time is recorded by the first process that reads it, which trusts that process's kubeconfig. | Fingerprints given in the Workload file. |
| A value lost from `status.captured` after its `Capture` step succeeded is not captured again: the operator restores it ([TokenMissing](../docs/runbooks/stop-reasons.md#tokenmissing)). A token read again later may come from another demotion. | A value lost without an edit of the ledger. |
| `status.writes` ends when the new primary takes writes at its site, not when clients reach it through Strait. In a site loss, its start is the run's start, not the loss. [Measure failover time](../docs/runbooks/measure-failover-time.md) measures what clients see. | A record of Strait's route change in the ledger. |
| `tack resume` takes over a Lease that another process holds, and does not refuse (Requirement 28). The ledger's writes stop one of two processes, not before (Requirement 5). The Lease is renewed by its own goroutine, so a stuck process, such as on a credential prompt, keeps it fresh. | Two processes observed to run one run, or a process observed to hold a Lease while it ran no step. |
| Until the operator runs `tack prune`, each search for runs reads every ledger of the workload at each site that answers ([Old ledgers](../docs/old-ledgers.md)). `tack prune` never deletes an abandoned or taken-over run. | A search observed to take seconds while the operator prunes: a retention that runs by itself, in a controller. Abandoned or taken-over runs that slow searches. |
| A run whose take-over mark did not land, because its site gave no answer to the run that took it over, shows an empty TakenOverBy in `kubectl get sfo`. `tack status` still lists it as `TakenOver`. | A take-over whose mark is observed missing. |

<h1 style="text-align: center;">[RFC#0009] The CLI and its Dry Run</h1>

# Abstract

`tack` has six commands that act on runs, `plan`, `run`, `resume`, `status`, `abandon` and `prune`, and `completion`, which prints a shell completion script. The help, the man pages and the skill document for AI agents all come from one definition of the commands. A release builds its archives the same way each time from the same commit, and signs and attests what it publishes.

# Overview

| Command | Changes | Does |
|---|---|---|
| `tack plan -f WORKLOAD --to SITE [--mode planned\|site-loss]` | nothing | prints every step and change; `-o yaml` or `-o json` the ledger it would create |
| `tack run -f WORKLOAD --to SITE [--mode ...]` | clusters and Git | prints the plan, asks, creates the ledger, runs |
| `tack resume RUN (-f WORKLOAD \| --context CTX)` | clusters and Git | prints the ledger, asks, runs the remaining steps |
| `tack status [RUN] (-f WORKLOAD \| --context CTX)` | nothing | lists runs, or shows one |
| `tack abandon RUN (-f WORKLOAD \| --context CTX)` | the run's ledger | prints the ledger and its holds, asks, records `status.abandoned` |
| `tack prune -f WORKLOAD --keep N` | the ledgers of old runs | lists the runs and what it does to each, asks, searches again, deletes |
| `tack completion bash\|zsh\|fish\|powershell` | nothing | prints a shell completion script |

| Release asset | Holds |
|---|---|
| `tack-vX.Y.Z-OS-ARCH.tar.gz`, `.zip` on `windows` | the binary, its man pages, the CRD, `LICENSE` and `README.md` (Requirement 12) |
| `tack-vX.Y.Z-OS-ARCH.cdx.json` | the CycloneDX SBOM of that archive's binary (Requirement 24) |
| `tack-X.Y.Z.tgz` | the chart of the CRD and of optional roles (Requirement 29), also at `oci://ghcr.io/takodotid/charts/tack` |
| `failover.tako.id_sitefailovers.yaml` | the CRD |
| `SHA256SUMS`, `SHA256SUMS.sigstore.json` | the SHA-256 of each asset above; the Sigstore bundle of that file (Requirement 23) |

# Motivation

| Choice | Reason |
|---|---|
| Captured values named in every message, and one filter for URLs | A `Wait` on the demotion token timed out with both the substituted and the live token in its message. Messages from Flux and Strait, such as a GitRepository that cannot clone a URL with a token, reached the ledger unchanged. |
| Typed confirmation; `--yes` only for an approved run | A habit of pressing "y" does not start a failover. Scripts and agents cannot start a run by accident. |
| Read the sites again after the confirmation, and before the first Failover step of every process | `tack run` waited at the confirmation with no time limit. If the same switch finished meanwhile, a planned plan ran a second time and promoted with a token already used, which makes CloudNativePG hold the Cluster as unrecoverable ([RFC#0004] Motivation). A resume after the operator switched the primary by hand demoted a replica. The ledger holds no copy of the plan's read, so the driver is asked again. It compares what it reads, not `resourceVersion`: CloudNativePG writes status often, and a write that changes nothing must not block a failover. |
| A run abandoned before its start does not make a plan stale | A run that lost the race of [RFC#0003] Requirement 8 while the operator confirmed changed nothing, yet the plan was refused. |
| The clusters and the Git URL before the confirmation | An operator could not see that a context reached another cluster. |
| Skill and man pages from the command definitions; explicit contexts per site | They cannot drift from `--help`. Tack must never act on whichever cluster is current. |
| A kube context or site name that YAML reads as other text is refused unquoted | `kubeContext: on` became `true`, a site name such as `n` or `yes` became a boolean, and `010` became `"8"`. The error named neither the field nor the fix. |
| The Workload file follows the ledger's API version, and v0.1.x files still load | The ledger holds a copy of the Workload's spec ([RFC#0003]). `v1` has the same schema as `v1alpha1`. |
| `tack abandon`, reading the ledger back, and listing the holds as the ledger records them | A run the operator abandoned could be resumed until a new run took it over. A CRD older than v1.3.0 drops the field without an error. Nothing writes the ledger when a hold is removed by hand, and reading the objects would add a read of each site. |
| A list of runs names a site that gave no answer, and exits 1; each search names a site it leaves out | `tack status` exited 0 and left out the runs of an unreachable site, and with both down printed an empty table. An operator reads that as no run there. The searches still go on ([RFC#0003] Requirements 8, 14 and 18), so a site loss does not block its failover. |
| `--force` for `tack abandon` and `--take-over`, not for `tack resume` | A process killed a moment ago keeps its Lease fresh for up to 40 s, and a run of v1.4.0 has no Lease, so the refusal can be wrong. `tack resume` is the way on after a process died, and the ledger's writes stop one of two processes on a run. |
| `TakenOver` in the list of runs | A taken-over run showed its last state, such as `Stopped StepFailed`. |
| Colour and symbols on a terminal only | An operator reads a failover plan under stress. Circuit (`takodotid/circuit`) has a settled CLI style: colour only on a terminal and never with `NO_COLOR`, one meaning per colour, thin-line tables. A script, a log and an agent read the same plain text. No spinner: a progress line is a record. |
| Times on progress lines, and each step's times in `tack status` | A terminal's log could not be laid next to the ledger or the API servers' audit logs. |
| Docs named by a link at the binary's release tag | An operator who runs a released `tack` has no checkout. The tag keeps the runbook in step with the code that printed it. |
| A release only from a signed tag on `main` with green CI, built and tested before any push | Any `v*` tag, on any commit, published a release, in one job that built and published with write access and no environment. |
| Keyless signatures and attestations | `SHA256SUMS` came from the same release as the archives, so a check proved only that a download was intact. Sigstore signs with the workflow's short-lived identity: no key can leak. |
| The same archives from the same commit | `tar` kept the build's time and owner, and a `.zip` written in another time zone differed in its MS-DOS time. |
| Actions, tools and images pinned; a vulnerability scan | The release ran whichever helm was the latest, with the token to push packages. The e2e checked its tools against checksums fetched from the same server. |
| The chart's roles stay off by default, and its notes name the check of who may write ledgers | Roles that bind to no subject grant nothing, and take no access away from another subject, such as a GitOps controller bound to `cluster-admin`. Turning them on by default made `helm upgrade` of a v1.4.0 release fail next to a hand-made Role of the same name, and for an installer who may not manage RBAC. Only a check of each other subject finds who may write ledgers. |
| Optional roles in the chart, each in the scope of its rows | A ClusterRole bound across the cluster would grant the object rows in every namespace. |
| `tack prune` lists every run before it asks, says why it keeps a run, and searches again after | Deleting a ledger cannot be undone. A run can start while the operator confirms. Without the reason, a run kept by another site's clock or by a `Rebuild` would look like a fault in `--keep`. |
| The chart's notes print `crds.install` and `crds.keep` | A release installed with `crds.keep=false` kept it across `helm upgrade` without values, and an upgrade with any other `--set` set it back to `true`. Nothing showed the value in force. |
| A second signal ends `tack` at once, and SIGHUP counts as a signal | A second Ctrl-C did nothing while the ledger write that records the stop took up to 30 s. SIGHUP ended `tack` without recording why the run stopped. |

# Requirements

Unless a requirement names another check, unit tests check it.

1. `tack plan` MUST NOT write to any cluster or to Git. Checked by unit tests that fail on any write call, and by golden tests of its output.
2. The dry run MUST print, in run order and grouped by phase: each step's ID, site, description, and exactly what it changes or waits for (annotations, merge patches, conditions and timeouts, captured names, the Git file, path and value of each field, the checks), the follow-ups, and notes on Git and on unreachable sites, each saying that the runs whose ledgers are there were not read.
   - Before the steps it MUST print each site's WAL position and how it compares with the others, when the driver reads them ([RFC#0004] Requirement 13).
   - Before the steps it MUST also print, per site, the context, the API server the context points at, and the UID of the cluster's `kube-system` namespace ([RFC#0003] Requirement 19), then the Git URL without credentials.
3. `tack run` MUST print the plan, then require the operator to type the workload's name, unless `--yes` is given. Without a terminal and without `--yes`, it MUST refuse and change nothing.
4. `tack resume` MUST print the ledger, then per site the context, the API server it points at in the operator's kubeconfig and the cluster the run recorded, then the Git URL without credentials, and confirm the same way. Its decision flags are `--accept-git-head SHA` ([RFC#0006]) and `--fence SITE` ([RFC#0007]). `tack plan` and `tack run` take `--accept-behind` ([RFC#0004] Requirement 14), a usage error without `--mode site-loss`.
5. `tack run --take-over RUN` MUST let the new run take over the holds of `RUN` ([RFC#0005]), and record it ([RFC#0003] Requirement 17). `RUN` then cannot resume ([RFC#0003] Requirement 18). The flag MAY be repeated, once per run, and each value MAY list runs separated by commas. After the confirmation and before the ledger's create, for each `RUN` found at a site that answers, it MUST refuse to take over a run that a tack process may still run, unless `--force` is given ([RFC#0003] Requirement 28). `--force` without `--take-over` MUST be a usage error.
6. Every site client MUST be built from the site's `kubeContext` in the kubeconfig (`--kubeconfig` or the standard loading rules). A context missing from the kubeconfig MUST be an error. Tack MUST NOT fall back to the current context.
7. Exit codes MUST be:

| Code | Meaning |
|---|---|
| 0 | success |
| 1 | error |
| 2 | usage error, including a refused confirmation without a terminal |
| 3 | the run stopped for the operator |
| 4 | the run waits for something outside it |

8. `tack --skill` MUST print a skill document: YAML frontmatter with `name` and `description`, then Markdown built from the command definitions. It MUST say that an agent never starts `tack run` or `tack resume` without an explicit instruction from a human for that run, and that `tack plan` comes first.
9. Man pages MUST be generated from the command definitions: `tack(1)` and one page per subcommand, shipped in the release archives with the binary.
10. Tack MUST NOT print a secret.
    - The text output of `tack status` MUST print captured values by name only. `-o yaml` and `-o json` print the whole ledger, which holds no secret ([RFC#0003]), with the Git URL's user and password replaced by `***` ([RFC#0006] Requirement 14).
    - A step's or run's message, in the ledger and in the output, MUST name a captured value of 8 bytes or more as `$(name)` instead of printing it. A `Wait` on a captured value MUST print neither it nor the live value it compares, only that value's size.
    - Every message that Tack records in the ledger or prints MUST show the user and password of each URL in it as `***`, whatever its source (Flux, Strait, git, an API server): run and step messages, the reason a run is abandoned, progress lines, a plan's notes and sites, the last error line, and `-o yaml`, for a ledger an older Tack wrote too. One function does it.
11. Tack MUST read a Workload file of `apiVersion` `failover.tako.id/v1`, and of `failover.tako.id/v1alpha1` with a warning on stderr that it is deprecated. Any other `apiVersion` MUST be an error. A site name, a reference to one, or a site's `kubeContext`, written as a plain YAML scalar that the decoder reads as other text, such as `n`, `on`, `yes` (booleans in YAML 1.1) or `010` (a number), MUST be refused, with a message that names it and says to quote it. The check reads the file only, not a ledger's snapshot.
12. `make dist` MUST build a release archive for `linux`, `darwin` and `windows`, each on `amd64` and `arm64`. Each archive MUST hold one directory named after it, with the binary, `man/man1/`, the CRD, `LICENSE` and `README.md`. On `windows` the binary MUST be `tack.exe` and the archive a `.zip`; otherwise the binary MUST be `tack` and the archive a `.tar.gz`. Checked by listing each archive.
13. After the confirmation, and before it creates the ledger, `tack run` MUST read again every site the plan read, with the plan's checks, and refuse, changing nothing, when:
    - a site's state as the driver reports it (reachable, role, declared primary, health, the driver's facts, the member's creation time) differs from the plan's, its position left out, since a replica's moves all the time;
    - the driver refuses the request on the new state;
    - a site's cluster differs from the plan's fingerprint ([RFC#0003] Requirement 19); or
    - a run of the workload exists at a site the plan searched that the plan did not find, unless it is abandoned and never recorded its start ([RFC#0003] Requirement 8).

    In each `tack run` and `tack resume`, before the run's first Failover step, while no Failover step has started in any process (each is `Pending` or `Deferred`, with no attempt), Tack MUST read every site again, with the run's checks, and stop with `StepFailed` before the step, which keeps its state, when the driver refuses the request on what it reads. A site whose steps can wait for it and that answers as primary, or declares itself primary, is left out: [RFC#0007] Requirements 6 and 9 decide on it.
14. The first SIGINT, SIGTERM or SIGHUP MUST cancel the run, which then records why it stopped, in a ledger write that outlives the cancel ([RFC#0003] Requirement 20). Any later signal MUST end `tack` at once, with the signal's default action. Checked by a test that sends both to a process.
15. `tack abandon RUN`:
    - MUST print the ledger, then the objects that the ledger records as held by the run and not released, and say that this list is the ledger's record, which a hold removed by hand does not change;
    - MUST then confirm as Requirement 3 says, with a question that says it changes only the run's ledger, then record `status.abandoned` with the time and `--reason` ([RFC#0003] Requirement 8), in a write that carries the ledger's `resourceVersion`, and change nothing else;
    - MUST refuse a run that succeeded with no `Deferred` step, and change nothing for a run already abandoned;
    - MUST refuse a run that a tack process may still run, before it asks and again after, unless `--force` is given ([RFC#0003] Requirement 28);
    - MUST read the ledger back, and fail with a message that names the CRD when the field is not there;
    - once the mark is recorded, MUST say that `kubectl get sfo` shows the mark in its Abandoned column, with the CRD of v1.4.0 or later, and the run's last state in its State column ([RFC#0003] Requirement 15).
16. `tack status` without RUN MUST list, in its state column, a run that is abandoned as `Abandoned`, and one that another run took over, by its `status.supersededBy` or a listed run's `spec.takeOver` or `spec.takeOvers`, as `TakenOver`.
    - When a site gives no answer to its checks ([RFC#0007] Requirement 5), `tack status` without RUN MUST list the runs it read, then name each such site with its error, and exit with code 1. With `-o yaml`, the names and errors MUST follow the ledgers as YAML comments. With `-o json`, they MUST go to stderr, so stdout stays one JSON value.
    - When `tack status RUN`, `tack resume RUN` or `tack abandon RUN` does not find RUN, its error MUST name each site that gave no answer, with its error.
    - Each search for runs that decides whether a plan, a run or a resume goes on ([RFC#0003] Requirements 8, 14 and 18) MUST print a progress line for each site that it leaves out because the site gave no answer, with the error, once per site in each process.
17. Every message, plan note and help line that Tack writes and that names a file of the repository, such as a runbook, MUST name it by its link `https://github.com/takodotid/tack/blob/<ref>/<path>`, with its anchor if any, and MUST NOT name it by its path alone. `<ref>` is the binary's version when that is a release tag `vX.Y.Z`, and `main` otherwise. One function builds the link. Each file and anchor linked MUST exist in the repository. The man pages of a release archive MUST link at the ref of its binary. Checked by unit tests, and for the man pages by `make dist`.

## Releases

18. `make dist` MUST write the same archives, byte for byte, from one commit, one Go version and one `SOURCE_DATE_EPOCH`, whatever the build's time, time zone, umask and user. Every entry MUST have the time `SOURCE_DATE_EPOCH`, owner 0 with no owner names, and mode 0755 for a directory or an executable file and 0644 otherwise. A `.tar.gz` MUST hold no name or time in its gzip header; a `.zip` MUST store its times in UTC. Checked by `make dist`, whose `hack/distcheck` fails on an entry that differs.
19. The release workflow MUST publish only for an annotated tag `vX.Y.Z` whose signature GitHub verifies, whose commit is on `main`, and whose commit's `ci` run of its push to `main` has finished with every job of `ci.yaml` successful. A later commit of `main` MUST NOT cancel that run. Checked by the release's job `gate`.
20. The release MUST NOT push a chart or create a GitHub release before `make verify test` and `hack/release/build.sh` pass on the tag's commit. It MUST publish the assets that this build wrote, checked against their `SHA256SUMS`. CI MUST run `hack/release/build.sh` on each pull request and each push to `main`.
21. A job of the release that runs `make`, or Go code of the module or of its dependencies, on the runner MUST hold read permissions only. `TestReleaseWorkflow` refuses `go`, `make`, `hack/release/build.sh` and `actions/setup-go` in a job that can write.
22. The release MUST NOT replace a published version. It MUST stop when the chart version `X.Y.Z` or the GitHub release `vX.Y.Z` exists, or when the registry or GitHub does not answer that it is absent. It MUST check both before its first push, and each again right before its own push.
23. The release MUST sign the chart, by the digest that the registry gives, and `SHA256SUMS` with Sigstore, keyless, under the workflow's OIDC identity. It MUST attest every asset of the GitHub release with GitHub artifact attestations. All of it MUST happen before the GitHub release exists. A long-lived signing key MUST NOT exist. The release MUST then verify what it published with the commands of [Verify a release](../docs/guide/install.md#verify-a-release), as its last step.
24. Next to each archive, a release MUST hold a CycloneDX SBOM, `tack-vX.Y.Z-OS-ARCH.cdx.json`, made from the build information of that archive's binary. `SHA256SUMS` MUST list every asset of the release but itself and `SHA256SUMS.sigstore.json`. `hack/release/build.sh` fails unless `dist/` holds each asset.
25. A workflow MUST pin every action by commit SHA. kind, kubectl, flux, helm, cosign and vale MUST be pinned by version and SHA-256 in `hack/tools/install.sh`, and the workflows and the e2e's instructions MUST install them with it. The Go tools of `make lint` and `make sbom` MUST be pinned in `hack/tools/go.mod`. Every image that the e2e's nodes pull, and every base image of a Dockerfile under `test/e2e/`, MUST be named by the digest of its index. `make lint` checks the actions, through `hack/release/pinned.sh`, and review checks the workflows' use of `install.sh`. Go, which `actions/setup-go` downloads, is not pinned this way: [What the release does not check](../docs/runbooks/release.md#what-the-release-does-not-check).
26. CI MUST run `go mod verify`, `govulncheck`, `helm lint --strict` and `hack/release/pinned.sh` on each pull request and each push to `main`. Checked by the job `lint` of `ci.yaml`, through `make lint`.

## Progress and status

27. Each progress line that `tack plan`, `tack run`, `tack resume`, `tack status`, `tack abandon` and `tack prune` print MUST start with its time in UTC, to the second, as RFC 3339 writes it, such as `2026-10-27T10:15:00Z`: the lines of the steps, the checks of a site, the notes, the deferrals, the stops and the ledger's writes. The plan, the status, the confirmation and the last error line MUST NOT. A line of a site's checks that is held back to keep the order of the sites ([RFC#0007] Requirement 10) MUST start with the time it was printed, not the time it goes out. Checked by unit tests and by the golden tests of the dry run.
28. `tack status RUN` MUST print:
    - when writes stopped and came back ([RFC#0003] Requirement 29), marking an estimate as one, and the fork point of a site loss ([RFC#0004] Requirement 15);
    - each phase's start and end, each step's start, end, attempts and earlier attempts, as the ledger records them;
    - the run's history ([RFC#0003] Requirement 22), oldest first: each entry's time, state, reason, version, user, flags and message, and the count of entries dropped.

    `-o yaml` prints the history with its messages cleaned as Requirement 10 says.

## The chart

29. The chart MUST create no role, and no binding, unless `rbac.create` is `true`; its templates MUST also render from values that have no `rbac` key, such as those of a release installed by an earlier chart.
    - With `rbac.create`, it MUST grant exactly the rows of the table in [Permissions](../docs/permissions.md), each in its scope ([The chart's roles](../docs/permissions.md#the-charts-roles)): in a ClusterRole, the non-resource URLs, `get` on the namespace `kube-system`, and `create` on `selfsubjectreviews`; in a Role in the release's namespace, the rows for `sitefailovers`, `sitefailovers/status`, `events` and `leases`, with `delete` on `sitefailovers` only when `rbac.prune` is `true`; in a Role in each namespace of `rbac.objects`, the rows for the Workload's Clusters, Poolers, Deployments, Kustomizations, GitRepositories, ConfigMaps, Secrets, SiteServices and ObjectStores, and for `pods`, `pods/proxy` and `backups` when the entry names `clusters`.
    - A rule for the namespace `kube-system` or for an object of `rbac.objects` MUST name it. A kind without names MUST get no rule, and an entry without a namespace, without names, or with the namespace of an earlier entry MUST fail the render.
    - With `rbac.subjects`, the chart MUST bind each role to them: the ClusterRole by a ClusterRoleBinding, each Role by a RoleBinding in its namespace.
    - Each install and upgrade MUST print, in the chart's notes, that writing a ledger is privileged, the accesses that write one, the release's namespace, and the link to [Who may write ledgers](../docs/permissions.md#who-may-write-ledgers) at the chart's release tag `v<appVersion>`, or at `main` when `appVersion` is not `X.Y.Z`.
    - They MUST also print the values of `crds.install` and `crds.keep` in force, say that `helm upgrade` without values reuses them, and warn, while `crds.install` is `true` and `crds.keep` is `false`, that `helm uninstall` deletes the CRD and every ledger, and how to set it back.

    Checked by `deploy/helm/rbac_test.go`, which reads the table, and by the e2e's `TestRoutingFromStrait`, which runs `tack` as a ServiceAccount bound to these roles.

## Old ledgers

30. `tack prune -f WORKLOAD --keep N` MUST print each run of the workload, newest first, with its site, its state as Requirement 16 lists it, its creation time, and `delete` or why it keeps the run ([RFC#0003] Requirement 27).
    - A run kept only because the clocks cannot order it MUST name the run they cannot order it against. A run kept for a follow-up `Rebuild` MUST name the site, and the member's creation time and the run's start, or why the member could not be judged.
    - When it would delete a ledger, it MUST then confirm as Requirement 3 says, saying how many ledgers it deletes. When it would delete none, it MUST say so, and MUST NOT ask.
    - It MUST print a progress line for each ledger it deletes.
    - It MUST exit 0 when it deleted each ledger it listed as `delete`, or none was listed; 1 when it refused, or a delete failed, naming how many it deleted; 2 when `--keep` is missing or below 1, or for a confirmation refused without a terminal.
    - It reads the sites of the Workload file and has no `--context`.

## Terminal output

31. On a terminal, the output of every command MUST mark meaning with colour and symbols:

| Mark | For |
|---|---|
| red | an error line, and a state that stopped or failed |
| yellow | a warning, a follow-up, and a state that waits or goes on |
| green | a step done (`✔ done`), a state that succeeded, and the most caught-up site |
| dim | detail, and the time of a progress line |
| bold | headings |

The plan's sites and WAL positions, and the list of runs, MUST be tables with thin lines whose last column wraps to the terminal's width. With `NO_COLOR` set to any non-empty value, the output MUST hold no colour, and keeps its symbols and tables. Written to anything but a terminal, the output MUST be byte for byte what it was before: no colour, symbol or table line. Text, status names, step IDs, exit codes, the ledger, `-o` output and the typed confirmation MUST stay exact. Checked by unit tests for a terminal, `NO_COLOR` and a pipe, and by the golden tests.

## Machine output

32. Wherever a command takes `-o yaml`, it MUST also take `-o json`, with the same content: one object as indented JSON, or, for `tack status` without RUN, one `List` (`apiVersion: v1`) whose `items` are the YAML output's documents, in order. Any other value of `-o` but `text` MUST be a usage error. Both are stable output. Checked by unit tests that parse both and compare them.

## Shell completion

33. `tack completion bash|zsh|fish|powershell` MUST print a completion script for that shell, and any other shell MUST be a usage error. Completion MUST complete the commands, their flags, the values of `--mode` (`planned`, `site-loss`) and `--output` (`text`, `yaml`, `json`), Workload files (`.yaml`, `.yml`) for `--file`, and, for `--to`, `--from` and `--fence`, the site names of the Workload file that `--file` names. It MUST read nothing but that file: no cluster, no kubeconfig, no Git. A RUN argument is not completed: run names live in ledgers at the sites. Checked by unit tests with a factory that fails on any request for clients.

# Design

**Workload file.**

```yaml
apiVersion: failover.tako.id/v1
kind: Workload
metadata:
  name: pg-main
spec:
  driver: cnpg
  sites: [...]        # [RFC#0004]
  git: {...}          # [RFC#0006]
  ledger: {namespace: tack-system}
  routing: {...}      # [RFC#0008], optional
  timeouts: {demotion: 10m, promotion: 10m, flux: 5m, routing: 2m}
```

`--from` defaults to the primary that the `to` site declares. With `-f`, `resume` and `status` search the ledger namespace of every reachable site; with `--context`, that one context, and `resume` then uses the Workload snapshot in the ledger, not the file.

**Releases.** Each job of `release.yaml`, in order. A review in the environment `release` holds every later job.

| Job | Needs | Permissions | Does |
|---|---|---|---|
| `gate` | | `contents: read`, `actions: read` | Requirements 19 and 22 |
| `test` | `gate` | `contents: read` | `make verify test`, then `hack/release/build.sh`: the archives, SBOMs, CRD, chart and `SHA256SUMS`, kept for `publish`. The chart's files take the time `SOURCE_DATE_EPOCH`, so its archive is reproducible too |
| `publish` | `test` | `contents: write`, `packages: write`, `id-token: write`, `attestations: write` | checks the assets against `SHA256SUMS`, attests them, signs `SHA256SUMS`, pushes and signs the chart, creates the GitHub release, then verifies them; runs shell, `helm`, `cosign`, `docker login` and `gh` only |
| `pages` | `publish` | `contents: read`, `pages: write`, `id-token: write` | calls `pages.yaml` with `deploy`: builds the documentation site from the tag with `bun`, then publishes it to GitHub Pages; runs no Go and no `make` |

A re-run of failed jobs runs those jobs and the jobs after them. A push that an earlier attempt made stops the re-run (Requirement 22), and the version is released as the next patch version ([Release](../docs/runbooks/release.md)).

The signatures and attestations name the workflow and the tag:

| Field | Value |
|---|---|
| Certificate identity | `https://github.com/takodotid/tack/.github/workflows/release.yaml@refs/tags/vX.Y.Z` |
| OIDC issuer | `https://token.actions.githubusercontent.com` |
| Repository of the attestations | `takodotid/tack` |

**Rules for AI agents**, in the root help and therefore in the skill document, with Requirement 8 and [the CLI reference](../docs/reference/cli.md): never pass `--yes`, `--fence`, `--accept-git-head`, `--accept-behind`, `--take-over` or `--force` unless the instruction names it; `tack plan` and `tack status` only read; when a run stops, report its reason and wait.

# Security Considerations

- Tack acts with the operator's kube credentials for each context ([Permissions](../docs/permissions.md)). The kubeconfig and Git credentials stay with the operator's tools; Tack stores none.
- The workflow's token and its OIDC identity exist only while its jobs run, and only `publish` can write ([Releases](#design)).

# Limitations

None that an operator must know. What the release workflow does not check is in [What the release does not check](../docs/runbooks/release.md#what-the-release-does-not-check).

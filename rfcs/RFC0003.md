<h1 style="text-align: center;">[RFC#0003] The Ledger: Schema, Phases and Resuming</h1>

# Abstract

Each run is a `SiteFailover` object (`failover.tako.id/v1`). Its spec holds the whole plan and a copy of the workload's configuration; its status records each phase and step before it starts and after it ends, with the values later steps need. A run resumes from this object and nothing else. The schema is Tack's contract with its users and with a future controller.

# Overview

| Part | Holds | Written |
|---|---|---|
| `metadata` | name `<workload>-<UTC yyyymmdd-hhmmss>` of the plan, with `-2` to `-9` appended when the name is taken (Requirement 7), label `failover.tako.id/workload: <workload>`, namespace from the Workload (default `tack-system`) | at creation |
| `spec` | mode, `from`, `to`, the Workload snapshot, the steps, the cluster of each site that answered the plan, the runs it takes over | at creation, never after |
| `status` | state, reason, phases, steps, captured values, held objects, Git revisions, follow-ups, the cluster of each site first read during the run, the run that took it over, an abandoned mark, the history of the run's state | before and after every step |

# Motivation

| Choice | Reason |
|---|---|
| The plan lives in `spec` | Resume runs the plan that was approved, even if the Workload file changed since. |
| The Workload is copied into `spec` | Resume needs the sites, contexts and Git mapping of the run, not of today's file. |
| `spec` is immutable | A ledger that can be rewritten is not a record. |
| The ledger lives at `to` | `to` must answer for any run to succeed; in a site loss, `from` does not. |
| `--take-over` more than once | Found in a review (#38, item 2), inferred from the code and shown in a CLI test: the flag took one value, so a run that had to take over two stopped runs could not start; the second refused it. |
| A take-over is in the new run's spec, and a run taken over or started before another never resumes | Found in a review (#27) and reproduced in a unit test: run-1, a site loss toward b, stopped at `promote-b`, and b was lost too. run-2 took it over and promoted c. When b came back, `tack resume run-1` promoted b: two primaries. The take-over lived only in run-2's process, and run-1's plan was older than the sites. |
| The read of a site's cluster is repeated like the site's check | Found in a review (#38, item 5) and reproduced in a unit test: one connection reset on the read right after the site answered its check stopped a run with `StepFailed`, and in a site loss a site that answered its check, then nothing more, stopped the run instead of deferring its steps. |
| Each site's cluster is recorded, and checked in every process | Found in a review (#32) and reproduced in a unit test: a resume with a kubeconfig whose context for site a reached another cluster, with the same object names, held and demoted the Cluster there. A site was known only by its context name, which each operator's kubeconfig defines. |
| The first status write outlives an interrupt, and a ledger without a state never resumes | Found in a review (#28) and reproduced in a unit test: the API server drops status on create, and the first status write used the run's cancellable context. A run interrupted between the two left a ledger without its start or its `Rebuild` follow-up. A resume then ran every step and ended `Succeeded` without the follow-up, so a later planned run onto the diverged member was allowed (Requirement 14). |
| A dry run before the ledger exists | An API server whose CRD is older than Tack drops the spec fields it does not know, without an error. A ledger without its take-over would let the run it took over resume. |
| A taken name gets a suffix, unless its run may still run | Found in the e2e of PR #36 (#37), on kind: a run's name holds its plan's time to the second, so a run with `--take-over` planned in the same second as the run it took over failed with "already exists". A run with the name that may still run can be a second `tack` process starting the same switch, so it keeps refusing. |
| After the run's commit, Hold accepts that commit | Found in a review (#35, row 14) and reproduced in a unit test: a lost site came back after the run's commit, and Flux there had applied it, which fenced the site. The resume stopped in Hold with `GitChanged`, and `--accept-git-head` after the commit sets the release revision, which Hold did not accept: the run could not finish. |
| Order runs by the clock of each ledger's site, with a margin across sites | Found in a review (#38, item 7, and PR #42), inferred from the code and shown in a unit test: "created after" was a strict comparison of `creationTimestamp` values, which have whole seconds and come from different API servers. A run created in the same second, or a few seconds earlier by a clock that is behind, did not count, and the older run resumed with a plan that may no longer match the sites. A run whose ledger is at the same site has the same clock. |
| A resume composes the plan again, and refuses steps that differ | Found in a review (#35, row 11), inferred from the code, then shown in a unit test: `tack resume` ran whatever steps a ledger held with the operator's credentials, such as a patch of another object, a capture of a Secret's field or another Git change, and a ledger is as easy to write as the operator's RBAC allows. The ledgers that v1.0.0, v1.1.3, v1.2.0 and v1.2.1 write for the same Workload and request have the same steps, descriptions included, so the check refuses none of them. |
| `tack resume` refuses a run that cannot resume before it asks, and searches again after | Found in a review (#38, item 3) and reproduced in a CLI test: the refusal came only after the operator typed the workload's name, and without a terminal `tack resume` exited 2 for the missing terminal instead of 1 for the refusal. A run can still take this run over while the operator confirms (#27), so the search runs again after the confirmation, with the same checks of each site. |
| After a capture that succeeded, the way on of `TokenMissing` restores the value | Found in a review (#38, item 1) and reproduced on kind: the value was removed from `status.captured` after `capture-token` succeeded. `capture-token` never runs again, so every resume stopped with `TokenMissing`. Copying the old primary's `status.demotionToken` back into the ledger let the run finish. |
| The way on of `GitDiffersFromLive` and `FluxChanged` names `--accept-git-head` | Found while writing the runbooks (#35, row 27), and run on kind: a fix to Git moves the branch past the release revision, so a plain resume stops with `GitChanged`. After `FluxChanged`, the object's generation stays changed, so a plain resume stops again; an accepted head turns that check into a report ([RFC#0005] Requirement 10). |
| A run that ends ends every phase whose steps are done | Found in PR #42 (#46), inferred from the code, then reproduced with a ledger that v1.2.0 wrote: v1.2.0 ended a phase only after one of its steps succeeded, so a site-loss run whose lost site's steps came last in Hold, PromoteToGitOps and Release left them unfinished, and a resume while the site stayed down ended the run with them unfinished. |
| A resume of a `Succeeded` run writes `Running` only with its first step | Found in a review (#35, row 31) and reproduced in a unit test: the resume wrote `Running` before it checked the deferred site. A process that died there, or a site still down, left a finished run `Running`, which refuses every new run of the workload (Requirement 8). |
| A ledger write that got no answer is repeated, with the same `resourceVersion` | Found in a review (#35, row 32) and reproduced in a unit test: one connection reset on a write stopped the run with "another tack process may be running this run", and left it `Running`. A repeat with the same `resourceVersion` cannot overwrite another writer. A write can land and lose its answer; its repeat then conflicts with itself, which the read tells apart. |
| A run searches again once its ledger exists | Found in a review (#35, row 35), and reproduced in a unit test: two `tack run` processes both found no active run, then both created a ledger and ran. Holds serialize them, and the loser was left not `Succeeded`, which refused every later run. After its create, each process sees the other's ledger, so at most one goes on. The loser ran no step; its mark keeps it from refusing later runs. A ledger without a state is refused by every `tack resume` since v1.2.0. |
| The field manager `tack` on ledger writes | Found in PR #43, observed on kind with `--show-managed-fields`: ledger writes named no field manager, and the API server took the one of the client's user agent, the binary's name. A binary named otherwise, such as `tack.exe`, would have written under that name (inferred). |
| A Reason column in `kubectl get sfo` | Found in a review (#35, row 49): the list showed a run `Stopped` or `Waiting` without why. |
| An Abandoned column in `kubectl get sfo`, after Age | Observed in a two-site test of v1.3.0 (#59): `kubectl get sfo` showed an abandoned run as `Stopped`, while `tack status` listed it as `Abandoned`. `status.state` keeps its values (Requirement 9), so the mark gets a column of its own. A column added last leaves each earlier column at its position, for a script that reads them by position. |
| Each write records its tack's version, and an older release refuses the ledger | Found in a review (#35, row 26): the schema verified, the loss inferred. A status write replaces the whole status, so a tack drops every status field it does not know, as an older CRD does. Once a release adds a status field, such as `status.history`, an older tack that resumes the run drops it. A newer patch release is refused too: a run in flight would otherwise follow the older tack's step rules. |
| A history of the run's state, with who and which flags, and Events | Found in a review (#35, row 29), verified in the code: a resume cleared the run's reason and message, and each attempt overwrote the step's message, so an earlier stop disappeared. `--fence`, `--take-over`, `--accept-git-head` and who ran each process were recorded nowhere, and the ledger got no Events. An incident's timeline could not be rebuilt. |
| The history's user comes from the API server | A kubeconfig names its user for the operator's host only. The ledger's API server names the user that its audit log records. |
| The history keeps its first entry, the newest ones and a count | An entry per state change bounds the history by the number of stops and resumes, not by the plan. The first entry records the start, its `--take-over` and who started it; the newest record the stop at hand. |
| Events are best effort | An Event lives about an hour, and a site may refuse it. A run must never stop, or wait, for one: the history is the record. |
| Optimistic concurrency on every write | Two `tack` processes on one run would interleave steps; the second write fails instead. |
| `v1` is stored; `v1alpha1` stays served, deprecated, with the same schema | Ledgers written by v0.1.x are stored as `v1alpha1` and must stay readable: they are the record of past runs. A v0.1.x CLI keeps working while the sites are upgraded one at a time. One schema needs no conversion webhook. |
| `v1alpha1` stays in the CRD | The API server refuses a CRD that drops a version listed in its `status.storedVersions`. |
| The `v1alpha1` version is a copy of `v1`, made by `make generate` | Two sets of Go types could drift apart; a copy cannot. |
| Ledgers are listed in pages of 100 | Measured for #35 row 47: a search at a site with 1,000 ledgers of a two-site run read them in one answer of 13.5 MB. A page bounds each answer: 1.35 MB for those ledgers. The largest ledger measured, of a run on 10 sites with a full history, is about 204 KB, so a page holds at most about 20 MB. The search still reads every ledger: the total is unchanged. |
| An expired page lists every ledger again in one request | It is what client-go's pager does. The pages follow one another at once, so a snapshot that expires between them is not expected. |
| Old ledgers are deleted by `tack prune`, which the operator runs | Found in a review (#35, row 47) and measured for it: each search for runs reads every ledger of the workload at each site, and ledgers were never deleted, so the cost of each search grew with the number of runs (#58). The operator decides when, as for every other change Tack makes. |
| `tack prune` deletes only when every site answers and every run is finished, and keeps what a later run needs | Inferred from the code for #58: a search for runs reads the ledgers to decide whether a run starts, resumes or is refused (Requirements 8, 14 and 18). Deleting a newer run lets an older run that is not finished resume. Deleting a run with a `Rebuild` follow-up lets a planned run onto a member that diverged. A run taken over whose mark did not land counts as taken over only through the spec of the run that took it over: deleting that run makes it block new runs again. A site that gives no answer may hold any of these. |

# Requirements

1. The CRD MUST be generated from the Go types in `api/v1`. Checked by `make verify`.
2. `spec` MUST be immutable: the CRD carries the CEL rule `self == oldSelf` on `spec`.
3. `spec.steps` MUST hold every step of the run, and `spec.workload` the Workload's name and spec as they were when the run started.
4. Before a step starts, the ledger MUST record it `Running` with `startedAt` and its attempt count; after it ends, `Succeeded`, `Failed` or `Deferred` with `finishedAt` and a message, together with any value it produced (captured value, held object, Git commit) in the same write. A Release step also records the object's generation while it runs, before it removes the hold ([RFC#0005] Requirement 9).
5. Every status write MUST carry the `resourceVersion` it read, so a concurrent writer makes it fail. A write that gets no answer, or an answer 5xx or 429, MUST be repeated with the same `resourceVersion`, for up to 30 s in all. When a repeat conflicts, Tack MUST read the ledger, and count the write as done only when the ledger holds the status it sent. Any other failed write MUST end the process without running further steps, and its message MUST name the failure: another writer on a conflict, the permission on a refusal, the missing ledger when it is gone. Checked by unit tests.
6. `tack resume` MUST take the plan from `spec.steps` and the progress from `status.steps`, and MUST NOT re-plan. A step recorded `Running` MUST run again ([RFC#0002] makes that safe).
7. The ledger MUST be created at the `to` site, in the Workload's ledger namespace. Creating it MUST NOT replace a ledger that exists. When a ledger has the run's name, and its run is `Succeeded`, was taken over (`status.supersededBy`), is abandoned (`status.abandoned`), or is the run this run takes over, `tack run` MUST try the name with `-2` appended, then `-3`, up to `-9`; when the ledger's run is any other, or every name is taken, the run MUST fail and create nothing. Creating it MUST also fail, and create nothing, when a dry-run create shows that the site's CRD drops a field of the spec; the error MUST say to apply this version's CRD there.
8. A run MUST NOT start while another run of the same workload, at any reachable site, is not `Succeeded`, unless the operator names it with `--take-over`. A run that another run took over (Requirement 17), or that is abandoned (`status.abandoned`), does not count. Once its ledger exists, before its first status write, `tack run` MUST search again, with the checks of the search before it; when it finds such a run, or the search fails, the run MUST end before any step, and record `status.abandoned` with the time and the reason as its only status, with its entry in `status.history` (Requirement 22) and `status.writtenBy` (Requirement 24). The operator records it with `tack abandon` ([RFC#0009] Requirement 15), which keeps the rest of the status. Checked by unit tests.
9. The run's state MUST be one of:

| State | Meaning | Next |
|---|---|---|
| `Running` | a process runs the plan, or one was interrupted while it did | `tack resume` continues it |
| `Waiting` | the run waits for something outside it; only reason `GitUnreachable` | `tack resume` once it is back |
| `Stopped` | something unexpected; the operator decides | `tack resume` with the decision's flag |
| `Succeeded` | every step that could run has run | none; deferred steps run if their site answers on a later `resume` |

A `tack resume` of a `Succeeded` run MUST leave it `Succeeded` until one of its steps starts, and record it `Running` in the write that records that step `Running`. Checked by unit tests.

10. A `Stopped` or `Waiting` run MUST carry one reason. The steps of each way on are in [docs/runbooks/stop-reasons.md](../docs/runbooks/stop-reasons.md).

| Reason | When | Operator's way on |
|---|---|---|
| `GitUnreachable` | Git cannot be fetched or pushed | resume when Git is back |
| `GitChanged` | the branch moved during the run, Flux applied a revision other than the run's base or the head the operator accepted (after the run's commit: also that commit, or the head the operator accepted after it), or the branch moved past the run's commit before a release ([RFC#0005] Requirement 8) | review, then `--accept-git-head <sha>`. When the stop names one commit, `<sha>` is that commit, or `HEAD` for it ([RFC#0006] Requirement 10) |
| `GitDiffersFromLive` | Git, as Flux renders it, differs from live before release | fix Git, then `--accept-git-head <sha>` of the fix |
| `TokenMissing` | a captured value is empty or absent; or, before the promotion, it differs from the value at its source now ([RFC#0007] Requirement 9) | inspect the workload, then resume. When the step that captured the value succeeded, restore the value from the workload first. When the value at its source changed, the run's plan may be stale: abandon the run ([docs/runbooks/abandon-run.md](../docs/runbooks/abandon-run.md)) |
| `FencedSiteIsPrimary` | a site whose steps are deferrable answers as primary, or declares itself primary, in the read before its steps ([RFC#0007] Requirement 6); or a site but `to` answers as primary, or declares itself primary, in the read of the other sites before a Failover step after the demotion, the promotion among them ([RFC#0007] Requirement 9) | `--fence <site>`. When no step of the run is left to fence the site, such as `from` promoted again by hand, the run's plan may be stale: abandon the run ([docs/runbooks/abandon-run.md](../docs/runbooks/abandon-run.md)) |
| `HeldByAnotherRun` | an object is held by another run or by hand | finish that run, or `--take-over` |
| `FluxChanged` | Flux changed a released object | inspect; the switch may be undone. For an expected change, `--accept-git-head <sha>` |
| `SiteMismatch` | a site's context reaches another cluster than the run recorded (Requirement 19) | point the context at the site's cluster, then resume; if the site's cluster was rebuilt, start a new run with `--take-over` |
| `StepFailed` | any other error, such as a timeout | fix the cause, then resume |

11. Each step's state MUST be one of `Pending`, `Running`, `Succeeded`, `Failed`, `Deferred`.
12. Each phase MUST be recorded with `startedAt` when its first step starts, and `finishedAt` once each of its steps is `Succeeded` or `Deferred`. A run that ends `Succeeded` MUST record the end of each such phase, also of one that a ledger of an earlier release left unfinished: at the last `finishedAt` of its steps, or at the run's end when a step records none. Checked by unit tests.
13. A change that would break a user of `v1` MUST be a new API version. Compatible additions MAY stay in `v1`.
14. A plan MUST read the earlier runs of the workload at every reachable site. When one of them recorded the follow-up `Rebuild` for the target site, and the target's member was created before that run started (its `status.startedAt`, or its `metadata.creationTimestamp` when that is unset), a `Planned` run MUST be refused, and a `SiteLoss` plan MUST note it. A member's status cannot show that it diverged; the ledger can.
15. The CRD MUST serve and store `v1`. It MUST also serve `v1alpha1`, deprecated, with the same schema, subresources and printer columns as `v1`, and no conversion webhook. The printer columns MUST be, in order: Workload, Mode, From, To, State, Reason, Phase, Age, then Abandoned, the date of `status.abandoned.at`, empty for a run that is not abandoned. Checked by `api/v1/crd_test.go`.
16. Tack MUST read and write ledgers as `v1`. When a site does not serve `v1`, the error MUST say to install or upgrade Tack's CRD there.
17. A run started with `--take-over RUN` MUST record `RUN` in its `spec.takeOver`, and MUST take over the holds of `RUN` in every process that runs it. It MUST then try to write its own name into `status.supersededBy` of `RUN`'s ledger; when that ledger does not answer, the run MUST go on. `--take-over` MAY be given more than once: the run then records the first run named in `spec.takeOver`, every run named in `spec.takeOvers`, in the order named, and acts as above for each. Every rule of this RFC about a run that another run takes over, or about the run a run takes over, MUST hold for each run in `spec.takeOver` or `spec.takeOvers`. Checked by unit tests.
18. Before it asks the operator to confirm, and again after the confirmation before it runs a step, `tack resume` MUST search the workload's runs at every reachable site of the run's Workload snapshot, and MUST refuse the run, changing nothing, when its `status.supersededBy` or `status.abandoned` is set, another run's `spec.takeOver` or `spec.takeOvers` names it, or another run of the workload was created after it. Its plan may then no longer match the sites. Each ledger's `metadata.creationTimestamp` comes from the API server of its site, to the second: another run whose ledger is at the same site counts as created after it when created in the same second or later; one whose ledger is at another site, when created less than 10 s before it or later. An abandoned run that never recorded its start ran no step, and a run that this run takes over is older: neither counts as created after it. Checked by unit tests.
19. The plan MUST record, for each site that answers, the UID of its cluster's `kube-system` namespace in `spec.fingerprints`. In each `tack run` and `tack resume`, before a site's first step, Tack MUST read that UID again, and stop with `SiteMismatch` before the step, which keeps its state, when it differs from the record. A site without a record, such as one lost at plan time, MUST be recorded in `status.fingerprints` on its first read, and checked against that record after. A read of the UID that gets no answer, or an answer 5xx or 429, MUST be repeated with the pauses of the site's checks ([RFC#0007] Requirement 5), up to 3 reads in all, in the plan and in the run. When the last read got no answer, a deferrable step MUST be `Deferred`, as on an unreachable site, and any other step MUST stop the run with `StepFailed` before the step, which keeps its state. Checked by unit tests.
20. Tack MUST write the ledger's first status, with every step `Pending`, `startedAt` and the follow-ups, before any step starts, in a write that an interrupt of the run does not cancel. `tack resume` MUST refuse a ledger whose status has no state, before it asks the operator to confirm: none of its steps ran, and its follow-ups are not in it. The way on is a new run with `--take-over`. Checked by unit tests.
21. Before it asks the operator to confirm, `tack resume` MUST compose the run's plan again, as [RFC#0002] Requirement 6 orders it, from: the Workload snapshot, `spec.from`, `spec.to` and `spec.mode`; the driver's steps, objects and Git changes for them ([RFC#0002] Requirement 2); the Kustomization each `Hold` step names; and the file, path and document of each change of the `Git` step. The `Git` step's changes MUST be the driver's, in order, with the same values, except an optional removal that the Workload does not map ([RFC#0006] Requirement 6). A run whose `spec.steps` differ from that plan in anything but a step's description MUST be refused, changing nothing, with a message that names the first difference. A run that succeeded with no `Deferred` step is not checked: nothing of it runs. Checked by unit tests, against the ledgers of earlier releases too.
22. Tack MUST append one entry to `status.history` in each status write that changes the run's state, and MUST NOT change an earlier entry. The entry's state is the run's state after the write, or `Abandoned`, or `TakenOver`:

| Write | Entry |
|---|---|
| The first status write of `tack run` (Requirement 20) | `Running` |
| The write of `tack resume` that records the run `Running`; for a `Succeeded` run, the write that records its first step `Running` (Requirement 9) | `Running` |
| A stop, a wait | `Stopped`, `Waiting` |
| The end of a run (Requirement 12) | `Succeeded` |
| The abandonment by the search after the create (Requirement 8), or by `tack abandon` ([RFC#0009] Requirement 15) | `Abandoned` |
| The mark of a take-over (Requirement 17), in the ledger of the run taken over | `TakenOver` |

Each entry MUST hold: the time; the state; the run's reason and message, or the reason of the abandonment, or the run that took it over; the version of the tack that wrote it; the user that the API server of the ledger's site names for that process's credentials, empty when it does not say; and the operator's decision flags of that process, `--take-over`, `--fence`, `--accept-git-head` with the commit it stands for, and `--yes`; a `TakenOver` entry holds the `--take-over` that names its run. The message MUST be cleaned as [RFC#0009] Requirement 10 says, then cut to at most 1024 bytes. The history MUST hold at most 100 entries: before an entry that would make 101, Tack MUST drop the oldest entry but the first, and add one to `status.historyDropped`. A repeated write (Requirement 5) appends its entry once. Checked by unit tests: `TestHistoryStaysWithinBound` stops and resumes a run 60 times, each stop with a message of about 4 KiB.
23. After each write of Requirement 22, and after each write that records a step `Running`, `Succeeded` or `Deferred`, Tack MUST create a Kubernetes Event on the ledger, in the ledger's namespace at its site: reason `Run<state>` or `StepStarted`, `StepSucceeded`, `StepDeferred`; type `Warning` for `Stopped`, `Waiting`, `Abandoned` and `StepDeferred`, `Normal` otherwise; the message cleaned and cut as in Requirement 22. Events are best effort: Tack MUST NOT repeat one, MUST wait at most 5 s for one, and after one fails MUST send no more in that process, print one progress line that says so, and go on. Checked by unit tests.
24. Every status write MUST record the version of the tack that writes it in `status.writtenBy`. When `status.writtenBy` names a newer release than the tack's own, `tack resume` and `tack abandon` MUST refuse the run before they ask the operator, and the mark of a take-over (Requirement 17) MUST NOT be written, all changing nothing, with a message that names both versions; the run that takes over goes on, as when that ledger does not answer. Versions compare as releases `vX.Y.Z`; a build after a release, as `git describe` names it, such as `v1.3.0-5-g1fda25c`, counts as newer than that release and older than the next. A version that names neither, such as `dev`, is not compared. `tack status` MUST still read the ledger, and say which tack wrote it. A run that succeeded with no `Deferred` step is not checked: nothing of it runs. Checked by unit tests, against the ledgers of earlier releases too.
25. Every write of a ledger, its dry-run create, its create and each status write, and the create of each of its Events, MUST name the field manager `tack`. Checked by unit tests.
26. Every list of ledgers, each search for runs and `tack status --context`, MUST ask for at most 100 ledgers in each request, with the same namespace and label selector in each, and MUST follow the API server's continue token until it gives none. When the API server answers a page after the first with 410 Expired, the continue token's snapshot is gone: Tack MUST list the ledgers again in one request without a limit, and use only that answer. Checked by unit tests.
27. `tack prune` MUST delete only the ledger of a run that is `Succeeded` with no `Deferred` step, and MUST keep, of the workload's runs at every site: the `--keep` newest, by `metadata.creationTimestamp`, with `--keep` 1 or more; each run that is abandoned (`status.abandoned`) or taken over (Requirement 17); each run with a follow-up `Rebuild` (Requirement 14); each run whose `spec.takeOver` or `spec.takeOvers` names a listed run that is neither abandoned nor marked by its own `status.supersededBy`; and each run whose `status.writtenBy` names a newer release than the tack's own (Requirement 24). It MUST delete nothing when a site of the workload gives no answer to its checks ([RFC#0007] Requirement 5), when a search fails, or when a run of the workload is not finished: `Succeeded` with no `Deferred` step, abandoned or taken over. After the operator confirms ([RFC#0009] Requirement 30), it MUST search again, with the same checks of each site, and delete nothing when a run appeared or went, or a ledger was written, since the list. It MUST delete one ledger at a time, by name, oldest first, each with the UID and `resourceVersion` it read as preconditions, and MUST stop at the first delete that fails. Checked by unit tests.

# Design

**Spec.**

| Field | Content |
|---|---|
| `workload.name`, `workload.spec` | the Workload snapshot: driver, sites with kube contexts, Git, ledger namespace, routing, timeouts |
| `mode` | `Planned` or `SiteLoss` |
| `from`, `to` | site names |
| `fingerprints[]` | site, `kubeSystemUID`: the cluster of each site that answered the plan (Requirement 19) |
| `takeOver` | the run this run takes over, the first named (Requirement 17); unset for most runs |
| `takeOvers` | every run this run takes over, in the order named, when there is more than one (Requirement 17); unset for most runs |
| `steps[]` | `id`, `phase`, `type`, `site`, `description`, `deferrable`, and one member named by `type`: `hold`, `reconcile`, `patch`, `wait`, `capture`, `git`, `verifyGit`, `release`, `verifyNoop`, `routing` |

**Status.**

| Field | Content |
|---|---|
| `state`, `reason`, `message` | as in Requirements 9 and 10 |
| `phase`, `phases[]` | the current phase; each phase's start and end. A step of a finished phase that runs later, such as a deferred step whose site came back, clears the end until the phase ends again (Requirement 12) |
| `steps[]` | per step: `state`, `startedAt`, `finishedAt`, `attempts`, `message` |
| `captured` | values for later steps, such as `demotionToken` |
| `held[]` | site, object, its Kustomization, `heldAt`, `releasedAt`, `generation` at release, recorded before the hold is removed ([RFC#0005] Requirement 9) |
| `git` | `baseRevision` (what live matched at Hold), `acceptedRevision` (operator's override of the base), `commit` (the run's own), `releaseRevision` (a later head the operator accepted after the commit, [RFC#0006] Requirement 10), `changedRevision` (the one commit the run's `GitChanged` stop named, which `--accept-git-head` must name) |
| `followUps[]` | site, action, reason: work left for the operator, such as `Rebuild` |
| `startedAt`, `finishedAt` | the run's start and success |
| `fingerprints[]` | as in `spec`, for a site first read during the run |
| `supersededBy` | the run that took this run over, when that run could write it |
| `abandoned` | `at` and `reason`: the run never goes on. Written by the search after the create (Requirement 8), or by `tack abandon`. `tack status` lists it as `Abandoned` |
| `writtenBy` | the version of the tack that last wrote the status (Requirement 24) |
| `history[]` | per change of the run's state: `time`, `state`, `reason`, `message`, `version`, `user`, `flags` (Requirement 22) |
| `historyDropped` | the entries dropped from `history` to keep it within 100 |

**History and Events.** Each process that runs a run reads its user once, with a `SelfSubjectReview` at the ledger's site, before its first write. A history holds at most 100 entries of at most about 1.5 KiB each: a message of at most 1024 bytes, the user, the version and the flags. One process adds two entries in most runs: `Running`, then its stop, wait or success. Events carry what the history leaves out, each step's start and end, for as long as the API server keeps them: `kubectl describe sfo RUN` lists them.

| Event reason | Type | When |
|---|---|---|
| `RunRunning`, `RunSucceeded`, `RunTakenOver` | Normal | the history entry of that state |
| `RunStopped`, `RunWaiting`, `RunAbandoned` | Warning | the history entry of that state |
| `StepStarted`, `StepSucceeded` | Normal | a step recorded `Running`, `Succeeded` |
| `StepDeferred` | Warning | a step recorded `Deferred` |

**Base revision.** The `Reconcile` steps of the Hold phase return the revision Flux applied at each site. The first becomes `git.baseRevision`; a different one at another site stops the run with `GitChanged`, unless it is the head the operator accepted (#35 row 37). Once the run committed, the run's commit, or the head the operator accepted after it (`git.releaseRevision`), passes too: a site that comes back after the commit may have applied it ([RFC#0007] Design). The check reads no Git; the Release phase checks the branch before it releases the site ([RFC#0005] Requirement 8).

**API versions.**

| Version | Served | Stored | Since |
|---|---|---|---|
| `v1` | yes | yes | v1.0.0 |
| `v1alpha1` | yes, deprecated: the API server warns on each request | no | v0.1.0 |

The API server converts between the two by changing `apiVersion` only. An object stored as `v1alpha1` is stored as `v1` the next time it is written. The upgrade steps are in the [README](../README.md#upgrading-from-v01x).

**Resume.** `tack resume` first searches for a run that took this run over or started after it (Requirement 18), and composes the run's plan again (Requirement 21), before it asks the operator; it searches again after. The runner then walks `spec.steps` in order: it skips `Succeeded` steps, re-checks the reachability of each site and its cluster (Requirement 19), reads every site but `to` before each Failover step after the demotion that is not `Succeeded` ([RFC#0007] Requirement 9), reads each deferrable site before its first step that is not `Succeeded` ([RFC#0007] Requirement 6), and runs the rest, `Deferred` steps whose site answers again among them. A site's `VerifyGit` that succeeded in an earlier process runs again before the site's first Release step ([RFC#0005] Requirement 8).

# Security Considerations

- Writing a ledger is privileged. A ledger names the steps, the kube contexts and the Git URL that `tack resume` uses with the operator's credentials: anyone who may create `sitefailovers`, or update `sitefailovers/status`, can plant a run or change one. `spec` is immutable, so a change is a create, or a write of `status`. Requirement 21 binds the steps to the ledger's Workload snapshot and request, and [RFC#0006] Requirement 15 binds the Git change's files to it. The snapshot itself, and `status`, are as written: the operator restricts who may write them ([docs/operations.md](../docs/operations.md#who-may-write-ledgers)). How such a ledger would be planted is inferred, not observed.
- The ledger holds no secret. A CloudNativePG demotion token encodes checkpoint location, timeline, system identifier and operator version; it grants nothing. `tack status` prints captured values by name only.
- Writing a ledger needs `create`, `get`, `list` on `sitefailovers` and `update` on `sitefailovers/status` in the ledger namespace at each site.
- `tack prune` needs `delete` on `sitefailovers` in the ledger namespace at each site. Whoever may delete ledgers can delete any run's record outside Tack, a run that is not finished among them: grant it to the operators only.
- Identifying a site's cluster needs `get` on the namespace `kube-system`, a cluster-scoped object, at each site.
- The history's user needs `create` on `selfsubjectreviews` (`authentication.k8s.io`) at the ledger's site, which Kubernetes grants every authenticated user through the ClusterRole `system:basic-user`. Events need `create` on `events` in the ledger namespace; without it, the run goes on without Events (Requirement 23).
- The history names the user of each process: whoever may read a ledger sees who ran it.

# Limitations

| Limitation | Trigger to revisit |
|---|---|
| Requirement 21 binds a run's steps to its Workload snapshot, not the snapshot to the operator: a ledger planted with other contexts, Clusters or Git URL composes its own plan, and passes. The confirmation prints each site's context, API server and recorded cluster, and the Git URL ([RFC#0009] Requirement 4). `status` is not checked: captured values, Git revisions, step states, holds and follow-ups are as written. | A controller whose service account alone may write ledgers. |
| The ledger lives at one site. If `to` is lost mid-run, its ledger is out of reach; a new run toward a reachable site takes over the holds with `--take-over`. | A controller, or ledger copies at every reachable site. |
| A newer run whose ledger is at a site that does not answer is not found, and `tack resume` runs the older run, with a progress line that names the site ([RFC#0009] Requirement 16). The check before each patch ([RFC#0005] Requirement 11) still stops it at an object another run holds. | A controller, or ledger copies at every reachable site. |
| Two sites' API servers whose clocks differ by more than 10 s can still order two runs wrong, and a run of another site created less than 10 s before this one, such as by another operator, refuses its resume. The way on is a new run with `--take-over`. | A clock difference observed between sites, or a refusal of a run that should resume. |
| A site lost at plan time is recorded by the first process that reads it, which trusts that process's kubeconfig. | Fingerprints given in the Workload file. |
| A CRD older than v1.3.0 drops `spec.takeOvers`: a run with `--take-over` given more than once is refused at its creation (Requirement 7). A CLI older than v1.3.0 reads only `spec.takeOver`: it does not take over the holds of the other runs, and stops on them with `HeldByAnotherRun`. A CRD older than v1.3.0 drops `status.abandoned`, `status.git.changedRevision`, `status.history`, `status.historyDropped` and `status.writtenBy`: a run there keeps no history. There, a status write that lands and loses its answer is not recognised by its repeat, whose read shows the status without those fields (Requirement 5): the run stops with "another tack process may be running this run", and resumes (inferred from the code). A run abandoned by the search after its create then reads as one that never recorded its start: a new run needs `--take-over` for it, and `tack resume` refuses it. `tack abandon` fails and says so. `--accept-git-head` is taken as given. A CLI older than v1.3.0 ignores `status.abandoned`: its `tack resume` resumes a run that `tack abandon` marked, and drops the mark with its first write; its `tack run` refuses a new run while the marked run is not `Succeeded`, unless `--take-over` names it. A CLI older than v1.3.0 drops both fields, and `status.history`, `status.historyDropped` and `status.writtenBy`, when it writes the ledger: it neither records its version nor refuses a ledger that a newer tack wrote (Requirement 24). | Every site's CRD, and every operator's CLI, on v1.3.0 or later. |
| A CLI older than v1.2.0 neither records nor honours a take-over, nor checks a site's cluster, and its status writes drop `status.supersededBy` and `status.fingerprints`. | Every operator on v1.2.0 or later. |
| A value lost from `status.captured` after its `Capture` step succeeded is not captured again: the operator restores it ([docs/runbooks/stop-reasons.md](../docs/runbooks/stop-reasons.md#tokenmissing)). Only an edit of the ledger is known to lose one, and a token read again later may come from another demotion. | A value lost without an edit of the ledger. |
| Events are written one by one, after each ledger write, and only an Event that fails turns them off. An API server that answers each slowly, up to 5 s, slows each step by that, the Failover steps among them. | An Event observed to take more than a second. |
| A build whose version names no release, such as `dev` from `go install`, is not compared: it writes over a ledger of any release, and any release writes over its ledger (Requirement 24). | Such a build run against production. |
| Events last as long as the API server keeps them, 1 h by default. The history keeps each change of the run's state, but not each step's start and end: a step's status holds its last attempt. | An incident whose timeline needs the steps of an earlier attempt. |
| A process ended by a second signal, or killed, records no entry for its end. The next entry is the next process's `Running`. | A controller. |
| The history counts the entries it dropped, not what they held. | A run stopped and resumed more than about 50 times. |
| A `Running` ledger does not tell a live process from a dead one. The concurrency check catches two writers, not a stale `Running`. | A lease held by the running process. |
| Tack deletes a ledger only when the operator runs `tack prune` (Requirement 27). Until then, each search for runs reads every ledger of the workload at each site that answers, and `tack status -f` lists them all: their cost grows with the number of runs. The sizes measured are in [docs/operations.md](../docs/operations.md#old-ledgers). | A search observed to take seconds while the operator prunes: a retention that runs by itself, in a controller. |
| `tack prune` keeps a run with a follow-up `Rebuild` after the member was rebuilt: it reads no object of the workload. The operator deletes that ledger by hand ([docs/operations.md](../docs/operations.md#old-ledgers)). | A workload whose kept `Rebuild` runs slow its searches. |
| `v1alpha1` stays served. Ledgers not written since the upgrade stay stored as `v1alpha1`. | A release that stops serving `v1alpha1`. It must first rewrite every ledger as `v1`, then remove `v1alpha1` from the CRD's `status.storedVersions`. |

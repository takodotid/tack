<h1 style="text-align: center;">[RFC#0002] The Engine and the Driver Interface</h1>

# Abstract

Tack is a generic engine plus one driver per workload type. A driver turns the workload's state into steps as data; the engine adds the hold, the Git change and the checks, and runs the steps. This RFC sets the driver interface, the step types and the plan order.

# Overview

Parts and scope: [RFC#0001]. A driver owns reading the workload at each site, the Failover steps in order, the fields that make Git equal live, and the workload's own word that the switch is complete. The engine owns the rest of a plan.

# Motivation

| Choice | Reason |
|---|---|
| Steps are data | A dry run prints what a run does, and a run resumes step by step from the ledger. |
| The engine knows no workload | A second workload type needs a driver, not a second engine. |
| Built-in drivers only | A driver acts on production; it is reviewed like any code. |
| Steps, objects and Git changes come from the Workload and the request alone | A resume rebuilds the plan from the ledger, which holds the Workload and the request, not the topology, and refuses steps planted by whoever can write it ([RFC#0003] Requirement 21). |
| An empty captured value counts as missing | An empty value in place of a token let a resume promote without the demotion's checkpoint. |

# Requirements

1. The engine packages (`internal/engine`, `internal/flux`, `internal/gitops`, `internal/strait`, `internal/cli`) MUST NOT import a driver package, except the binary's wiring and tests. Checked by `TestEngineImportsNoDriver`.
2. A driver MUST implement:

| Function | Returns | MUST |
|---|---|---|
| `Validate(workload)` | an error | reject a Workload it cannot run |
| `Discover(workload, clients)` | per site: reachable, role, declared primary, health, a summary, the objects a run may change, and two more fields (below the table) | report a site whose check got no answer ([RFC#0007] Requirement 5) in its state, not as an error; return any other error; change nothing |
| `Plan(workload, topology, request)` | the Failover steps, and follow-ups for the operator | refuse a request the topology does not allow; else return what `Steps` returns, then the follow-ups that depend on what it read |
| `Steps(workload, request)` | the Failover steps and follow-ups, from the Workload and the request alone; with the request's `Legacy`, the steps v1.6.0 planned | change and read nothing ([RFC#0003] Requirement 21) |
| `Objects(workload, site)` | the objects a run may change at the site, from the Workload alone | equal the objects `Discover` reports for the site |
| `GitChange(workload, topology, request)` | fields, per site and object, with their value after the run | cover every field the Failover steps change that Git sets; depend on the Workload and the request alone |
| `Verify(workload, request, site)` | Wait steps | hold only once the switch is complete at that site |
| `Writes(workload, request)`, optional | the ID of the step whose start stops writes (none when the mode cannot tell), and of the step after whose end the new primary takes writes ([RFC#0003] Requirement 29) | name steps of `Steps` |
| `Progress(workload, clients, step, captured)`, optional | for a `Wait` with `stall`: how far the workload got, and whether it is still behind what the wait needs | only read; return "not behind" when unsure |
| `Demotion(request, site)` | the ID of the Failover step after which the site no longer runs as primary; none for `to` | name the same step as every earlier release, so their ledgers read the same way ([RFC#0007] Requirement 9) |

- `Discover` also returns the member's creation time ([RFC#0003] Requirement 14) and, if the driver reads it, how far the site's data reaches ([RFC#0004] Requirement 13).
- A request the topology does not allow is, for example, a planned switchover from a site that is not a healthy primary. A follow-up that depends on what `Plan` read is, for example, a `Rebuild` for a site ahead of the new primary ([RFC#0004] Requirement 14).
- `Demotion` returns, for `from`, its demotion or fence; for any other site but `to`, the step that declares the new primary there.

3. A step MUST be one of the types below, and MUST be safe to run again after it started and was not recorded as done.

| Type | Emitted by | Action | Why it is safe to repeat |
|---|---|---|---|
| `Hold` | engine | annotate one object ([RFC#0005]) | adding an annotation this run set is a no-op |
| `Reconcile` | engine | request a Flux reconcile and wait until handled | a new request is handled like the first |
| `Patch` | driver | JSON merge patch of one live object, field manager `tack` | a merge patch with the same values changes nothing |
| `Wait` | driver | poll conditions on one object until all hold or a timeout | it only reads |
| `Capture` | driver | copy one field of a live object into the ledger | it re-reads the field |
| `Create` | driver | create one object, labelled `failover.tako.id/run: <run>`; `$(run)` in its manifest and name is the run's name | an object of that name with this run's label is adopted; one without it stops the run |
| `Record` | driver | read the workload through the driver's API and record it in the ledger ([RFC#0004] Requirement 15); asks again until its timeout while the driver waits | it only reads |
| `Git` | engine | one commit ([RFC#0006]) | a commit this run already pushed is adopted |
| `VerifyGit` | engine | check that Git equals live ([RFC#0005]) | it only reads |
| `Release` | engine | remove the hold | removing what is gone is a no-op |
| `VerifyNoop` | engine | check that Flux changed nothing ([RFC#0005]) | it only reads |
| `Routing` | engine | wait for Strait's route ([RFC#0008]) | it only reads |

4. A `Wait` MAY set `stall`; it then MUST fail once the driver's `Progress` has reported the workload behind, with the same progress, for that long. A `Wait` condition MUST be a JSONPath on the object and one operator: `Equals`, `NotEquals`, `NotEmpty`, `Empty`, or `Contains` (one of the space-separated results equals the value). A missing field reads as empty.
5. When the step runs, `$(name)` in a `Patch`, a `Wait` value, a `Reconcile` revision or a Git value MUST be replaced by the ledger's captured value `name`, and `$(git.commit)` by the run's commit. A missing or empty value MUST stop the run with reason `TokenMissing`, before the step changes anything; so MUST a `Capture` that reads an empty field. Checked by unit tests.
6. The engine MUST compose the plan in this order; the same inputs MUST give the same plan. Checked by golden tests of the dry run.

| Phase | Steps, in order |
|---|---|
| Hold | per site, in Workload order: `Hold` of each object the run may change, then one `Reconcile` |
| Failover | the driver's steps, as returned |
| PromoteToGitOps | one `Git`, then per site a `Reconcile` until Flux applied the run's commit, or the branch head that contains it ([RFC#0005] Requirement 12) |
| Release | per site: `VerifyGit`, `Release` of each object, `Reconcile` at the run's commit or the branch head that contains it, `VerifyNoop`; then a `Routing` per Strait service when configured |

7. A step on a site MUST be deferrable unless the site is `to`, or the mode is `Planned` and the site is `from`. A deferrable step on an unreachable site is marked `Deferred`, the run goes on, and the step runs when the site answers again ([RFC#0007]). A non-deferrable step on an unreachable site MUST stop the run.
8. Step IDs MUST be unique within a plan.

# Design

Driver interface: `internal/driver/driver.go`. A driver registers by name; the Workload's `spec.driver` picks one. `Discover` returns `Facts`, a string map the driver uses for its own checks in `Plan`.

Topology: each site's state has a role, as the workload reports it:

| Role | Meaning |
|---|---|
| `Primary` | the site's member accepts writes |
| `Replica` | the site's member follows another |
| `Unknown` | the site cannot be read, or is neither |

Plan inputs: `Compose` reads nothing. It takes the request, the topology, the Flux owner of each object, the driver's steps and follow-ups, and the resolved Git changes. `MakePlan`, which changes nothing, reads clusters and Git before it. `tack resume` composes the plan again from the ledger, taking the inputs the plan read from the ledger's own steps ([RFC#0003] Requirement 21).

Field manager: patches use `tack` ([RFC#0005]).

<h1 style="text-align: center;">[RFC#0004] CloudNativePG Support</h1>

# Abstract

The `cnpg` driver switches the primary of a CloudNativePG deployment in the distributed topology. In that topology, each site has one `Cluster`, `.spec.replica.primary` names the primary, and a demotion token moves the primary without losing writes. The driver also moves the read-write `Pooler`, which runs only at the primary's site.

# Overview

| Mode | What happens |
|---|---|
| `Planned` | The old primary demotes and publishes a demotion token. The new site replays up to that token, then promotes with it. No write is lost. |
| `SiteLoss` | The old site is lost. The new site promotes without a token. The old primary may hold writes the new one lacks; rebuild it before it follows again. |

# Motivation

CloudNativePG v1.30.1 facts:

| Fact | Consequence |
|---|---|
| The webhook rejects `promotionToken` while the Cluster is a replica, and a token with `minApplyDelay`. | Token and `primary` go in one patch at the new site. Plan refuses a planned run when the new site sets `minApplyDelay`. |
| `primary` set to self without a token promotes at once, unchecked. | A planned switchover never sets `primary` first. |
| `enabled` alone is the legacy replica switch; with `primary` it is rejected. | The driver requires `primary` and refuses `enabled`. |
| `demotionToken` is set once per demotion, before `switchReplicaClusterStatus.inProgress` goes false, and cleared when the Cluster is not a replica. | Demotion is complete when the token is set and `inProgress` is not `true`. |
| `lastPromotionToken` is set after `pg_ctl promote` succeeds, and cleared when the spec token is removed. | Promotion is complete when it equals the token. |
| A used token that returns after removal, or a Cluster recreated with it, fails the timeline check, sets phase `Cluster is unrecoverable and needs manual intervention` and holds all reconciliation. | Git never holds a token. Tack removes the used token live once promotion is confirmed. |
| An old primary that becomes a replica is never rewound. | After a site loss it needs a rebuild. |
| `Pooler.status.instances` is the Deployment's replicas, not ready pods; its phase is `active` even at 0. | Tack waits on `readyReplicas`. |
| In a replica Cluster, the `-rw` Service points at a read-only standby. | The read-write Pooler is scaled to 0 away from the primary. |
| The `Cluster` status holds no WAL position or lag. | Tack reads the position from the instance manager. |
| The instance manager serves `/pg/status` on port 8000 through the API server's pod proxy, without authentication, over https when the `postgres` container runs with `--status-port-tls`. | One GET per site, with `get` on `pods/proxy`; the Pod is read first, for the scheme. |
| `/pg/status` holds `receivedLsn`, `replayLsn`, `timeLineID`, `systemID`, `isPrimary`, `isWalReceiverActive`, `replayPaused`, `currentWAL` and `lastArchivedWAL`; no replay time. | The replay time comes from the metrics. |
| A replica's `receivedLsn` is never behind its `replayLsn`. | A site's position is the furthest of the two. |
| `timeLineID` comes from the last checkpoint, which lags. A WAL file is named after its timeline. | Tack reads the new timeline from `currentWAL`, and never compares sites by `timeLineID`. |
| A promotion with a token waits until replay reaches the token's `latestCheckpointREDOLocation`; the token is base64 of JSON. | Requirement 18 compares replay with it. |
| A primary's shutdown in a switchover may last up to `spec.switchoverDelay`, 3600 s by default. | [docs/operations.md](../docs/operations.md#how-long-writes-stay-down) sets it against `timeouts.demotion`. |
| A replica Cluster runs with `archive_mode = always`, so each site writes to its archive before any promotion. | Each site's destination must be its own from day one (Requirement 16). |
| A Cluster refuses a non-empty archive (`Expected empty archive`); a unique `serverName` avoids it. | Requirement 16 reads the `serverName` along with the path. |
| A replica Cluster's `ContinuousArchiving` may be `True` from before the promotion. | Requirement 17 waits for a file of the new timeline too. |
| A `Backup` with `method: volumeSnapshot` fails without `spec.backup.volumeSnapshot` in its Cluster and VolumeSnapshot support in the site. | The snapshot is opt-in, per site. |
| A cold snapshot (`online: false`) fences the instance through `cnpg.io/fencedInstances` and removes the annotation after. A Cluster can start from VolumeSnapshots; `Backup.status.snapshotBackupStatus.elements` names them. | The snapshot is cold, so Git and the check before release see nothing in the Cluster. Tack records the names. |
| The instance manager serves metrics on port 9187, path `/metrics`, without authentication, over TLS when the `postgres` container runs with `--metrics-port-tls`. | One more GET per replica, with the same permissions. |
| `cnpg_pg_replication_lag` is 0 for a primary or an instance that replayed all it received, else the seconds since the last replayed commit, by the replica's clock. | A lag of 0 says nothing of how old the data is. |
| The lag refreshes at most every `spec.monitoring.metricsQueriesTTL` (30 s). | A read can be up to 30 s old. |
| `spec.monitoring.customQueriesConfigMap` adds queries, exported as `cnpg_<query>_<column>` (NULL as NaN, a timestamp as seconds since 1970). | Tack's opt-in replay-time query (Requirement 13) rides on the same GET. |
| PostgreSQL 18.6 stamps a commit before it inserts the commit record into the WAL. Under concurrent writes, commit times are not in WAL order. | A transaction stamped just before the replay time may come later in the WAL and be lost. |
| A replica takes its replay time from each commit record in WAL order. | The replay time is the last replayed commit's, not a line before which every commit is replayed. |

Observed on kind with CloudNativePG v1.30.1 and Flux v2.10.0:

| Observation | Consequence |
|---|---|
| In a demotion, `Ready=True` and phase `Cluster in healthy state` return about a second before `demotionToken` is set. | Health is not a demotion signal; the token and `inProgress` are. |
| `lastPromotionToken` is set up to 2 s before PostgreSQL leaves recovery. | The promotion wait also needs an instance reporting `isPrimary: true` and a healthy phase. |
| A stale token makes the webhook reject Flux's dry-run when Git demotes that Cluster, which blocks the whole Kustomization. | Every patch that declares another primary also sets `promotionToken: null`. |
| An old primary that returns after a site loss keeps taking writes until Flux or Tack fences it, and both sites report healthy. Only the timeline and `isPrimary` differ. | The fence check reads `isPrimary`; routing away from it is Strait's job. |
| A failed-over old primary loops on "requested starting point ... is not in this server's history" while its status stays `Cluster in healthy state`. | Status does not tell a diverged replica from a healthy one. |
| A healthy replica reports its old timeline until its next restartpoint. | Nor does the timeline. Tack relies on the `Rebuild` follow-up. |
| A rebuild needs `bootstrap` changed in Git first, and deleting the Cluster removes its PVC. | The runbook changes Git before deleting. |

| Choice | Reason |
|---|---|
| A Cluster without `spec.replica`, or without `primary`, that reports `isPrimary` is `Primary` (Requirement 3) | It is a live primary, so `Primary` is the safer answer: a site-loss plan refuses it (Requirement 5), and the read before its steps stops the run ([RFC#0007] Requirement 6). |
| The plan checks each site's `spec.externalClusters` | CloudNativePG refuses a site that declares an unknown cluster primary (`External cluster pg-c not found`), in a step after the promotion. |
| Positions through the API server | SQL needs a database credential and a network path to each database, or `exec` ([RFC#0001] Requirement 2 forbids it). The status endpoint needs only `get` on pods and `pods/proxy`. |
| A position that cannot be read is a warning | A site loss must not stop because the operator lacks the new permission, or because a pod does not answer. |
| The replay lag from the instance's metrics | It needs the same `pods/proxy` permission as the position, and no database credential. It replaces nothing: the position still decides which replica is ahead. |
| A site's position is the furthest of what it received and replayed | Before a replica ends recovery, its promotion replays the WAL it received, so received WAL is not lost. |
| The replay time from an opt-in query, read only when present | It gives the RPO of a site loss as a time, with no guarantee that every earlier commit is in `to`. |
| The replay-time query is in Git | CloudNativePG's default queries do not export the time. A Cluster without the query plans as before. |
| A `SiteLoss` run refuses a target behind another replica, unless `--accept-behind` | A replica ahead of `to` cannot follow it. The override is in the ledger, so the read before the first Failover step ([RFC#0009] Requirement 13) accepts it in every process. |
| The fork point, the old primary's snapshot and its archive are recorded | Without a fork point, the rebuild drops the writes the old primary took after it. |
| The old primary's writes are handed over, never merged | Two histories can change the same row, so the writes go to their owners. |
| A record that cannot be read does not stop the run | A position or timeline that cannot be read must not block a promotion. The runbook says how to find the fork point without it. |
| Archiving that does not work after the promotion warns and records `CheckArchiving`, and does not stop the run | Writes are back by then. A stop would keep Flux held and Git behind live until the archive is fixed. |
| A shared archive refuses a planned run and warns in a site loss | Same reason as Requirement 12: the fix is in Git, and a site loss may have taken Git. |
| A `SiteLoss` plan warns of a missing `externalClusters` entry, and does not refuse | A refusal there has no override and says to fix it through Git, which may have gone with the lost site. |
| The step for a missing `externalClusters` entry fails closed | CloudNativePG refuses it and changes nothing. |
| The snapshot is opt-in, and a failed snapshot stops the run | A Backup fails on a site without VolumeSnapshot support, such as the e2e's kind clusters. An operator who asked for it is told before anyone rebuilds. |

# Requirements

1. Each site's member MUST be one `Cluster` whose `.spec.replica` sets `primary`, and MUST NOT set `enabled`. Each site's `Cluster` MUST have its own name.
2. The driver MUST read, per site: `spec.replica.{self,primary,minApplyDelay,enabled}`, the names of `spec.externalClusters`, `status.phase`, `status.currentPrimary`, `status.switchReplicaClusterStatus.inProgress`, `status.instancesReportedState.*.isPrimary`, the configured `Pooler`, and the position of Requirement 13.
3. Roles, by the first rule that matches. Checked by unit tests.

| Role | Rule |
|---|---|
| `Unknown` | `enabled` is set |
| `Replica` | `primary` is set and differs from `self` (or the name) |
| `Primary` | an instance reports `isPrimary: true`, and `primary` equals `self` (or the name), or `spec.replica` or its `primary` is absent |
| `Unknown` | otherwise |

A site is healthy when its phase is `Cluster in healthy state` and no demotion is in progress.

4. A `Planned` run MUST be refused unless: `from` is a healthy `Primary`; `to` is a healthy `Replica`; every reachable site declares `from`; `to` does not set `minApplyDelay`; no demotion is in progress; and `to` was not left to rebuild by an earlier run ([RFC#0003] Requirement 14). The driver reports `metadata.creationTimestamp` as the member's creation time.
5. A `SiteLoss` run MUST be refused if `from` answers as `Primary`, and unless `to` is a healthy `Replica`.
6. A `Planned` run's Failover steps MUST be, in order:

| # | Step | Site | Content |
|---|---|---|---|
| 1 | Patch, Wait | from | Pooler `instances: 0`; Deployment `replicas` empty |
| 2 | Patch | from | `replica.primary: <to Cluster>`, `replica.promotionToken: null` |
| 3 | Wait | from | `status.demotionToken` not empty, `status.switchReplicaClusterStatus.inProgress` not `true` |
| 4 | Capture | from | `status.demotionToken` as `demotionToken` |
| 5 | Patch | to | `replica.primary: <to Cluster>`, `replica.promotionToken: $(demotionToken)`, in one patch, once the read before the promotion lets it, and from's `status.demotionToken` still equals `$(demotionToken)` when from answers ([RFC#0007] Requirement 9) |
| 6 | Wait | to | `status.lastPromotionToken` equals `$(demotionToken)`, an instance `isPrimary`, phase healthy |
| 7 | Patch | to | `replica.promotionToken: null` |
| 8 | Patch | each other site | `replica.primary: <to Cluster>`, `replica.promotionToken: null` |
| 9 | Patch, Wait | to | Pooler `instances: <configured>`; Deployment `readyReplicas` equals it |
| 10 | Patch, Wait | each site but `from` and `to` | Pooler `instances: 0`; Deployment `replicas` empty |
| 11 | Wait | to | Verify (Requirement 9) |
| 12 | Record | to | `verify-archiving-<to>` (Requirement 17) |

7. A `SiteLoss` run's Failover steps MUST be, in order:

| # | Step | Site | Content |
|---|---|---|---|
| 1 | Patch | from, deferrable | fence: `replica.primary: <to Cluster>`, `replica.promotionToken: null` |
| 2 | Patch, Wait | from, deferrable | Pooler `instances: 0`; Deployment `replicas` empty |
| 2a | Record | to | `record-position-<to>`: its position (Requirement 15) |
| 3 | Patch | to | `replica.primary: <to Cluster>`, `replica.promotionToken: null`, once the read before the promotion lets it ([RFC#0007] Requirement 9) |
| 4 | Wait | to | an instance `isPrimary`, phase healthy |
| 4a | Record | to | `record-fork-<to>`: its new timeline (Requirement 15) |
| 5 | Patch | each other site | as Planned step 8 |
| 6 | Patch, Wait | to | as Planned step 9 |
| 6a | Create, Record | from, deferrable | with `snapshot` set for `from`: `snapshot-<from>`, then `record-snapshot-<from>`; otherwise `record-archive-<from>` (Requirement 15) |
| 7 | Wait | to | Verify (Requirement 9) |
| 8 | Record | to | `verify-archiving-<to>` (Requirement 17) |

The run MUST record the follow-up `Rebuild` for `from`.

In both modes, `Demotion` ([RFC#0002] Requirement 2) MUST name, by the IDs of every earlier release, `demote-<from>` (Planned step 2) or `fence-<from>` (SiteLoss step 1) for `from`, and `declare-<site>` (Planned step 8, SiteLoss step 5) for each other site but `to`. Checked by unit tests.

8. The Git change MUST set, for every site: the `Cluster`'s `spec.replica.primary` to the `to` Cluster's name; the Pooler's `spec.instances` to the configured value at `to` and `0` elsewhere; and MUST remove the `Cluster`'s `spec.replica.promotionToken`. The removal is optional ([RFC#0006]); without it, the check before release stops the run if Git sets a token.
9. Verify at `to` MUST hold when the `Cluster` declares itself primary, an instance reports `isPrimary: true`, and the phase is healthy. At any other site it MUST hold when the `Cluster` declares the `to` Cluster primary.
10. Every `Wait` MUST time out: demotion waits after `timeouts.demotion`, promotion and Pooler waits after `timeouts.promotion` (both default 10m), the wait for a snapshot after `timeouts.snapshot` (default 30m).
11. Tack MUST NOT rebuild a member. The rebuild is the operator's: [docs/runbooks/rebuild-old-primary.md](../docs/runbooks/rebuild-old-primary.md).
12. A site that answers, other than `to`, and whose `Cluster` lacks `to`'s `Cluster` in `spec.externalClusters` cannot declare it primary. A `Planned` run MUST be refused for it, in its plan and before any step. A `SiteLoss` plan MUST NOT be refused: it MUST warn, naming the step where the run stops with `StepFailed` (`fence-<from>` before the promotion, `declare-<site>` after it). Each message MUST name the site, its `Cluster` and `to`'s. Checked by unit tests.
13. A plan MUST read, at each site that answers:
    - the WAL position of the `Cluster`'s current primary pod (`status.currentPrimary`): a GET of the Pod, then a GET of `/pg/status` (port 8000) through the API server's `pods/proxy`, with the scheme the `postgres` container serves;
    - for a replica, its replay lag: a GET of the same pod's `/metrics` (port 9187), with the same scheme, and the value of `cnpg_pg_replication_lag`.

    It MUST read nothing else through `pods/proxy`. A read that fails MUST NOT refuse the plan. The plan MUST print it and warn, naming the permissions. A replay lag that cannot be read MUST be printed as such, and noted without a warning for `to`.

    The plan MUST print, per site:
    - a replica: the received and replayed positions, the timeline, whether its WAL receiver runs, whether replay is paused, and its replay lag, a lag of 0 as `replayed all it received`, never as a time;
    - a replica, when the metrics hold `cnpg_tack_replay_timestamp_seconds` from the opt-in query `deploy/cnpg/replay-time.yaml`: instead of the lag, the commit time of the last transaction it replayed, in RFC 3339 to the millisecond, and its age by Tack's clock;
    - a primary: its write position;
    - each replica against the others of the same database (`systemID`): `most caught up`, or `behind <site> by <size>`.

    A site's position is the furthest of its received and replayed positions.

    A `SiteLoss` plan MUST note that replication between sites is asynchronous and that the writes the old primary took after `to`'s position are lost. With the replay-time query, it MUST also note `to`'s last replayed commit time, by the old primary's clock, and that the writes the old primary committed after it are lost, and so may be a few committed just before it. It MUST NOT state that every transaction committed up to that time is in `to`. When the query returns NULL, it MUST note that it cannot say when `to`'s last replayed commit was. Without the metric, the output MUST be what it is without the query. It MUST warn when `to` sets `minApplyDelay`, when `to`'s replay is paused, and when `to`'s replay lag is above 0, with the size of the WAL it received and has not replayed, if any. Checked by unit tests.
14. A `SiteLoss` plan MUST refuse, before any step, a site that answers, is neither `from` nor `to`, and is a `Replica` of the same database with a position past `to`'s, unless the operator passes `--accept-behind`. The refusal MUST name both sites, both positions, the most caught-up site and the flag. With the flag, the ledger MUST record it in `spec.acceptBehind`, the plan MUST warn of each such site, and the run MUST record the follow-up `Rebuild` for each. Unreadable positions cause no refusal. A `Planned` run MUST refuse the flag. Checked by unit tests.
15. A `SiteLoss` run MUST find, keep and hand over the old primary's writes, and MUST NOT merge them:

| Step | Reads, then records | Where | When it cannot read |
|---|---|---|---|
| `record-position-<to>`, right before the promotion | `to`'s position (Requirement 13) and timeline; with the replay-time query, the last replayed commit time | `status.fork.position`, `.parentTimeline`, `.lastCommit` | records why in `status.fork.message`; the run goes on |
| `record-fork-<to>`, right after the promotion | the timeline in the name of the WAL file that `to`'s current primary writes (`currentWAL`), and the time | `status.fork.timeline`, `.at` | as above |
| `snapshot-<from>`, when `spec.sites[].cnpg.snapshot` is set for `from` | creates a `Backup` named `<run>-<from>`, labelled `failover.tako.id/run: <run>`, with `method: volumeSnapshot`, `target: primary`, `online: false`; adopts only a Backup of that name with this run's label | the Backup | stops the run |
| `record-snapshot-<from>` | waits for the Backup's phase `completed`; records it, its VolumeSnapshots and where `from`'s Cluster archives WAL | the follow-up `Rebuild` of `from`: `snapshot`, `archive` | a failed Backup stops the run, with what to fix |
| `record-archive-<from>`, without `snapshot` | where `from`'s Cluster archives WAL: `spec.backup.barmanObjectStore` or the barman-cloud plugin | the follow-up `Rebuild` of `from`: `archive` | stops the run |

`record-position-<to>` records:

- The position and timeline where the new history leaves the old one, or just after.
- With the replay-time query, the commit time of the last transaction `to` replayed, from the metrics the plan reads, by the old primary's clock, to the microsecond.
- Metrics that cannot be read, or hold no replay time, leave `.lastCommit` out with no message; a NULL time goes in the message.

A planned run records none of them: it forks no history. The rebuild runbook's first check MUST be that the run recorded the snapshot, and it MUST stop without one. Checked by unit tests.

16. A plan MUST read, at each site that answers, where its `Cluster` archives WAL: the `destinationPath` of `spec.backup.barmanObjectStore`, or of the `ObjectStore` (`barmancloud.cnpg.io/v1`) that its barman-cloud plugin names, with the server name (`serverName` or the `Cluster`'s name). Sites with the same path and server name share a destination. A `Planned` run MUST be refused for it, in its plan and before any step. A `SiteLoss` plan MUST NOT be refused: it MUST warn. Each message MUST name both sites, both `Cluster`s and the destination. A destination that cannot be read MUST warn and refuses nothing. Checked by unit tests.
17. In both modes, the last Failover step, `verify-archiving-<to>`, MUST wait, up to `timeouts.archiving` (default 5m), until `to`'s `Cluster` reports `ContinuousArchiving` `True` and its current primary's last archived WAL file (`lastArchivedWAL` of `/pg/status`) is of the timeline it writes. It MUST pass at once when the `Cluster` names no WAL archive. On timeout, the step MUST end with a warning, the run MUST record the follow-up `CheckArchiving` for `to`, and go on. A plan MUST warn when `to` reports `ContinuousArchiving` `False`. Checked by unit tests.
18. A `Planned` run's wait for the promotion (step 6) MUST set `stall` to 2 minutes. The wait then stops early, with `StepFailed`, when `to`'s replay position (`/pg/status`) stands still for that long short of the demotion token's checkpoint (`latestCheckpointREDOLocation`). A position or token that cannot be read MUST NOT stop it. The promotion patch stays: a resume waits again. Checked by unit tests.

# Design

**Workload.**

```yaml
spec:
  driver: cnpg
  sites:
  - name: a
    kubeContext: site-a
    cnpg:
      cluster: {namespace: db, name: pg-a}
      pooler: {namespace: db, name: pg-a-pooler-rw, instances: 2}
```

**Old Pooler first.** A Pooler at 0 refuses connections at once. A Pooler whose Cluster demotes gives connect timeouts for 7 to 16 s, then read-only errors.

**Fence first in a site loss.** A `from` that answers is declared a replica before `to` promotes, so it cannot return as a second primary. A `from` that does not answer is fenced when it returns ([RFC#0007]).

**Snapshot order.** The steps at `from` follow its fence, so the snapshot is of a member that takes no writes.

# Security Considerations

| Need | Grant ([Permissions](../docs/permissions.md)) | Note |
|---|---|---|
| Requirement 13 | `get` on `pods` and `pods/proxy` in each member's namespace | Pod names are generated, so the grant cannot name them. Grant `pods/proxy` only in the members' namespaces. |
| Requirement 15's snapshot | `create` and `get` on `backups` (`postgresql.cnpg.io`) in each member's namespace | Backup names hold the run's name, so the grant cannot name them. |
| Requirement 16 | `get` on the `objectstores` that the Clusters name | Optional: without it, the plan warns that it could not check. |

`get` on `pods/proxy` lets its holder GET any port of any Pod in the namespace, including unauthenticated endpoints. `/pg/status` holds positions, the system identifier, configuration hashes and the pod's spec; `/metrics` holds database names and settings. Tack prints only the positions, the timeline and the stream's state, and reads only `cnpg_pg_replication_lag` and `cnpg_tack_replay_timestamp_seconds` from the metrics.

# Limitations

| Limitation | Trigger to revisit |
|---|---|
| One read-write Pooler per site. Read-only Poolers are not moved. | A workload with several Poolers that follow the primary. |
| With three or more sites, the driver does not check that each replica's `source` chain reaches the new primary. | The first three-site deployment. |
| A shutdown of the old primary that outlasts `switchoverDelay` makes CloudNativePG shut down at once and publish no token; the demotion wait times out. | An observed timeout. |
| A shutdown that outlasts `timeouts.demotion` stops the run while CloudNativePG keeps waiting. A resume waits again ([docs/operations.md](../docs/operations.md#how-long-writes-stay-down)). | An observed timeout. |
| The rebuild of an old primary is manual, and so is the hand-over of its writes ([docs/runbooks/recover-old-primary-writes.md](../docs/runbooks/recover-old-primary-writes.md)). | A safe, declarative rebuild in CloudNativePG. |
| The fork position is read right before the promotion; a replica that promotes after replaying more WAL forks just after it, so the runbook lists a little more, never less. | A record of the exact switch point from the instance status. |
| A replica of a third site that was ahead of `to` gets a `Rebuild`, but no snapshot: only `from` does. | A run observed with a third site ahead. |
| Without the opt-in replay-time query ([docs/workload.md](../docs/workload.md#replay-time)), a replica that replayed all it received shows a lag of 0 whatever the age of its data (Requirement 13). | The time of the last replayed transaction in the instance status or CloudNativePG's default queries. |
| With the query, the time is no exact RPO line: a few commits stamped just before it may be lost. | A WAL-ordered commit position from PostgreSQL. |
| Lag and time can be up to `metricsQueriesTTL` old, and the time is the old primary's clock (Requirement 13). | A WAL-ordered commit position from PostgreSQL. |
| Positions are read in the plan and after the confirmation. A replica that restores WAL from an archive can move past another between the read and the promotion. | A replica observed to move after the read. |
| An old primary that is alive but cut off from the operator keeps taking writes until fenced ([RFC#0007] Limitations). The new primary lacks them, and the rebuild drops them. | A fence that does not need the site's API. |

Without the query, a replica whose source stopped long ago reads as most caught up when no other site is ahead.

<h1 style="text-align: center;">[RFC#0006] The Git Change</h1>

# Abstract

After the switch, Tack writes one commit to the GitOps repository so that Git equals live. The operator maps each field to a file and path, or lets Tack find the object's manifest. The commit lands only on top of the revision live matched when the run started.

# Overview

| Input | From |
|---|---|
| Fields and values | the driver's `GitChange` ([RFC#0002]) |
| Where each field lives | the Workload's `spec.git.fields` (mapping), or `spec.git.find` |
| The base commit | the revision Flux applied at Hold ([RFC#0003]), or the head the operator accepted |

# Motivation

| Choice | Reason |
|---|---|
| The system `git` binary | It uses the operator's credential helpers and SSH agent; Tack never handles a Git secret. |
| Byte-level edits | A reviewer sees only the changed values; comments and layout stay. |
| A deadline on every git command, and one fetch per plan | A remote that accepted the connection and never answered hung the fetch, so the Git step never reached `Waiting`. |
| One commit per run, with a trailer | A run interrupted after its push adopts its own commit instead of stopping on `GitChanged`. |
| Stop when the branch moved | A commit made during the run may conflict with the switch; the operator decides. |
| Refuse a credential in the URL | The Workload is copied into the ledger's immutable spec, so a token would stay in every ledger and in `tack plan -o yaml` and `tack status -o yaml`. |
| An empty hooks path, not only `--no-verify` | `--no-verify` skips only `pre-commit`, `commit-msg` and `pre-push`. A global `prepare-commit-msg` hook could drop the trailer, and a resumed run would stop with `GitChanged` instead of adopting its commit. |
| No file system monitor, `ext::` transport, automatic gc or maintenance | Tack reads the operator's global configuration for credential helpers and ssh. A `core.fsmonitor` there would run its program in Tack's clone, and a `protocol.ext.allow` would let the URL `ext::CMD` run `CMD`. The URL comes from the Workload, which [RFC#0003] Requirement 21 does not check. |
| The commit checks where each change is written | The ledger records each change's file and path. Anyone who may write a ledger could otherwise point a removal at any key of the repository. [RFC#0003] Requirement 21 checks the rest of the Git step. |
| `--accept-git-head` must name the commit the stop named | A flag that took any value let Hold accept any revision at the other sites, so a head applied after the operator's review went unseen. |
| `--accept-git-head HEAD` is recorded as the commit it names | Recorded as `HEAD`, the release revision made the next check before release stop with `GitChanged`. |
| `--accept-git-head` after the commit sets what the release checks | Otherwise the steps after the commit waited for the run's commit, and a run whose branch moved past it could not go on. |

# Requirements

1. Tack MUST run `git` with `GIT_TERMINAL_PROMPT=0` and `LC_ALL=C`, without `GIT_DIR` and its sibling variables, and MUST NOT print credentials embedded in a URL.
2. Tack MUST NOT run client-side hooks: every git command runs with `core.hooksPath` set to an empty directory that Tack creates. Server-side rules still apply. Every git command MUST also turn off the other programs the operator's configuration could run that access does not need: `core.fsmonitor=false`, `protocol.ext.allow=never` (an `ext::` URL is a command), `gc.auto=0` and `maintenance.auto=false`. Credential helpers, askpass, the ssh command, proxies and commit signing stay as configured. Checked by unit tests.
3. Any failure to fetch, other than a missing branch, MUST count as unreachable, including a rejected credential or a wrong URL. A `Planned` plan then refuses to start ([RFC#0007]). Every git command MUST end within 2 minutes; a fetch or push that does not counts as unreachable, but a cancel of the run (Ctrl-C) stays a cancel. An HTTP transfer slower than 1 byte a second for 30 s MUST end earlier. Over SSH, Tack MUST give up on a connection after 15 s, and after 3 unanswered keepalives 15 s apart, unless the operator chose the ssh command (`GIT_SSH_COMMAND`, `GIT_SSH` or `core.sshCommand`). A plan MUST fetch Git at most once. Checked by unit tests.
4. A field with a mapping MUST be written where the mapping says. A mapping matches on site, object kind, name (and namespace when given) and field.
5. A field without a mapping MUST, when `spec.git.find` is set, be written into the one YAML document, in the site's find paths or the whole repository, whose API group, kind, name and namespace match its object. None or several matches MUST fail the plan, naming the candidates.
6. A field with neither MUST fail the plan, except an optional removal ([RFC#0004]), which the plan leaves out and notes.
7. At plan time, when Git is reachable, each mapped file MUST exist, and so MUST the parent of each mapped path that sets a value. A removal needs no parent (Requirement 8). Checked by unit tests.
8. An edit MUST change only the bytes of the value. A missing key MUST be inserted into its block mapping at that mapping's indentation. A removal MUST delete the key's lines, and be a no-op when the key is absent. Flow-style containers, anchors and aliases on the path, and replacing a multi-line block scalar, MUST be errors.
9. The commit MUST be based on the run's base commit. If the remote branch head differs:
   - when the head is this run's commit (trailer `Tack-Run: <run>`) on top of the base, Tack MUST adopt it;
   - otherwise Tack MUST stop with `GitChanged`, naming base and head.
10. Before the run's commit, `tack resume --accept-git-head <sha>` MUST record `<sha>` as the run's accepted revision (`status.git.acceptedRevision`) and use it as the base. After the run's commit, it MUST record `<sha>` as the release revision (`status.git.releaseRevision`), which the Release phase checks Git against ([RFC#0005] Requirements 8 and 12). A release revision that does not contain the run's commit MUST stop the run with `GitChanged`. When a `GitChanged` stop names one commit, the ledger MUST record it in `status.git.changedRevision` until the run goes on. While it is recorded, `<sha>` MUST name that commit, or be `HEAD`, which stands for it ([stop-reasons.md](../docs/runbooks/stop-reasons.md) has the procedure). Any other value MUST be refused before the operator is asked to confirm, with nothing written. A ledger without it takes `<sha>` as given, except `HEAD`, which stands for the branch head: `tack resume` MUST then read the branch head before asking the operator to confirm, print it, and record that commit, never `HEAD`; when Git cannot be read, it MUST refuse, with nothing written. Checked by unit tests.
11. The commit message MUST be `tack: <workload> primary <from> to <to> (<mode>)`, with `<mode>` the run's mode in lower case (`planned` or `siteloss`), a body naming the run, and the trailer `Tack-Run: <run>`. When `spec.git.author` is set, it is both author and committer. Otherwise git's configuration is used, with `user.useConfigOnly=true`, so git never guesses an identity. Checked by unit tests, and by golden tests of the dry run, which prints the message.
12. Tack MUST push without force. A rejected push MUST stop the run with `GitChanged`. A remote that cannot be reached MUST put the run in `Waiting` with `GitUnreachable` ([RFC#0007]).
13. If the edits change nothing, Tack MUST NOT commit, and the base is the run's commit.
14. The Workload's `spec.git.url` MUST NOT hold a password, nor a user in an `http` or `https` URL (a Git host may take it as a token). Otherwise loading the Workload MUST fail, and the error MUST NOT repeat the URL. A user in an `ssh` URL or an scp-like address (`git@host:path`) MAY be given. Tack MUST print the ledger's copy of the URL with any user and password replaced by `***`, also in YAML. Checked by unit tests.
15. Before it writes a change, the commit MUST check where the change goes. With a mapping (Requirement 4) in the run's Workload snapshot, the file, path and document MUST be the mapping's. Without one, the path MUST be the field's, and the file's document MUST define the change's object, by API group, kind, name and namespace, in the base commit. Any other change MUST stop the run with `StepFailed` before anything is committed, with a message naming the change and where its Workload puts it. A change without a file is found then (Requirement 5), so it passes. Checked by unit tests.

# Design

**Mapping.**

```yaml
spec:
  git:
    url: ssh://git@git.example.com/gitops.git
    branch: main
    fields:
    - site: a
      object: {kind: Cluster, namespace: db, name: pg-a}
      field: spec.replica.primary
      file: apps/db/site-a/values.yaml
      path: cnpg.replica.primary
    find:
      paths:
      - {site: a, path: clusters/site-a}
```

| Path syntax | Meaning |
|---|---|
| `a.b.c` | key `c` under `b` under `a` |
| `a[2].b` | key `b` of the third item of list `a` |

| Value | Written as |
|---|---|
| JSON string | a YAML string, plain when safe, else double-quoted |
| JSON number or boolean | plain |
| unset | the key is removed |

In a multi-document file where no document is the object, `document` selects a YAML document by index.

# Security Considerations

- Tack holds no Git credential. The operator's `git` configuration provides access.
- A Git URL with an embedded secret is refused (Requirement 14).

# Limitations

| Limitation | Trigger to revisit |
|---|---|
| Keys that contain dots cannot be addressed. | A repository that needs them. |
| Flow-style YAML on a path cannot be edited. | A repository that uses it. |
| A filter driver, such as Git LFS, still runs on checkout and add when `.gitattributes` names it and the operator's configuration defines it. Git cannot turn filters off in one setting. | A repository with a filter attribute on a file Tack reads or edits. |
| Tack does not sign commits; Git's configuration decides. | A repository that requires signed commits. |
| A fetch over 2 minutes counts as unreachable, even while it makes progress; so does one whose server sends nothing for 30 s (Tack fetches with `--quiet`). Over HTTP or HTTPS, and with the operator's own ssh command, only the 2-minute deadline ends a connection that never completes, so a plan can wait 2 minutes in a site loss that also takes down Git's host. | A fetch observed to end, or to wait, this way. |

<h1 style="text-align: center;">[RFC#0007] Break-Glass</h1>

# Abstract

A site loss can take Git with it. Tack then still holds and switches the live objects, and the Git step waits until Git is back. Steps on a lost site wait for that site; if it comes back still answering as primary, the run stops until the operator approves fencing it.

# Overview

| What is unreachable | What the run does |
|---|---|
| Git | Hold and Failover run without Git; the run waits at the Git step (`Waiting`, `GitUnreachable`, exit code 4); `tack resume` continues once Git answers. |
| A site other than `to` (and other than `from` in a planned run) | Its steps are `Deferred`; the run goes on and ends `Succeeded` with them deferred. |
| `to` | The run cannot start; a running step on it stops the run. |

# Motivation

| Choice | Reason |
|---|---|
| Switch live without Git | During a site loss, restoring writes is urgent; Git can follow. |
| Never release while waiting for Git | Released objects would get the old values back from Flux's last artifact. |
| Base revision from Flux, not from Git | It is what live matches, and it is readable in-cluster when Git is not. |
| Check a site several times before it counts as unreachable | Observed in a two-site test: one 5 s `/readyz` timeout, from a 10 s network blip between the operator's host and one site, stopped a step, twice in one run. |
| Check a deferrable site once in a site loss | The lost site does not answer; each further check would add up to 30 s to the write outage. |
| No Git fetch in Hold during a site loss | Observed in a two-site test with Git cut: Hold waited 1m30s for a GitRepository that could not fetch, which added 1m35s to a 3m11s write outage. |
| Stop when a lost site comes back as primary | Two primaries is the outcome a failover must not produce; the operator decides how to fence it. |

# Requirements

1. The Hold and Failover phases MUST NOT need Git. The base revision MUST come from the Kustomizations' `status.lastAppliedRevision` ([RFC#0003]). In a `SiteLoss` run, the Hold phase's `Reconcile` steps MUST NOT request or wait for a GitRepository fetch: Flux applies the artifact it has ([RFC#0005] Requirement 6). Checked by the dry run and by unit tests.
2. A `SiteLoss` plan MUST be possible with Git unreachable. Fields that need find ([RFC#0006]) stay unresolved in the plan, which says so, and are resolved when the Git step runs. A `Planned` plan MUST be refused when Git cannot be read: break-glass is for a site loss, and a misconfigured Git URL or credential would otherwise hold objects with no way to commit.
3. When Git cannot be reached at the Git step, the run MUST be `Waiting` with reason `GitUnreachable`, and the step `Pending`. A Release step MUST NOT run before the Git step succeeded.
4. `tack resume` MUST retry the Git step, and MUST still stop with `GitChanged` if the branch moved from the base.
5. `tack run` and `tack resume` MUST check a site's API (`/readyz`, 5 s per check) before their first step at that site. The site counts as unreachable only when 3 checks over at most 30 s fail; in a `SiteLoss` run, when 1 check fails and the site's steps are deferrable. When more than one check ran, the message of the site's step MUST say how many. A deferrable step ([RFC#0002]) on an unreachable site MUST be recorded `Deferred`; the run MUST go on. Checked by unit tests.
6. Before the first deferred step of a site that answers again, Tack MUST read the site. If it answers as primary and the operator did not pass `--fence <site>`, the run MUST stop with `FencedSiteIsPrimary` and change nothing at that site.
7. With `--fence <site>`, the site's deferred steps MUST run in plan order: its holds first, then its fence.
8. A run whose only remaining steps are deferred MUST end `Succeeded`, with a message counting them. A later `tack resume` MUST run them if their site answers.

# Design

A site loss with Git down, then both back:

| # | Event | Ledger |
|---|---|---|
| 1 | `tack run --mode site-loss --to b` with site a and Git down | Hold at b; a's steps `Deferred`; b promoted; state `Waiting`, `GitUnreachable` |
| 2 | Site a answers again, still primary; `tack resume` | state `Stopped`, `FencedSiteIsPrimary`; nothing changed at a |
| 3 | `tack resume --fence a` | a held and fenced; state `Waiting`, `GitUnreachable` |
| 4 | Git answers again; `tack resume` | commit, verify, release at a and b; state `Succeeded`; follow-up `Rebuild` for a |

If site a comes back after the commit instead, Flux at a applies Git, which already declares b primary: Flux fences a.

# Limitations

| Limitation | Trigger to revisit |
|---|---|
| While the run waits for Git, held objects stay held: Flux applies nothing to them, including unrelated Git changes. | A long Git outage. |
| A site that comes back after the run succeeded is fenced by Flux from Git, not by Tack; Tack does not watch for it. | A controller. |
| A run checks a site once per process, before its first step there. A network blip during a later step at that site still fails the step. | A step that fails from a blip after its site's check. |
| The plan and the search for runs check each site once. A blip then refuses a planned run, plans the site as unreachable, or leaves its ledgers out of the checks of [RFC#0003] Requirements 8 and 14. | A plan or a resume refused because of a blip. |
| In a `SiteLoss` run, the base is the revision Flux last applied, even when Git answers. If the branch moved after Flux last fetched it, the run stops with `GitChanged` at the Git step, after the switch. | An observed `GitChanged` after a site loss. |
| With three or more sites, sites where Flux last applied different revisions stop a `SiteLoss` run with `GitChanged` in Hold, before the switch. | The first three-site deployment. |

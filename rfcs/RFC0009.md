<h1 style="text-align: center;">[RFC#0009] The CLI and its Dry Run</h1>

# Abstract

`tack` has four commands: `plan`, the dry run; `run`, which starts a run after the operator confirms it; `resume`, which continues one from its ledger; and `status`, which reads ledgers. One definition of the commands produces the help, the man pages and the skill document for AI agents. A release builds the CLI's archives the same way from the same commit, and signs and attests what it publishes.

# Overview

| Command | Changes | Does |
|---|---|---|
| `tack plan -f WORKLOAD --to SITE [--mode planned\|site-loss]` | nothing | prints every step and change |
| `tack run -f WORKLOAD --to SITE [--mode ...]` | clusters and Git | prints the plan, asks, creates the ledger, runs |
| `tack resume RUN (-f WORKLOAD \| --context CTX)` | clusters and Git | prints the ledger, asks, runs the remaining steps |
| `tack status [RUN] (-f WORKLOAD \| --context CTX)` | nothing | lists runs, or shows one |
| `tack abandon RUN (-f WORKLOAD \| --context CTX)` | the run's ledger | prints the ledger and the holds it leaves, asks, records `status.abandoned` |

| Release asset | Holds |
|---|---|
| `tack-vX.Y.Z-OS-ARCH.tar.gz`, `.zip` on `windows` | the binary, its man pages, the CRD, `LICENSE` and `README.md` (Requirement 12) |
| `tack-vX.Y.Z-OS-ARCH.cdx.json` | the CycloneDX SBOM of that archive's binary (Requirement 24) |
| `tack-X.Y.Z.tgz` | the chart of the CRD, also at `oci://ghcr.io/takodotid/charts/tack` |
| `failover.tako.id_sitefailovers.yaml` | the CRD |
| `SHA256SUMS` | the SHA-256 of each asset above |
| `SHA256SUMS.sigstore.json` | the Sigstore bundle of `SHA256SUMS` (Requirement 23) |

# Motivation

| Choice | Reason |
|---|---|
| Captured values named in every message | Found in a review (#35, row 41) and reproduced in a unit test: a `Wait` on the demotion token that timed out printed the substituted token and the live one in its message, which `tack status` prints. |
| One filter for the URLs in every message, at the ledger write and the output | Found in a review (#35, row 43), inferred from the code, then shown in a unit test: Flux's and Strait's messages, such as a GitRepository that cannot clone a URL with a token, went into the ledger and the output as they came, and the redaction was defined twice. |
| Typed confirmation of the workload name | A habit of pressing "y" does not start a failover. |
| Read the sites again after the confirmation | Found in a review (#30), inferred: `tack run` waited at the confirmation with no time limit, then refused only runs that were not `Succeeded`. If the same switch finished meanwhile, a planned plan ran again: the demotion changed nothing, the capture read the old primary's leftover demotion token, and the promotion wrote a used token back. [RFC#0004] Motivation: CloudNativePG then holds the Cluster as unrecoverable. The comparison is of what the driver reads, not `resourceVersion`: CloudNativePG writes status often, and a refusal for a status write that changes nothing would block a failover. |
| The sites are read again before the first Failover step of every process | Found in a comment on #46 (PR #48's "Found, not fixed"), then reproduced in a unit test: the read after the confirmation ran only in `tack run`. A planned run that stopped in Hold, then resumed after the operator switched the primary by hand, scaled the old primary's Pooler to 0, ran the demotion on what was now a replica, patched the new primary with the token it captured, and timed out waiting for the promotion in the fake CloudNativePG. The ledger holds no copy of the plan's read, so the resume asks the driver whether it still allows the run. |
| A run abandoned before its start does not make a plan stale | Found in PR #49 by reading the code (#46), then reproduced in a CLI test: a run that lost the race of #35 row 35 while the operator confirmed changed nothing, yet the plan was refused, and the operator had to plan again. |
| The clusters and the Git URL before the confirmation | Found in a review (#32): the confirmation of `tack resume` showed neither the contexts nor the Git URL, so an operator could not see that a context reached another cluster. |
| `--yes` only for an approved run, refused without a terminal otherwise | Scripts and agents cannot start a run by accident. |
| Skill and man pages from the command definitions | They cannot drift from `--help`. |
| Explicit contexts per site | Tack must never act on whichever cluster happens to be current. |
| A site name that YAML reads as other text is refused unquoted | Found in a review (#35, row 50) by a probe of `config.Parse`: an unquoted site name `n`, `y`, `on`, `off`, `yes` or `no` became `"false"` or `"true"`, and `--to n` then failed; `010` became `"8"`. The ledger recorded the decoded name. |
| The Workload file follows the ledger's API version, and v0.1.x files still load | The Workload's spec is copied into the ledger ([RFC#0003]), so both change together. The `v1` schema equals `v1alpha1`'s, so an old file needs no change to work. |
| `tack abandon` | Found while writing the runbooks (PR #44), inferred from the code: a run abandoned by the operator had no durable mark, so it could be resumed until a new run took it over, and its Hold steps not yet done would hold again. The field `status.abandoned` exists since the search after the create (#35, row 35). The command reads the ledger back: a CRD older than v1.3.0 drops the field without an error. |
| `TakenOver` in the list of runs | Observed on kind (PR #44): `tack status` without a run listed a run that another run took over as its last state, such as `Stopped StepFailed`, with no sign of the take-over. |
| Times on progress lines, and each step's times in `tack status` | Found in a review (#35, row 29), verified in the code: progress lines had no time, and `tack status RUN` left out each step's `startedAt`, `finishedAt` and `attempts`, which the ledger holds. A terminal's log could not be laid next to the ledger, or the API servers' audit logs. |
| Docs named by a link at the binary's release tag | Reported in #51, inferred from the code: messages, plan notes and help named a doc by its path in the repository, such as `docs/runbooks/abandon-run.md`. An operator who runs a released `tack` has no checkout, and needs the runbook most when a run stops. The tag keeps the runbook in step with the code that printed it. |
| A release only from a signed tag on `main` with green CI, built and tested before any push | Found in a review (#33): any `v*` tag, on any commit, published a release. One job built and published, with write access to the repository and the packages, and without an environment. |
| Keyless signatures and attestations | Found in a review (#35, row 24): nothing was signed, and `SHA256SUMS` came from the same release as the archives, so the README's check proved only that a download was intact. Sigstore signs with the workflow's short-lived identity, so no signing key exists to leak, and the certificate names the workflow and the tag. |
| The same archives from the same commit | Found in a review (#35, row 44): the binaries rebuilt from a tag matched the release, the archives did not: `tar` kept the build's time and owner. While testing the fix, a `.zip` written in another time zone differed in its MS-DOS time, though its UTC time was the same. |
| Actions, tools and images pinned; a vulnerability scan | Found in a review (#35, rows 25, 45 and 46): the release ran whichever helm was the latest, with the token to push packages; the e2e checked its tools against checksums fetched from the same server; its images followed their tags; CI scanned for no known vulnerability. While pinning, the tag `18.6-system-trixie` of the PostgreSQL image named one digest in a local cache and another in the registry. |
| A second signal ends `tack` at once, and SIGHUP counts as a signal | Found in a review (#35, row 38), reproduced in a test that sends signals to a process: after the first Ctrl-C, the handler kept catching signals, so a second Ctrl-C did nothing while the ledger write that records the stop took up to 30 s. SIGHUP, sent when the operator's terminal or SSH session ends, ended `tack` without recording why the run stopped. |

# Requirements

1. `tack plan` MUST NOT write to any cluster or to Git. Checked by unit tests that fail on any write call, and by golden tests of its output.
2. The dry run MUST print, in run order and grouped by phase: each step's ID, site, description, and exactly what it changes or waits for (annotations, merge patches, conditions and timeouts, captured names, the Git file, path and value of each field, the checks), the follow-ups, and notes on unreachable sites and Git. Before the steps it MUST print, per site, the context, the API server the context points at, and the UID of the cluster's `kube-system` namespace ([RFC#0003] Requirement 19), then the Git URL without credentials.
3. `tack run` MUST print the plan, then require the operator to type the workload's name, unless `--yes` is given. Without a terminal and without `--yes`, it MUST refuse and change nothing.
4. `tack resume` MUST print the ledger, then per site the context, the API server it points at in the operator's kubeconfig and the cluster the run recorded, then the Git URL without credentials, and confirm the same way. Its decision flags are `--accept-git-head SHA` ([RFC#0006]), `--fence SITE` ([RFC#0007]).
5. `tack run --take-over RUN` MUST let the new run take over the holds of `RUN` ([RFC#0005]), and record it ([RFC#0003] Requirement 17). `RUN` then cannot resume ([RFC#0003] Requirement 18). The flag MAY be repeated, once per run, and each value MAY list runs separated by commas.
6. Every site client MUST be built from the site's `kubeContext` in the kubeconfig (`--kubeconfig` or the standard loading rules). A context missing from the kubeconfig MUST be an error; Tack MUST NOT fall back to the current context.
7. Exit codes MUST be:

| Code | Meaning |
|---|---|
| 0 | success |
| 1 | error |
| 2 | usage error, including a refused confirmation without a terminal |
| 3 | the run stopped for the operator |
| 4 | the run waits for something outside it |

8. `tack --skill` MUST print a skill document: YAML frontmatter with `name` and `description`, then Markdown built from the command definitions. It MUST say that an agent never starts `tack run` or `tack resume` without an explicit instruction from a human for that run, and that `tack plan` comes first.
9. Man pages MUST be generated from the command definitions: `tack(1)` and one page per subcommand, shipped in the release archives with the binary.
10. Tack MUST NOT print a secret. The text output of `tack status` MUST print captured values by name only; `-o yaml` prints the whole ledger, which holds no secret ([RFC#0003]), with the Git URL's user and password replaced by `***` ([RFC#0006] Requirement 14). A step's or run's message, in the ledger and in the output, MUST name a captured value of 8 bytes or more as `$(name)` instead of printing it; a `Wait` on a captured value MUST print neither it nor the live value it compares, only that value's size. Every message that Tack records in the ledger or prints MUST show the user and password of each URL in it as `***`, whatever its source, such as Flux, Strait, git or an API server: the run's and each step's message, the reason a run is abandoned, progress lines, a plan's notes and sites, the last error line, and `-o yaml`, for a ledger an older Tack wrote too. One function does it. Checked by unit tests.
11. Tack MUST read a Workload file of `apiVersion` `failover.tako.id/v1`, and of `failover.tako.id/v1alpha1` with a warning on stderr that it is deprecated. Any other `apiVersion` MUST be an error. A site name, or a reference to one, written as a plain YAML scalar that the file's decoder reads as other text, such as `n`, `on` or `yes` (a boolean in YAML 1.1) or `010` (a number), MUST be refused, with a message that names it and says to quote it; a quoted name is kept as written. The check reads the file only: the Workload snapshot of a ledger is not checked. Checked by unit tests.
12. `make dist` MUST build a release archive for `linux`, `darwin` and `windows`, each on `amd64` and `arm64`. Each archive MUST hold one directory named after it, with the binary, `man/man1/`, the CRD, `LICENSE` and `README.md`. On `windows` the binary MUST be `tack.exe` and the archive a `.zip`; otherwise the binary MUST be `tack` and the archive a `.tar.gz`. Checked by listing each archive.
13. After the confirmation, and before it creates the ledger, `tack run` MUST read again every site the plan read, with the plan's checks of each site, and refuse, changing nothing, when: a site's state as the driver reports it (reachable, role, declared primary, health, the driver's facts, the member's creation time) differs from the plan's; the driver refuses the request on the new state; a site's cluster differs from the plan's fingerprint ([RFC#0003] Requirement 19); or a run of the workload exists at a site the plan searched that the plan did not find, unless that run is abandoned and never recorded its start ([RFC#0003] Requirement 8): it ran no step. In each `tack run` and `tack resume`, before the run's first Failover step, while no Failover step has started in any process (each is `Pending` or `Deferred`, with no attempt), Tack MUST read every site again, with the run's checks, and stop with `StepFailed` before the step, which keeps its state, when the driver refuses the request on what it reads. A site whose steps can wait for it and that answers as primary, or declares itself primary, is left out of that read: [RFC#0007] Requirements 6 and 9 decide on it. Checked by unit tests.
14. The first SIGINT, SIGTERM or SIGHUP MUST cancel the run, which then records why it stopped, in a ledger write that outlives the cancel ([RFC#0003] Requirement 20). Any later signal MUST end `tack` at once, with the signal's default action. Checked by a test that sends both to a process.
15. `tack abandon RUN` MUST print the ledger and the objects the run still holds, then confirm as Requirement 3 says, then record `status.abandoned` with the time and `--reason` ([RFC#0003] Requirement 8), in a write that carries the ledger's `resourceVersion`, and change nothing else. It MUST refuse a run that succeeded with no `Deferred` step, and change nothing for a run already abandoned. It MUST read the ledger back, and fail with a message that names the CRD when the field is not there. Checked by unit tests.
16. `tack status` without RUN MUST list, in its state column, a run that is abandoned as `Abandoned`, and one that another run took over, by its `status.supersededBy` or a listed run's `spec.takeOver` or `spec.takeOvers`, as `TakenOver`. Checked by unit tests.
17. Every message, plan note and help line that Tack writes and that names a file of the repository, such as a runbook, MUST name it by its link `https://github.com/takodotid/tack/blob/<ref>/<path>`, with its anchor if any, and MUST NOT name it by its path alone. `<ref>` is the binary's version when that version is a release tag `vX.Y.Z`, and `main` otherwise. One function builds the link. Each file and anchor linked MUST exist in the repository. The man pages of a release archive MUST link at the ref of its binary. Checked by unit tests, and for the man pages by `make dist`.

## Releases

18. `make dist` MUST write the same archives, byte for byte, from one commit, one Go version and one `SOURCE_DATE_EPOCH`, whatever the build's time, time zone, umask and user. Every entry MUST have the time `SOURCE_DATE_EPOCH`, owner 0 with no owner names, and mode 0755 for a directory or an executable file and 0644 otherwise. A `.tar.gz` MUST hold no name or time in its gzip header; a `.zip` MUST store its times in UTC. Checked by the unit tests `TestWrite` and `TestReproducible` of `hack/archive`, and by `make dist`, whose `hack/distcheck` fails on an entry that differs (`TestRunRefusesUnreproducibleArchives`).
19. The release workflow MUST publish only for an annotated tag `vX.Y.Z` whose signature GitHub verifies, whose commit is on `main`, and whose commit's `ci` run of its push to `main` has finished with every job of `ci.yaml` successful. A later commit of `main` MUST NOT cancel that run. Checked by the unit tests `TestGate` and `TestCIWorkflow`, and by the release's job `gate`.
20. The release MUST NOT push a chart or create a GitHub release before `make verify test` and `hack/release/build.sh` pass on the tag's commit. It MUST publish the assets that this build wrote, checked against their `SHA256SUMS`. CI MUST run `hack/release/build.sh` on each pull request and each push to `main`. Checked by the unit tests `TestReleaseWorkflow` and `TestCIWorkflow`.
21. A job of the release that runs `make`, or Go code of the module or of its dependencies, on the runner MUST hold read permissions only. Checked by `TestReleaseWorkflow`, which refuses `go`, `make`, `hack/release/build.sh` and `actions/setup-go` in a job that can write.
22. The release MUST NOT replace a published version. It MUST stop when the chart version `X.Y.Z` or the GitHub release `vX.Y.Z` exists, or when the registry or GitHub does not answer that it is absent. It MUST check both before its first push, and each again right before its own push. Checked by the unit test `TestAbsent`, and by `TestReleaseWorkflow`.
23. The release MUST sign the chart, by the digest that the registry gives, and `SHA256SUMS` with Sigstore, keyless, under the workflow's OIDC identity. It MUST attest every asset of the GitHub release with GitHub artifact attestations. All of it MUST happen before the GitHub release exists. A long-lived signing key MUST NOT exist. The release MUST then verify what it published with the commands of the README's [Verify a release](../README.md#verify-a-release). Checked by `TestReleaseWorkflow`, and on each release by its last step.
24. Next to each archive, a release MUST hold a CycloneDX SBOM, `tack-vX.Y.Z-OS-ARCH.cdx.json`, made from the build information of that archive's binary. `SHA256SUMS` MUST list every asset of the release but itself and `SHA256SUMS.sigstore.json`. Checked by `hack/release/build.sh`, which fails unless `dist/` holds each asset, and by `TestReleaseWorkflow` for the files that the release attests and publishes.
25. A workflow MUST pin every action by commit SHA. kind, kubectl, flux, helm and cosign MUST be pinned by version and SHA-256 in `hack/tools/install.sh`, and the workflows and the e2e's instructions MUST install them with it. The Go tools of `make lint` and `make sbom` MUST be pinned in `hack/tools/go.mod`. Every image that the e2e's nodes pull, and every base image of a Dockerfile under `test/e2e/`, MUST be named by the digest of its index. Checked by `make lint`, through `hack/release/pinned.sh`, for the actions; by the unit tests `TestInstallChecksSHA256` and `TestE2EImagesPinned`; and by review for the workflows' use of `install.sh`. Go, which `actions/setup-go` downloads, is a Limitation.
26. CI MUST run `go mod verify`, `govulncheck`, `helm lint --strict` and `hack/release/pinned.sh` on each pull request and each push to `main`. Checked by the job `lint` of `ci.yaml`, through `make lint` (`TestCIWorkflow`).

## Progress and status

27. Each progress line that `tack plan`, `tack run`, `tack resume`, `tack status` and `tack abandon` print MUST start with its time in UTC, to the second, as RFC 3339 writes it, such as `2026-10-27T10:15:00Z`: the lines of the steps, the checks of a site, the notes, the deferrals, the stops and the ledger's writes. The plan, the status, the confirmation and the last error line MUST NOT. Checked by unit tests and by the golden tests of the dry run.
28. `tack status RUN` MUST print each phase's start and end, each step's start, end and attempts, as the ledger records them, and the run's history ([RFC#0003] Requirement 22), oldest first: each entry's time, state, reason, version, user, flags and message, and the count of entries dropped. `-o yaml` prints the history with its messages cleaned as Requirement 10 says. Checked by unit tests.

# Design

**Workload file.**

```yaml
apiVersion: failover.tako.id/v1
kind: Workload
metadata:
  name: pg-main
spec:
  driver: cnpg
  sites: [...]        # [RFC#0004]
  git: {...}          # [RFC#0006]
  ledger: {namespace: tack-system}
  routing: {...}      # [RFC#0008], optional
  timeouts: {demotion: 10m, promotion: 10m, flux: 5m, routing: 2m}
```

`--from` defaults to the primary that the `to` site declares.

**Finding a run.** With `-f`, `resume` and `status` search the ledger namespace of every reachable site; with `--context`, one context. `resume` then uses the Workload snapshot in the ledger, not the file.

**Releases.** Each job of `release.yaml`, in order:

| Job | Needs | Permissions | Does |
|---|---|---|---|
| `gate` | | `contents: read`, `actions: read` | Requirement 19, in the environment `release`. Checks that neither the chart nor the GitHub release of the version exists (Requirement 22). |
| `test` | `gate` | `contents: read` | `make verify test`, then `hack/release/build.sh`: the archives, the SBOMs, the CRD, the chart and `SHA256SUMS`, kept for `publish`. |
| `publish` | `test` | `contents: write`, `packages: write`, `id-token: write`, `attestations: write` | Checks the assets against `SHA256SUMS`, attests them, signs `SHA256SUMS`, pushes and signs the chart, creates the GitHub release, then verifies them. Runs shell, `helm`, `cosign`, `docker login` and `gh` only. |

A review in the environment `release` holds every later job. `build.sh` packages the chart from a copy whose files have the time `SOURCE_DATE_EPOCH`, so the chart's archive is the same for the same commit too. A re-run of failed jobs runs those jobs and the jobs after them; a push that an earlier attempt made stops the re-run (Requirement 22), and the version is released as the next patch version ([Release](../docs/runbooks/release.md)).

The signatures and attestations name the workflow and the tag:

| Field | Value |
|---|---|
| Certificate identity | `https://github.com/takodotid/tack/.github/workflows/release.yaml@refs/tags/vX.Y.Z` |
| OIDC issuer | `https://token.actions.githubusercontent.com` |
| Repository of the attestations | `takodotid/tack` |

**Rules for AI agents**, in the root help and therefore in the skill document:

- never start `tack run` or `tack resume` without a human's explicit instruction for that run;
- run `tack plan` first and show it;
- never pass `--yes`, `--fence`, `--accept-git-head` or `--take-over` unless the instruction names it;
- `tack plan` and `tack status` only read;
- when a run stops, report its reason and wait.

# Security Considerations

- Tack acts with the operator's kube credentials for each context; [RFC#0003] and [RFC#0005] list the permissions.
- The kubeconfig and Git credentials stay with the operator's tools; Tack stores none.
- A release holds no long-lived secret: the workflow's token and its OIDC identity exist only while its jobs run, and only `publish` can write ([Releases](#design)).

# Limitations

| Limitation | Trigger to revisit |
|---|---|
| No shell completion. | Operator request. |
| Output is text or YAML; no JSON. | A tool that consumes it. |
| A captured value shorter than 8 bytes is printed in messages: replacing it would garble them, and it is no token. | A driver that captures a short value. |
| A build that is not of a release tag links the docs at `main`, which may differ from its code: `make build` after a tag, `go install`, which sets no version, or a pre-release tag such as `v1.3.0-rc.1`. | A pre-release tag, or such a build run against production. |
| A message that a Tack older than v1.3.0 recorded in a ledger, such as a follow-up's reason, names its doc by its path: Tack prints it as recorded, also inside a new message that quotes it, such as the refusal of a planned run to a site left to rebuild. | An operator who reads such a ledger and needs the link. |
| `gate` runs from the workflow of the tag's commit. A tag on a commit whose `release.yaml` lacks it publishes anyway. Only the right to push `v*` tags limits that: a tag ruleset, a repository setting. | A release that must hold against a person who can push tags. |
| GitHub verifies a tag's signature against the keys of the tagger's GitHub account. Any account that may push tags passes Requirement 19 with its own key. | More than one person who may push tags, with only some trusted to release. |
| Some tools come pinned by others, or with the runner. `actions/setup-go` downloads Go. docker, gh, jq, curl and sha256sum come with the runner image. The e2e's Git server installs git with `apk add`, which checks the packages' signatures against the keys of its base image, pinned by digest, but not their versions. | A tool that a job with write access runs, and that these leave unpinned. |
| A run that fails after its chart's push cannot go on: a re-run stops with the version published (Requirement 22). The next patch version releases instead. | A release that fails there. A step could then skip an asset that this run's `SHA256SUMS` names. |
| The SBOM lists the modules that the binary's build information names, with the Go version as a property, not the standard library as a component. `govulncheck` in CI covers the standard library. | A consumer of the SBOM that must see the standard library. |

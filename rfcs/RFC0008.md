<h1 style="text-align: center;">[RFC#0008] Confirming Routing from Strait's Status</h1>

# Abstract

Strait points each application name at the workload's active member, and follows a promotion by itself. When the Workload names Strait's objects, a run ends by waiting until Strait at each listed site routes to the new primary's member only. Tack reads Strait's status; it never writes Strait's objects.

# Overview

The check is opt-in: it exists in a plan only when the Workload sets `spec.routing.strait`.

# Requirements

1. Tack MUST only `get` Strait's `SiteService` objects (`strait.tako.id/v1alpha1`).
2. The Workload MUST name, per site that runs Strait, the `SiteService` to read, and, for every site, the name of the site's member in that `SiteService`.
3. A `Routing` step MUST succeed when the `SiteService`'s `status.observedGeneration` equals its `metadata.generation`, `status.route.members` is exactly the `to` site's member, and `status.route.reason` is `Active`. It MUST fail after `timeouts.routing` (default 2m).
4. When the `SiteService` API is absent at a site, the step MUST fail saying Strait is not installed there.
5. The `Routing` steps MUST run after every release.

# Design

```yaml
spec:
  routing:
    strait:
      services:
      - {site: a, namespace: apps, name: postgres}
      - {site: b, namespace: apps, name: postgres}
      members:
      - {site: a, member: pg-a}
      - {site: b, member: pg-b}
```

Fields read, from Strait's `api/v1alpha1/siteservice_types.go` on branch `v1`:

| Field | Use |
|---|---|
| `metadata.generation`, `status.observedGeneration` | the status is current |
| `status.route.members` | the routed members; empty means nowhere |
| `status.route.reason` | `Active` when one writable member is routed |
| `status.route.message` | reported when the check fails |

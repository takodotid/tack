<h1 style="text-align: center;">[RFC#0004] CloudNativePG Support</h1>

# Abstract

The `cnpg` driver switches the primary of a CloudNativePG deployment in the distributed topology. In that topology, each site has one `Cluster`, `.spec.replica.primary` names the primary, and a demotion token moves the primary without losing writes. The driver also moves the read-write `Pooler`, which runs only at the primary's site. This RFC sets the steps, the signals Tack waits for, and the fields Tack writes to Git, each with the CloudNativePG fact behind it.

# Overview

| Mode | What happens |
|---|---|
| `Planned` | The old primary demotes and publishes a demotion token. The new site replays up to that token, then promotes with it. No write is lost. |
| `SiteLoss` | The old site is lost. The new site promotes without a token. The old primary may hold writes that the new one lacks. It needs a rebuild before it can follow again. |

Facts observed on kind with CloudNativePG v1.30.1 and Flux v2.10.0:

| Observation | Consequence |
|---|---|
| During a demotion, `Ready=True` and phase `Cluster in healthy state` come back about a second before `demotionToken` is set. | Health is not a demotion signal; the token and `inProgress` are. |
| `lastPromotionToken` is set up to 2 s before PostgreSQL leaves recovery. | The promotion wait also needs an instance reporting `isPrimary: true` and a healthy phase. |
| A Pooler whose Cluster demotes gives connect timeouts for 7 to 16 s, then read-only errors; a Pooler at 0 gives `Connection refused` at once. | The old site's Pooler goes to 0 before the demotion. |
| A stale token on a Cluster makes the webhook reject Flux's dry-run when Git demotes that Cluster, which blocks the whole Kustomization. | Every patch that declares another primary also sets `promotionToken: null`. |
| An old primary that returns after a site loss keeps taking writes until Flux or Tack fences it, and both sites report healthy. Only the timeline and `isPrimary` differ. | The fence check reads `isPrimary`; routing away from it is Strait's job. |
| A failed-over old primary loops on "requested starting point ... is not in this server's history" while its status stays `Cluster in healthy state`. | Status cannot tell it from a healthy replica. Tack relies on the `Rebuild` follow-up in the ledger. |
| A healthy replica reports its old timeline in `instancesReportedState.*.timeLineID` until its next restartpoint, while it already streams on the new one. | The timeline cannot tell a diverged replica from a healthy one either. |
| Rebuilding needs `bootstrap` changed in Git first: a replica cannot be created from `initdb`. Deleting the Cluster removes its PVC. | The runbook changes Git before deleting. |

| Choice | Reason |
|---|---|
| A Cluster without `spec.replica`, or without `primary`, that reports `isPrimary` is `Primary` (Requirement 3) | Found in a review (#35, row 42): the role table called it `Unknown`, while the driver called it `Primary`. The driver's answer is the safer one. Such a site counts as a live primary, so a site-loss plan refuses it (Requirement 5), and the read before its steps stops the run ([RFC#0007] Requirement 6). |
| The plan checks each site's `spec.externalClusters` | Observed on kind in the first three-site e2e (#66): CloudNativePG's webhook refused to make pg-b declare pg-c primary, `spec.replicaCluster.primary: Invalid value: "pg-c": External cluster pg-c not found`, in a step after the promotion. The step stopped with `StepFailed` and changed nothing, but the run stopped with its new primary promoted. |
| Positions from `/pg/status`, through the API server | Decided for #72. SQL needs a database credential and a network path to each site's database, or `exec` into a pod, which Requirement 2 of [RFC#0001] forbids. The status endpoint needs `get` on pods and `pods/proxy` in the member's namespace, and a GET only. |
| A position that cannot be read is a warning | Decided for #72: a site loss must not stop because the operator lacks the new permission, or because a pod does not answer. |
| The replay lag from the instance's metrics | Decided by the operator for #72, 2026-11-13: the same `pods/proxy` permission as the position, and no database credential. It replaces nothing: the position still decides which replica is ahead. |
| The replay time from an opt-in query, read only when present | Decided by the operator for #94, 2026-11-13: the RPO of a site loss as a time, without a guarantee that every earlier commit is in `to` (see the PostgreSQL fact above). CloudNativePG's default queries do not export the time. The query is in Git, so a Cluster without it keeps the plan of #72. |
| A site's position is the furthest of what it received and replayed | Before a replica ends recovery, its promotion replays the WAL it received. So received WAL is not lost. |
| A `SiteLoss` run refuses a target behind another replica, unless `--accept-behind` | Found in a review of v1.6.0 (#72): with three sites, nothing helped pick the most caught-up replica, and a replica ahead of `to` was left unable to follow it, with no `Rebuild`. The override is recorded in the ledger, so the read before the first Failover step ([RFC#0009] Requirement 13) accepts it in every process. |
| The fork point, the old primary's snapshot and its archive are recorded | Found in a review of v1.6.0 (#73): a site loss recorded no fork point, and the rebuild dropped the writes that the old primary took after that point. Two histories can change the same row, so the writes are handed to their owners, never merged. |
| Archiving that does not work after the promotion warns and records `CheckArchiving`, and does not stop the run | Decided for #74: writes are back by then. A stop there would keep Flux held and Git behind live until the archive is fixed. |
| A shared archive refuses a planned run and warns in a site loss | Same reason as Requirement 12: the fix is in Git, and a site loss may have taken Git with it. |
| A record that cannot be read does not stop the run | A position or timeline that cannot be read must not block a promotion. The runbook says how to find the fork point without it. |
| The snapshot is opt-in, and a failed snapshot stops the run | A Backup fails on a site without VolumeSnapshot support, such as the e2e's kind clusters. An operator who asked for the snapshot is told, before anyone rebuilds. |
| A `SiteLoss` plan warns of it, and does not refuse | Found in a review of PR #68: the refusal applied to `SiteLoss` plans too, with no override, and said to fix it through Git, which may have gone with the lost site. The step fails closed: CloudNativePG refuses it, and it changes nothing, as observed on kind. |

# Requirements

1. Each site's member MUST be one `Cluster` whose `.spec.replica` sets `primary`, and MUST NOT set `enabled`. Each site's `Cluster` MUST have its own name.
2. The driver MUST read, per site: `spec.replica.{self,primary,minApplyDelay,enabled}`, the names of `spec.externalClusters`, `status.phase`, `status.currentPrimary`, `status.switchReplicaClusterStatus.inProgress`, `status.instancesReportedState.*.isPrimary`, the configured `Pooler`, and the position of Requirement 13.
3. Roles, by the first rule that matches. Checked by unit tests.

| Role | Rule |
|---|---|
| `Unknown` | `enabled` is set |
| `Replica` | `primary` is set and differs from `self` (or the name) |
| `Primary` | an instance reports `isPrimary: true`, and `primary` equals `self` (or the name), or `spec.replica` or its `primary` is absent |
| `Unknown` | otherwise |

A site is healthy when its phase is `Cluster in healthy state` and no demotion is in progress.

4. A `Planned` run MUST be refused unless: `from` is a healthy `Primary`; `to` is a healthy `Replica`; every reachable site declares `from`; `to` does not set `minApplyDelay`; no demotion is in progress; and `to` was not left to rebuild by an earlier run ([RFC#0003] Requirement 14). The driver reports the `Cluster`'s `metadata.creationTimestamp` as the member's creation time.
5. A `SiteLoss` run MUST be refused if `from` answers as `Primary`, and unless `to` is a healthy `Replica`.
6. A `Planned` run's Failover steps MUST be, in order:

| # | Step | Site | Content |
|---|---|---|---|
| 1 | Patch, Wait | from | Pooler `instances: 0`; Deployment `replicas` empty |
| 2 | Patch | from | `replica.primary: <to Cluster>`, `replica.promotionToken: null` |
| 3 | Wait | from | `status.demotionToken` not empty, `status.switchReplicaClusterStatus.inProgress` not `true` |
| 4 | Capture | from | `status.demotionToken` as `demotionToken` |
| 5 | Patch | to | `replica.primary: <to Cluster>`, `replica.promotionToken: $(demotionToken)`, in one patch, once the read before the promotion lets it, and from's `status.demotionToken` still equals `$(demotionToken)` when from answers ([RFC#0007] Requirement 9) |
| 6 | Wait | to | `status.lastPromotionToken` equals `$(demotionToken)`, an instance `isPrimary`, phase healthy |
| 7 | Patch | to | `replica.promotionToken: null` |
| 8 | Patch | each other site | `replica.primary: <to Cluster>`, `replica.promotionToken: null` |
| 9 | Patch, Wait | to | Pooler `instances: <configured>`; Deployment `readyReplicas` equals it |
| 10 | Patch, Wait | each site but `from` and `to` | Pooler `instances: 0`; Deployment `replicas` empty |
| 11 | Wait | to | Verify (Requirement 9) |
| 12 | Record | to | `verify-archiving-<to>` (Requirement 17) |

7. A `SiteLoss` run's Failover steps MUST be, in order:

| # | Step | Site | Content |
|---|---|---|---|
| 1 | Patch | from, deferrable | fence: `replica.primary: <to Cluster>`, `replica.promotionToken: null` |
| 2 | Patch, Wait | from, deferrable | Pooler `instances: 0`; Deployment `replicas` empty |
| 2a | Record | to | `record-position-<to>`: its position (Requirement 15) |
| 3 | Patch | to | `replica.primary: <to Cluster>`, `replica.promotionToken: null`, once the read before the promotion lets it ([RFC#0007] Requirement 9) |
| 4 | Wait | to | an instance `isPrimary`, phase healthy |
| 4a | Record | to | `record-fork-<to>`: its new timeline (Requirement 15) |
| 5 | Patch | each other site | as Planned step 8 |
| 6 | Patch, Wait | to | as Planned step 9 |
| 6a | Create, Record | from, deferrable | with `snapshot` set for `from`: `snapshot-<from>`, then `record-snapshot-<from>`; otherwise `record-archive-<from>` (Requirement 15) |
| 7 | Wait | to | Verify (Requirement 9) |
| 8 | Record | to | `verify-archiving-<to>` (Requirement 17) |

The run MUST record the follow-up `Rebuild` for `from`.

In both modes, `Demotion` ([RFC#0002] Requirement 2) MUST name, by the IDs of every earlier release: `demote-<from>` (Planned step 2) or `fence-<from>` (SiteLoss step 1) for `from`, and `declare-<site>` (Planned step 8, SiteLoss step 5) for each other site but `to`. Checked by unit tests.

8. The Git change MUST set, for every site: the `Cluster`'s `spec.replica.primary` to the `to` Cluster's name; the Pooler's `spec.instances` to the configured value at `to` and `0` elsewhere; and MUST remove the `Cluster`'s `spec.replica.promotionToken`. The removal is optional ([RFC#0006]). Without a mapping or find, it is left out, and the check before release stops the run if Git sets a token.
9. Verify at `to` MUST hold when the `Cluster` declares itself primary, an instance reports `isPrimary: true`, and the phase is healthy. At any other site it MUST hold when the `Cluster` declares the `to` Cluster primary.
10. Every `Wait` MUST time out: demotion waits after `timeouts.demotion`, promotion and Pooler waits after `timeouts.promotion` (both default 10m). The wait for a snapshot MUST time out after `timeouts.snapshot` (default 30m).
11. Tack MUST NOT rebuild a member. The rebuild is the operator's: [docs/runbooks/rebuild-old-primary.md](../docs/runbooks/rebuild-old-primary.md).
12. This rule is about a site that answers, other than `to`, whose `Cluster` does not name `to`'s `Cluster` among its `spec.externalClusters`. Every such site's `Cluster` comes to declare `to`'s `Cluster` primary, and CloudNativePG refuses a primary that the `Cluster` does not name there. For such a site, a `Planned` run MUST be refused, in its plan and before any step. A `SiteLoss` plan MUST NOT be refused for it. The plan MUST note it as a warning that names the step where the run stops: `fence-<from>` before the promotion, or `declare-<site>` after it. CloudNativePG refuses that step, the step fails, and the run stops there with `StepFailed`. Each message MUST name the site, its `Cluster` and `to`'s. Checked by unit tests.
13. A plan MUST read, at each site that answers, the WAL position of the `Cluster`'s current primary pod (`status.currentPrimary`): a GET of the Pod, then a GET of its instance manager's status, port 8000, path `/pg/status`, through the API server's `pods/proxy`, with the scheme that the Pod's `postgres` container serves. For a replica, it MUST then read its replay lag: a GET of the same pod's metrics, port 9187, path `/metrics`, with the scheme that the `postgres` container serves them, and the value of `cnpg_pg_replication_lag`. It MUST read nothing else through `pods/proxy`. A read that fails MUST NOT refuse the plan. The plan MUST print it and note it as a warning that names the permissions. A replay lag that cannot be read MUST be printed as such, and noted without a warning for `to`. The plan MUST print, per site: for a replica, the received and replayed positions, the timeline, whether its WAL receiver runs, whether replay is paused, and its replay lag, a lag of 0 as `replayed all it received` and never as a time; when the metrics hold `cnpg_tack_replay_timestamp_seconds`, from the opt-in query `deploy/cnpg/replay-time.yaml`, the commit time of the last transaction it replayed, in RFC 3339 to the millisecond, and its age by Tack's clock, in its place; for a primary, its write position; and how each replica compares with the others of the same database (`systemID`): `most caught up`, or `behind <site> by <size>`. A site's position is the furthest of its received and replayed positions. A `SiteLoss` plan MUST note that replication between sites is asynchronous, and that the writes the old primary took after `to`'s position are lost. With the replay-time query, it MUST also note `to`'s last replayed commit time, by the old primary's clock, and that the writes the old primary committed after it are lost, and so may be a few committed just before it, under concurrent writes. It MUST NOT state that every transaction committed up to that time is in `to`. When the query returns NULL, it MUST note that it cannot say when `to`'s last replayed commit was. Without the metric, the plan's output MUST be what it is without the query. It MUST warn when `to` sets `minApplyDelay`, when `to`'s replay is paused, and when `to`'s replay lag is above 0, with the size of the WAL it received and has not replayed, if any. Checked by unit tests.
14. A `SiteLoss` run MUST be refused, in its plan and before any step, when a site that answers, other than `from` and `to`, is a `Replica` of the same database whose position is past `to`'s, unless the operator passes `--accept-behind`. The refusal MUST name both sites, both positions, the most caught-up site, and the flag. With the flag, the ledger MUST record it in `spec.acceptBehind`, the plan MUST warn of each such site, and the run MUST record the follow-up `Rebuild` for each. Positions that cannot be read cause no refusal. A `Planned` run MUST refuse the flag. Checked by unit tests.
15. A `SiteLoss` run MUST find, keep and hand over the old primary's writes, and MUST NOT merge them:

| Step | Reads, then records | Where | When it cannot read |
|---|---|---|---|
| `record-position-<to>`, right before the promotion | `to`'s position (Requirement 13) and its timeline: the new history leaves the old one there, or just after | `status.fork.position`, `.parentTimeline` | records why in `status.fork.message`, and the run goes on |
| `record-fork-<to>`, right after the promotion | the timeline in the name of the WAL file that `to`'s current primary writes (`currentWAL` of `/pg/status`), and the time | `status.fork.timeline`, `.at` | as above |
| `snapshot-<from>`, when the Workload sets `spec.sites[].cnpg.snapshot` for `from` | creates a CloudNativePG `Backup` named `<run>-<from>`, labelled `failover.tako.id/run: <run>`, with `method: volumeSnapshot`, `target: primary`, `online: false`; adopts only a Backup of that name with this run's label | the Backup | stops the run |
| `record-snapshot-<from>` | waits until the Backup's phase is `completed`; records it and its VolumeSnapshots (`status.snapshotBackupStatus.elements`), and where `from`'s Cluster archives WAL | the follow-up `Rebuild` of `from`: `snapshot`, `archive` | a failed Backup stops the run, with what to fix |
| `record-archive-<from>`, without `snapshot` | where `from`'s Cluster archives WAL: `spec.backup.barmanObjectStore` or the barman-cloud plugin | the follow-up `Rebuild` of `from`: `archive` | stops the run |

The steps at `from` come after its fence, so the snapshot is of a member that no longer takes writes. A planned run records none of them: it forks no history. The rebuild runbook's first check MUST be that the run recorded the snapshot, and it MUST stop without one. Checked by unit tests.

16. A plan MUST read, at each site that answers, where its `Cluster` archives WAL: `spec.backup.barmanObjectStore`'s `destinationPath`, or the `destinationPath` of the `ObjectStore` (`barmancloud.cnpg.io/v1`) that its barman-cloud plugin names, with the server name, `serverName` or the `Cluster`'s name. Two such sites share a destination when they have the same path and server name. In that case, a `Planned` run MUST be refused, in its plan and before any step. A `SiteLoss` plan MUST NOT be refused for it, and MUST note it as a warning. Each message MUST name both sites, both `Cluster`s and the destination. A destination that cannot be read MUST be noted as a warning, and refuses nothing. Checked by unit tests.
17. In both modes, the last Failover step, `verify-archiving-<to>`, MUST wait, up to `timeouts.archiving` (default 5m), until `to`'s `Cluster` reports `ContinuousArchiving` `True` and its current primary's last archived WAL file (`lastArchivedWAL` of `/pg/status`) is of the timeline it writes. It MUST pass at once when the `Cluster` names no WAL archive. When it times out, the step MUST end with a warning, the run MUST record the follow-up `CheckArchiving` for `to`, and go on. A plan MUST warn when `to` reports `ContinuousArchiving` `False`. Checked by unit tests.

18. A `Planned` run's wait for the promotion (step 6) MUST set `stall` to 2 minutes. The wait then stops early, with `StepFailed`, when `to`'s replay position (`/pg/status`) stands still for that long short of the demotion token's checkpoint (`latestCheckpointREDOLocation`), which CloudNativePG waits for before it promotes. A position or token that cannot be read MUST NOT stop it. The promotion patch stays: a resume waits again. Checked by unit tests.

# Design

**Workload.**

```yaml
spec:
  driver: cnpg
  sites:
  - name: a
    kubeContext: site-a
    cnpg:
      cluster: {namespace: db, name: pg-a}
      pooler: {namespace: db, name: pg-a-pooler-rw, instances: 2}
```

**Why the token is removed live.** After step 5, the token has done its work. If it stays in the spec, it blocks a later demotion, because the webhook rejects a token on a replica. It also becomes the trap described above if it is ever removed and then applied again. Removing it from a primary only clears `lastPromotionToken`.

**Why the old Pooler stops first.** Writes stop anyway when the old primary demotes. If its Pooler is at 0 first, clients get a fast refusal, instead of timeouts followed by read-only errors from a standby. The new Pooler comes up once the new primary is healthy.

**Why fence first in a site loss.** If `from` answers at all, it is declared a replica before `to` promotes, so it cannot come back as a second primary. If it does not answer, the fence waits for it ([RFC#0007]).

# Security Considerations

- Requirement 13 needs `get` on `pods` and `pods/proxy` in each member's namespace ([docs/operations.md](../docs/operations.md#permissions), row 18). Pod names are generated, so the grant cannot name them. `pods/proxy` with `get` lets its holder send a GET to any port of any Pod in that namespace through the API server, including an endpoint served without authentication. Tack sends a GET to `/pg/status`, and for a replica a GET to `/metrics`. Grant it only in the members' namespaces.
- Requirement 15's snapshot needs `create` and `get` on `backups` (`postgresql.cnpg.io`) in each member's namespace (row 19). Backup names hold the run's name, so the grant cannot name them. A Backup that Tack creates fences its target instance while the snapshot is taken, as any cold Backup does.
- Requirement 16 needs `get` on the `objectstores` that the Clusters name (row 20). It is optional: without it, the plan warns that it could not check.
- `/pg/status` holds positions, the system identifier, configuration hashes and the pod's spec. Tack prints only the positions, the timeline and the stream's state.
- `/metrics` holds the instance's metrics, such as database names and settings. Tack reads only `cnpg_pg_replication_lag` and `cnpg_tack_replay_timestamp_seconds`.

# Limitations

| Limitation | Trigger to revisit |
|---|---|
| One read-write Pooler per site. Read-only Poolers are not moved. | A workload with several Poolers that follow the primary. |
| With three or more sites, the driver does not check that each replica's `source` chain reaches the new primary. | The first three-site deployment. |
| If the old primary's fast shutdown outlasts `switchoverDelay`, CloudNativePG shuts down immediately and never publishes a token (`pkg/management/postgres/instance.go:695-720`). The demotion wait then times out and the run stops. A shutdown that outlasts `timeouts.demotion` stops the run while CloudNativePG keeps waiting. A resume waits again ([docs/operations.md](../docs/operations.md#how-long-writes-stay-down)). | An observed timeout. |
| The rebuild of an old primary is manual, and so is the hand-over of its writes ([docs/runbooks/recover-old-primary-writes.md](../docs/runbooks/recover-old-primary-writes.md)). | A safe, declarative rebuild in CloudNativePG. |
| The fork position is read right before the promotion: a replica that replays more WAL before it promotes forks just after it. The runbook reads from that position, so it lists a little more, never less. | A record of the exact switch point that the instance status gives. |
| A replica of a third site that was ahead of `to` gets a `Rebuild`, but no snapshot: only `from` does. | A run observed with a third site ahead. |
| Without the opt-in replay-time query ([docs/workload.md](../docs/workload.md#replay-time)), the plan cannot say when a replica's last replayed commit was: the replay lag is 0 once a replica has replayed all it received, which is the usual state after a site loss. A replica whose source stopped long ago then reads as most caught up when no other site is ahead. With the query, the time is no exact RPO line: under concurrent writes, a few commits stamped just before it may be lost. The lag and the replay time can be up to `metricsQueriesTTL` old. The replay time is the old primary's clock. | The time of the last replayed transaction in the instance status, or in CloudNativePG's default queries; a WAL-ordered commit position that PostgreSQL exposes. |
| Positions are read once in the plan and once after the confirmation. A replica that still restores WAL from an archive can move past another between the read and the promotion. | A replica observed to move after the read. |
| In a `SiteLoss` run, an old primary that is alive but cut off from the operator keeps taking writes until it is fenced ([RFC#0007] Limitations). Those writes are lost to the new primary. The rebuild drops them. | A fence that does not need the site's API. |

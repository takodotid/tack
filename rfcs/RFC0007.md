<h1 style="text-align: center;">[RFC#0007] Break-Glass</h1>

# Abstract

A site loss can take Git with it. Tack then still holds and switches the live objects, and the Git step waits until Git is back. Steps on a lost site wait for that site; if it comes back still answering as primary, the run stops until the operator approves fencing it. From the demotion of `from` on, before each Failover step, the promotion of `to` among them, the run stops in every mode while another site that answers is primary. Before the promotion, it also stops while a value it captured, such as the demotion token, differs from its source.

# Overview

| What is unreachable | What the run does |
|---|---|
| Git | Hold and Failover run without Git; the run waits at the Git step (`Waiting`, `GitUnreachable`, exit code 4); `tack resume` continues once Git answers. |
| A site other than `to` (and other than `from` in a planned run) | Its steps are `Deferred`; the run goes on and ends `Succeeded` with them deferred. |
| `to` | The run cannot start; a running step on it stops the run. |

# Motivation

| Choice | Reason |
|---|---|
| Switch live without Git | During a site loss, restoring writes is urgent; Git can follow. |
| Never release while waiting for Git | Released objects would get the old values back from Flux's last artifact. |
| Base revision from Flux, not from Git | It is what live matches, and it is readable in-cluster when Git is not. |
| Only a check that gets no answer counts toward a lost site | Found in a review (#25) and reproduced in a unit test: a context missing from the kubeconfig, or a token the site refuses (401, 403), made a live primary read as lost. A site-loss plan was accepted, its fence was deferred, and the run ended `Succeeded` with two primaries. Such an error is on the operator's side and lasts: it would make every run see the site as lost. |
| Repeat a check that the API server answers with 5xx or 429, but never count the site as lost for it | An API server that restarts answers `/readyz` with an error for a moment. The answer still shows that the site is there. |
| A 5xx or 429 never counts as a lost site, also during a real loss | Decided for #38, item 8. A load balancer in front of a lost control plane may answer 503, but so may one in front of a live API server that restarts or is overloaded: Tack cannot tell them apart from the operator's host. Counting the answer as a lost site could promote a second primary next to a live one (#25). The operator confirms the loss from a second vantage point, and the runbook's way on then makes the site give no answer. How real providers answer during a loss was not tested. |
| Check a site several times before it counts as unreachable | Observed in a two-site test: one 5 s `/readyz` timeout, from a 10 s network blip between the operator's host and one site, stopped a step, twice in one run. |
| The same checks in the plan and the searches for runs | Observed in a two-site test: a short network blip between the operator's host and one site failed `tack plan`, which checked each site once. The searches for runs checked each site once too: a blip left the site's runs out of the checks of [RFC#0003] Requirements 8 and 14, and out of `tack resume` and `tack status`. |
| Check a site other than `to` once in a site loss | The lost site does not answer; two more checks and their pauses would add up to 25 s to the write outage, in the plan and again in the run. |
| 3 checks in the read before a site's steps, in every mode | The site has just answered the check before its step, so a failed check is a blip, not a lost site. With 1 check, a blip kept its steps `Deferred` until a later resume. |
| The search for a named run checks a failed site again only when the run is not found | A resume of a site-loss run finds its ledger at `to`. Two more checks of the lost site would add up to 25 s to each resume, and to the write outage when the run stopped before the promotion. |
| No Git fetch in Hold during a site loss | Observed in a two-site test with Git cut: Hold waited 1m30s for a GitRepository that could not fetch, which added 1m35s to a 3m11s write outage. |
| Note in every site-loss plan that a lost site may only be cut off | Found in a review (#26), inferred from the code: no runbook, plan note or Limitation said that a site cut off from the operator, but alive, stays primary while the run promotes another. |
| Stop when a lost site comes back as primary | Two primaries is the outcome a failover must not produce; the operator decides how to fence it. |
| Read a site before its first step in each process, whatever the step's state | Observed in a unit test (#23): the read ran only before a `Deferred` step. The stop with `FencedSiteIsPrimary` recorded the step `Failed`, so a second `tack resume` without `--fence` held Cluster `pg-a` at the returning site, still primary. After a resume with `--fence`, the site's steps can be `Pending`, `Failed` or `Running`, and the ledger does not record the approval. |
| A stop by the read leaves the step's state | The step did not start. |
| An interrupt during the read is not a site that gave no answer | Found in a review (#35, row 34) and reproduced in a unit test: a Ctrl-C during the read made the site read as giving no answer, so a `Pending` step was recorded `Deferred` with "context canceled", and the run stopped at the next step. |
| Read every site but `to` before the promotion, in every mode and process (Requirement 9) | Found on kind while writing the runbooks of #41 (#45): a planned run from b to a died after `demote-b`; the operator promoted b again by hand and removed the holds. A resume stopped at `promote-a` because the holds were gone, and its message said to hold them again. Reproduced in a unit test: with the holds back, the resume promoted a with the token of b's earlier demotion while b was primary, and the run ended `Succeeded`. Two primaries on CloudNativePG is inferred. The read before a site's steps (Requirement 6) skips `to`, and does not run for a site whose steps are done. |
| A site that declares itself primary counts, before it reports `isPrimary` | CloudNativePG promotes such a Cluster at once ([RFC#0004] Motivation). |
| The read before a site's steps counts a site that declares itself primary too | Found in a review (#35, row 33) and reproduced in a unit test: a lost site came back declaring itself primary, before an instance reported `isPrimary`. The read before its steps saw no primary, and the resume held and fenced it without the operator's decision. |
| A plan notes such a site, and does not refuse it | A `SiteLoss` plan refuses only a `from` that answers as primary ([RFC#0004] Requirement 5). A `from` whose API answers but whose instances are down still declares itself primary. Refusing it would leave no way through Tack: a fence by hand is undone by Flux, which no run holds. The run stops before its first step there, and `--fence` lets it hold and fence the site. |
| `--fence` does not let the promotion go on for a site whose Failover steps are all before it | Such a site is `from`. Its demotion or fence is done, and no step of the run fences it again. Promoting `to` then gives two primaries, and in a `Planned` run uses the token of a demotion that a later promotion undid. |
| `--fence` lets the promotion go on for a site whose Failover steps come after it | It keeps what `--fence` did for a third site before this read: the run holds the site, promotes `to`, then declares the new primary there ([RFC#0004] Requirement 6, step 8). |
| Read every site but `to` before each Failover step after the demotion, not only before the promotion | Observed in a two-site test of v1.2.1 (#46): a planned run was killed during `wait-demoted-F`, and F was promoted again by hand. A resume waited the whole demotion timeout, 5 min, for a token F no longer published, then stopped with `StepFailed`; the runbooks said it stops with `FencedSiteIsPrimary`. Reproduced in a unit test, which also showed a resume after the promotion end `Succeeded` with both sites primary in the fake CloudNativePG. |
| The read of the other sites comes before the read before the step's site | Found while fixing #46, and reproduced in a unit test: in a site loss whose `from` was promoted again by hand after its fence, the read before `from`'s steps asked for `--fence`, and the resume with it stopped before the promotion, where `--fence` cannot help. |
| Compare each captured value with its source before the promotion | Found in PR #48 (#46), inferred from the code, then reproduced in a unit test: after F was promoted again and then demoted again by hand, the read passed, and a resume promoted T with the token of F's first demotion; the run ended `Succeeded`. What CloudNativePG does with the token of a demotion that a later one replaced was not tested. |
| `--fence` counts only the step that makes the site declare another primary, as the driver names it | Found while fixing #46, and reproduced in a unit test on three sites: a third site promoted again by hand after the step that declares the new primary there passed the read, since a later step still scaled its Pooler. The run ended `Succeeded` with two sites primary in the fake CloudNativePG. |

# Requirements

1. The Hold and Failover phases MUST NOT need Git. The base revision MUST come from the Kustomizations' `status.lastAppliedRevision` ([RFC#0003]). In a `SiteLoss` run, the Hold phase's `Reconcile` steps MUST NOT request or wait for a GitRepository fetch: Flux applies the artifact it has ([RFC#0005] Requirement 6). Checked by the dry run and by unit tests.
2. A `SiteLoss` plan MUST note that Tack cannot tell a lost site from one cut off from the operator's host, and name [docs/runbooks/site-loss.md](../docs/runbooks/site-loss.md). A `SiteLoss` plan MUST be possible with Git unreachable. Fields that need find ([RFC#0006]) stay unresolved in the plan, which says so, and are resolved when the Git step runs. A `Planned` plan MUST be refused when Git cannot be read: break-glass is for a site loss, and a misconfigured Git URL or credential would otherwise hold objects with no way to commit.
3. When Git cannot be reached at the Git step, the run MUST be `Waiting` with reason `GitUnreachable`, and the step `Pending`. A Release step MUST NOT run before the Git step succeeded.
4. `tack resume` MUST retry the Git step, and MUST still stop with `GitChanged` if the branch moved from the base.
5. Before Tack counts a site as unreachable, it MUST check the site's API (`/readyz`, 5 s per check) as the table below says. The site counts as unreachable only when all its checks fail, with pauses of 5 s and 10 s between them, and the last one got no answer. A check gets no answer when no connection to the server can be made, the connection is reset or closed before an answer, the name does not resolve, or the check times out. A check answered with 5xx or 429 MUST be repeated like one that got no answer. Any other failure, such as a context missing from the kubeconfig, a credential plugin that fails, a certificate Tack does not trust, or a refused credential (401, 403), MUST NOT be repeated. A site whose last check failed for any reason but no answer is not unreachable: the plan MUST refuse, a search for runs MUST fail, and a run MUST stop with `StepFailed` before the site's step, which keeps its state. When a `SiteLoss` plan refuses because a site's last check was answered 5xx or 429, its message MUST name [docs/runbooks/site-loss.md](../docs/runbooks/site-loss.md#when-tack-refuses-the-lost-site). Each failed check that another check follows MUST print a progress line. When more than one check ran, the plan MUST say how many, in its notes when the site answered and in the site's line when it did not; in a run, the message of the site's next step MUST say how many. A deferrable step ([RFC#0002]) on an unreachable site MUST be recorded `Deferred`; the run MUST go on. Checked by unit tests.

| Read | Checks per site |
|---|---|
| The plan, by `tack plan` and by `tack run` before it asks, with its search for runs ([RFC#0003] Requirement 14) | 3; in a `SiteLoss` plan, 1 for a site other than `to` |
| The read after the confirmation of `tack run` ([RFC#0009] Requirement 13) | none: it reuses the plan's checks |
| The search for runs before `tack run` starts ([RFC#0003] Requirement 8) | as the plan |
| The search again once the ledger exists ([RFC#0003] Requirement 8) | none: it reuses the checks of the search before the run starts |
| The search for a named run, by `tack resume` and `tack status` | 1; 3 in all for a site that failed, when the run is not found at another site |
| The search by `tack resume` for a run that took the run over or started after it ([RFC#0003] Requirement 18) | as the plan of that run, before the confirmation; none after it: the search again reuses those checks |
| The search for every run, by `tack status` | 3 |
| The check before the first step at a site, by `tack run` and `tack resume` | 3; in a `SiteLoss` run, 1 when the site's steps are deferrable |
| The read before a site's steps (Requirement 6) | 3 for the site it reads, in every mode; 1 for each other site, whose state it does not use |
| The read of a site's cluster identity ([RFC#0003] Requirement 19) | none: up to 3 reads, with the same pauses |
| The read of the other sites (Requirement 9) | as the check before the first step at a site; none for a site checked in that process, or one that did not answer the read before its steps |

6. In each `tack run` and `tack resume`, before the first step of a deferrable site ([RFC#0002]) that is not `Succeeded`, whatever its state, Tack MUST read the site, and then act as the table below says. Checked by unit tests and by the e2e.

| The read | The run | The step |
|---|---|---|
| The run is interrupted during the read, such as by Ctrl-C. | `Stopped`, `StepFailed` | keeps its state |
| The site does not answer. | goes on | `Deferred`, and so are the site's later steps in that process |
| The site answers as primary, or declares itself primary, and the operator did not pass `--fence <site>` to that process. | `Stopped`, `FencedSiteIsPrimary`; nothing changed at that site | keeps its state |
| Any other error | `Stopped`, `StepFailed` | keeps its state |
| Otherwise | runs the step | |

A plan MUST note each site that answers as primary, or declares itself primary, and whose steps are deferrable: the run stops there. Checked by unit tests.

7. With `--fence <site>`, the site's deferred steps MUST run in plan order: its holds first, then its fence.
8. A run whose only remaining steps are deferred MUST end `Succeeded`, with a message counting them. A later `tack resume` MUST run them if their site answers, unless the run cannot resume because another run took it over or started after it ([RFC#0003] Requirement 18).
9. In each `tack run` and `tack resume`, before each Failover step after the step that demotes `from`, and before the step that promotes `to`, Tack MUST read every site but `to`, and then act as the table below says. The driver names the step after which a site no longer runs as primary ([RFC#0002] Requirement 2): for `from`, its demotion, or its fence in a `SiteLoss` run. The step that promotes `to` is the run's first Failover step at `to`. The read runs when the step is not `Succeeded`, whatever its state, before the read before the step's site (Requirement 6). A site that did not answer a check or a read in that process MUST count as giving no answer, with no further check. The read MUST NOT change anything. Checked by unit tests and by the e2e.

| The read of a site | The run | The step |
|---|---|---|
| The site gives no answer. | goes on | |
| The site answers as primary, or declares itself primary, and the step that makes it declare another primary is not after the promotion, or is `Succeeded`, such as `from`'s demotion. | `Stopped`, `FencedSiteIsPrimary`, also with `--fence <site>`. The message names [docs/runbooks/abandon-run.md](../docs/runbooks/abandon-run.md), and does not offer `--fence`. After the promotion, it says that the site and `to` are both primary. | keeps its state |
| The site answers as primary, or declares itself primary, the step that makes it declare another primary comes after the promotion and is not `Succeeded`, and the operator did not pass `--fence <site>` to that process. | `Stopped`, `FencedSiteIsPrimary`. The message says that with `--fence <site>`, the site and `to` are both primary until the run fences the site. | keeps its state |
| Any other error | `Stopped`, `StepFailed` | keeps its state |

The run promotes `to`, and goes on after it, only when no site stops it.

Before the step that promotes `to`, after the read, Tack MUST read again each value that a `Capture` step before it captured and recorded `Succeeded`, at the step's site when that site answered in that process, and compare it with `status.captured`. When they differ, the run MUST stop with `TokenMissing` before the step, which keeps its state; the message names the value and its object, MUST NOT print either value, and names [docs/runbooks/abandon-run.md](../docs/runbooks/abandon-run.md). A site that gives no answer is not read, and the step's message MUST say so. Checked by unit tests.

# Design

A site loss with Git down, then both back:

| # | Event | Ledger |
|---|---|---|
| 1 | `tack run --mode site-loss --to b` with site a and Git down | Hold at b; a's steps `Deferred`; b promoted; state `Waiting`, `GitUnreachable` |
| 2 | Site a answers again, still primary; `tack resume` | state `Stopped`, `FencedSiteIsPrimary`; a's steps stay `Deferred`; nothing changed at a |
| 3 | `tack resume` again, without `--fence` | the same as 2 |
| 4 | `tack resume --fence a` | a held and fenced; state `Waiting`, `GitUnreachable` |
| 5 | Git answers again; `tack resume` | commit, verify, release at a and b; state `Succeeded`; follow-up `Rebuild` for a |

If site a comes back after the commit instead, Flux at a applies Git, which already declares b primary: Flux fences a. A later `tack resume` then holds and releases a: Hold accepts the run's commit as what Flux applied there ([RFC#0003] Design).

# Limitations

| Limitation | Trigger to revisit |
|---|---|
| While the run waits for Git, held objects stay held: Flux applies nothing to them, including unrelated Git changes. | A long Git outage. |
| Tack cannot tell a lost site from one that runs but is cut off from the operator's host. Such a site stays primary until Flux there applies the run's commit, which needs Git, or until Tack fences it: two primaries for that time. A `Routing` step at it is deferrable, so `Succeeded` says nothing about routing there. The runbook [docs/runbooks/site-loss.md](../docs/runbooks/site-loss.md) confirms the loss from a second vantage point and fences out of band before the run. | A fence that does not need the site's API, or a second vantage point that Tack reads. |
| A lost site whose API still answers, such as a load balancer that answers 503 in front of a lost control plane, does not count as lost; nor does a site whose context needs a credential plugin that fails during the loss. The plan refuses. | A site loss that Tack refused this way. The runbook's way on: [docs/runbooks/site-loss.md](../docs/runbooks/site-loss.md#when-tack-refuses-the-lost-site). |
| A server name that does not resolve counts as no answer, also when the kubeconfig names the wrong host. | A live site read as lost because of a wrong name. |
| A site that comes back after the run succeeded is fenced by Flux from Git, not by Tack; Tack does not watch for it. | A controller. |
| The read before a site's steps reads every site. A read error at another site that answers stops the run with `StepFailed` before the step, although the read does not use that site. | A run stopped by such an error. |
| The read runs once per site and process. A site that turns primary later in the same process is not read again before its next step. | A controller, or a site observed to turn primary during a run. |
| The read of the other sites runs before each Failover step, not during one. A site that turns primary during a step, such as the promotion's wait, is read only before the next step. | A controller, or a site observed to turn primary during a promotion. |
| A site that gives no answer to the read of the other sites does not stop the run. In a `Planned` run, a `from` that is cut off from the operator's host but was promoted again by hand then gives two primaries. A resume with `from` down promotes `to` on purpose ([docs/runbooks/no-primary-after-demotion.md](../docs/runbooks/no-primary-after-demotion.md), option 1). | An old primary observed to run as primary again after its demotion, while cut off. |
| With `--fence <site>` for a site that the run fences after the promotion, such as a third site that is primary, the site and `to` are both primary from the promotion until the run declares the new primary there. The site may hold writes that `to` lacks, and the run records no `Rebuild` follow-up for it. | The first three-site deployment. |
| In a `tack resume` of a `Planned` run, a site not checked before in that process, such as `from` or a third site whose steps before the promotion are done, gets its 3 checks in the first read of the other sites, while no site may be primary: up to about 30 s for a site that does not answer. | An outage observed to grow this way. |
| Tack retries the check, not what reads the site after it. A run checks a site once per process, before its first step there. A network blip after a site answered its check can still fail what reads the site next: a step at that site (a `Wait` rereads until its timeout), the plan, a search for runs, the read before a site's steps, or the read of the other sites, which runs before each Failover step after the demotion. The read of its cluster's identity is repeated ([RFC#0003] Requirement 19). | A failure from a blip after its site's check. |
| `tack status` without a run name checks each site that does not answer 3 times: about 15 s when the connection is refused, about 30 s when each check times out. | An operator who needs that list faster during a site loss. |
| In a `Planned` run, a third site that is down gets 3 checks in the plan, 3 in the search before the run starts, and 3 before its first step: about 90 s when each check times out. | The first three-site deployment. |
| In a `SiteLoss` run, the base is the revision Flux last applied, even when Git answers. If the branch moved after Flux last fetched it, the run stops with `GitChanged` at the Git step, after the switch. | An observed `GitChanged` after a site loss. |
| With three or more sites, sites where Flux last applied different revisions stop a `SiteLoss` run with `GitChanged` in Hold, before the switch. | The first three-site deployment. |

<h1 style="text-align: center;">[RFC#0007] Break-Glass</h1>

# Abstract

A site loss can take Git down with it. Tack then still holds and switches the live objects, and the Git step waits until Git is back; steps on a lost site wait for that site. If a site that was lost comes back and answers as primary, the run stops until the operator approves fencing it, and no run promotes `to` while another site that answers is primary or a captured value differs from its source.

# Overview

| What is unreachable | What the run does |
|---|---|
| Git | Hold and Failover run without Git; the run waits at the Git step (`Waiting`, `GitUnreachable`, exit code 4); `tack resume` continues once Git answers. |
| A site other than `to` (and other than `from` in a planned run) | Its steps are `Deferred`; the run goes on and ends `Succeeded` with them deferred. |
| `to` | The run cannot start; a running step on it stops the run. |

# Motivation

| Choice | Reason |
|---|---|
| Switch live without Git | Getting writes back is urgent. Git can follow. |
| Never release while waiting for Git | Released objects would get the old values back from Flux's last artifact. |
| Base revision from Flux | It is the revision the live objects match, and it can be read in the cluster when Git cannot. |
| A `Planned` plan is refused when Git cannot be read | A wrong Git URL or credential would hold objects with no way to commit. Break-glass is for a site loss. |
| No Git fetch in Hold during a site loss | A GitRepository that cannot fetch made Hold wait 1m30s, on top of the write outage. |
| Note in every site-loss plan that a lost site may only be cut off | A site that is alive but cut off from the operator stays primary while the run promotes another. |
| Stop when a lost site comes back as primary | A failover must never end with two primaries. The operator decides how to fence the site. |

Counting a site as unreachable:

| Choice | Reason |
|---|---|
| Only a check that gets no answer counts | Any other failure does not go away by itself. Counting it made a live primary look lost, and a run ended `Succeeded` with two primaries. |
| Repeat a check answered 5xx or 429, never count the site as lost for it | The answer shows the site is there. A restarting API server answers `/readyz` with an error for a moment. Counting a load balancer's 503 could promote a second primary. |
| Check a site several times | A 10 s network blip caused one 5 s `/readyz` timeout, which stopped a step. |
| The same checks in the plan and in the searches for runs | A blip failed `tack plan` and left the site's runs out of the checks of [RFC#0003] Requirements 8 and 14, `tack resume` and `tack status`. |
| Check a site other than `to` once in a site loss | The lost site does not answer. Two more checks and their pauses would add up to 25 s to the write outage, in the plan and again in the run. |
| 3 checks in the read before a site's steps, in every mode | The site has just answered, so a failed check is a blip. With 1 check, a blip kept its steps `Deferred` until a later resume. |
| The search for a named run checks a failed site again only when the run is not found | A resume of a site-loss run finds its ledger at `to`. Two more checks of the lost site would add up to 25 s to each resume. |
| Check the sites of a read at once | Sequential reads added each silent site's checks, up to about 30 s. A read now waits as long as its slowest site. |
| A read's error is the first failure in the Workload's order; lines of the checks come in that order, each with its print time | It is the error a sequential read gave. The operator reads site by site, and the print times line up with the API servers' audit logs ([RFC#0009] Requirement 27). |
| A check that ends with its read, or an interrupt, does not count | It would be no answer from a site that may have been about to give one, and a later read would count the site as lost. |
| Repeat a read that fails after its site's check | After the site answered, one connection reset, 503 or 429 stopped a run with `StepFailed`, and before a planned run's promotion the outage lasted until a resume. |
| Obtain each site's credentials before its checks, with no time limit, one site at a time | Plugin prompts at two sites printed on one line, and a plugin's wait inside the 5 s check counted a live `from` as lost. |
| The end of the operator's command ends the wait for credentials; only a context with a plugin waits for the turn | client-go runs a plugin with no context, so a SIGTERM left tack waiting, and a context without a plugin waited behind another site's. |
| Credentials are obtained before each step | Expired credentials were obtained inside a step's request, with no line and no way to interrupt; for `to`, that can fall between the demotion and the promotion. |
| The checks before the first step of every deferrable site start with the run | A paused third site's checks took 26 s, and each such site would add its own, one after another. |

- Load balancer: one in front of a lost control plane may answer 503 too, but Tack cannot tell it from one in front of a live API server. The operator confirms the loss from a second vantage point ([site-loss runbook](../docs/runbooks/site-loss.md#when-tack-refuses-the-lost-site)).
- Interrupted check: in a site loss, each site but `to` gets one check.
- Repeat that runs out of tries: it still stops the run, because counting it as no answer could promote while the site is primary.
- Credentials: a site whose credentials cannot be obtained is not lost.

Reads that stop a run:

| Choice | Reason |
|---|---|
| Read a site before its first step in each process, whatever the step's state | A read only before a `Deferred` step let a second `tack resume` without `--fence` hold a Cluster at a site that was still primary. |
| A stop by the read, or an interrupt during a check or read, leaves the step's state | The step did not start. Recording it `Failed` ("context canceled") or `Deferred` stopped the run at the next step. |
| The read before a site's steps reads that site only | Reading every site let a refused read at another site stop the run before the steps of a site that came back. |
| A site that declares itself primary counts, before it reports `isPrimary` | CloudNativePG promotes such a Cluster at once ([RFC#0004] Motivation). A lost site that returned declaring itself primary was held and fenced without the operator's decision. |
| A plan notes such a site and does not refuse it | Refusing it would leave no way through Tack: a fence by hand is undone by Flux, which no run holds. |
| `--fence` does not let the promotion go on for a site whose Failover steps are all before it | Such a site is `from`, already demoted or fenced, and no step fences it again. Promoting `to` gives two primaries. |
| `--fence` lets the promotion go on for a site whose Failover steps come after it | The run holds the site, promotes `to`, then declares the new primary there ([RFC#0004] Requirement 6, step 8). |
| `--fence` counts only the step that makes the site declare another primary, as the driver names it | A site promoted again by hand after that step passed the read, because a later step still scaled its Pooler, and the run ended `Succeeded` with two primaries. |
| A third site let through by `--fence` gets a `Rebuild` follow-up | b and c were both primary until the run declared b at c. A later planned run to c was allowed onto a member that may hold writes b lacks. |
| Read every site but `to` before the promotion and before each later Failover step, in every mode and process (Requirement 9) | A planned run died after `demote-b` and the operator promoted b by hand; a resume then promoted a with the token of b's earlier demotion while b was primary. |
| The read of the other sites comes before the read before the step's site | `from`, promoted again by hand after its fence, made the read before its steps ask for `--fence`; a resume with it stopped before the promotion, where it cannot help. |
| Compare each captured value with its source before the promotion | F was promoted and demoted again by hand, and a resume promoted T with the token of F's first demotion. |

- Read before a site's steps: the ledger does not record the `--fence` approval, and after it the site's steps can be `Pending`, `Failed` or `Running`.
- Declared primary: a `SiteLoss` plan refuses only a `from` that answers as primary ([RFC#0004] Requirement 5). A `from` whose API answers but whose instances are down still declares itself primary.
- `--fence` for `from`: in a `Planned` run, the promotion would also use the token of a demotion that a later promotion undid.
- Read of the other sites: see [no-primary-after-demotion](../docs/runbooks/no-primary-after-demotion.md). Without the read before later steps, a resume waited the whole demotion timeout for a token F no longer published, or ended `Succeeded` with both sites primary. The read before a site's steps (Requirement 6) skips `to` and does not run for a site whose steps are done.

# Requirements

1. The Hold and Failover phases MUST NOT need Git. The base revision MUST come from the Kustomizations' `status.lastAppliedRevision` ([RFC#0003]). In a `SiteLoss` run, the Hold phase's `Reconcile` steps MUST NOT request or wait for a GitRepository fetch: Flux applies the artifact it has ([RFC#0005] Requirement 6). Checked by the dry run and by unit tests.
2. A `SiteLoss` plan MUST note that Tack cannot tell a lost site from one cut off from the operator's host, and name [docs/runbooks/site-loss.md](../docs/runbooks/site-loss.md). A `SiteLoss` plan MUST be possible with Git unreachable. Fields that need find ([RFC#0006]) stay unresolved in the plan, which says so, and are resolved when the Git step runs. A `Planned` plan MUST be refused when Git cannot be read.
3. When Git cannot be reached at the Git step, the run MUST be `Waiting` with reason `GitUnreachable`, and the step `Pending`. A Release step MUST NOT run before the Git step succeeded.
4. `tack resume` MUST retry the Git step, and MUST still stop with `GitChanged` if the branch moved from the base.
5. Before Tack counts a site as unreachable, it MUST check the site's API (`/readyz`, 5 s per check) as the table below says. The site counts as unreachable only when all its checks fail, with pauses of 5 s and 10 s between them, and the last one got no answer.
    - A check gets no answer when no connection can be made, the connection is reset or closed before an answer, the name does not resolve, or the check times out.
    - A check answered 5xx or 429 MUST be repeated like one that got no answer.
    - Any other failure MUST NOT be repeated: a context missing from the kubeconfig, a credential plugin that fails, a certificate Tack does not trust, a refused credential (401, 403).
    - A site whose last check failed for any reason but no answer is not unreachable. The plan MUST refuse, a search for runs MUST fail, and a run MUST stop with `StepFailed` before the site's step, which keeps its state. A run interrupted during a check, such as by Ctrl-C, MUST stop the same way.
    - A `SiteLoss` plan that refuses because a site's last check was answered 5xx or 429 MUST name [docs/runbooks/site-loss.md](../docs/runbooks/site-loss.md#when-tack-refuses-the-lost-site) in its message.
    - Each failed check that another follows MUST print a progress line. When more than one check ran, the plan MUST say how many, in its notes when the site answered and in the site's line when it did not; in a run, the message of the site's next step MUST say how many.
    - A deferrable step ([RFC#0002]) on an unreachable site MUST be recorded `Deferred`; the run MUST go on.

    Checked by unit tests.

| Read | Checks per site |
|---|---|
| The plan, by `tack plan` and by `tack run` before it asks, with its search for runs ([RFC#0003] Requirement 14) | 3; in a `SiteLoss` plan, 1 for a site other than `to` |
| The read after the confirmation of `tack run` ([RFC#0009] Requirement 13) | none: it reuses the plan's checks |
| The search for runs before `tack run` starts ([RFC#0003] Requirement 8) | as the plan |
| The search again once the ledger exists ([RFC#0003] Requirement 8) | none: it reuses the checks of the search before the run starts |
| The search for a named run, by `tack resume` and `tack status` | 1; 3 in all for a site that failed, when the run is not found elsewhere |
| The search by `tack resume` for a run that took the run over or started after it ([RFC#0003] Requirement 18) | as the plan of that run, before the confirmation; none after it: the search again reuses those checks |
| The search for every run, by `tack status` | 3 |
| The check before the first step at a site, by `tack run` and `tack resume` | 3; in a `SiteLoss` run, 1 when the site's steps are deferrable |
| The read before a site's steps (Requirement 6) | 3 for the site it reads, in every mode; none for any other site, which it does not read |
| The read of a site's cluster identity ([RFC#0003] Requirement 19) | none: up to 3 reads, with the same pauses |
| The read of the other sites (Requirement 9) | as the check before the first step at a site; none for a site checked in that process, or one that did not answer the read before its steps |

The checks before the first step at a site start with the process's steps, for every deferrable site with a step not `Succeeded`. The site's first step waits for them.

6. In each `tack run` and `tack resume`, before the first step of a deferrable site ([RFC#0002]) that is not `Succeeded`, whatever its state, Tack MUST read the site, and no other site, and then act as the table below says. Checked by unit tests and by the e2e.

| The read | The run | The step |
|---|---|---|
| The run is interrupted during the read, such as by Ctrl-C. | `Stopped`, `StepFailed` | keeps its state |
| The site does not answer. | goes on | `Deferred`, and so are the site's later steps in that process |
| The site answers as primary, or declares itself primary, and the operator did not pass `--fence <site>` to that process. | `Stopped`, `FencedSiteIsPrimary`; nothing changed at that site | keeps its state |
| Any other error | `Stopped`, `StepFailed` | keeps its state |
| Otherwise | runs the step | |

A plan MUST note each site that answers as primary, or declares itself primary, and whose steps are deferrable: the run stops there. Checked by unit tests.

7. With `--fence <site>`, the site's deferred steps MUST run in plan order: its holds first, then its fence.
8. A run whose only remaining steps are deferred MUST end `Succeeded`, with a message counting them. A later `tack resume` MUST run them if their site answers, unless the run cannot resume because another run took it over or started after it ([RFC#0003] Requirement 18).
9. In each `tack run` and `tack resume`, before each Failover step after the step that demotes `from`, and before the step that promotes `to`, Tack MUST read every site but `to`, and then act as the table below says. The driver names the step after which a site no longer runs as primary ([RFC#0002] Requirement 2): for `from`, its demotion, or its fence in a `SiteLoss` run. The step that promotes `to` is the run's first Failover step at `to`. The read runs when the step is not `Succeeded`, whatever its state, before the read before the step's site (Requirement 6). A site that did not answer a check or a read in that process MUST count as giving no answer, with no further check. The read MUST NOT change anything. Checked by unit tests and by the e2e.

| The read of a site | The run | The step |
|---|---|---|
| The site gives no answer. | goes on | |
| The site answers as primary, or declares itself primary, and the step that makes it declare another primary is not after the promotion, or is `Succeeded`, such as `from`'s demotion. | `Stopped`, `FencedSiteIsPrimary`, also with `--fence <site>`. The message names [docs/runbooks/abandon-run.md](../docs/runbooks/abandon-run.md), and does not offer `--fence`. After the promotion, it says that the site and `to` are both primary. | keeps its state |
| The site answers or declares itself as primary, its step that makes it declare another primary is after the promotion and not `Succeeded`, and that process got no `--fence <site>`. | `Stopped`, `FencedSiteIsPrimary`; the message says that with `--fence <site>` the site and `to` are both primary until the run fences the site. | keeps its state |
| Any other error | `Stopped`, `StepFailed` | keeps its state |

The run promotes `to`, and goes on after it, only when no site stops it. When `--fence <site>` lets it go on while that site answers as primary, or declares itself primary, the run MUST record the follow-up `Rebuild` for the site, once, in its next ledger write ([RFC#0003] Requirement 14). Checked by unit tests.

Before the step that promotes `to`, after that read, Tack MUST read again each value captured by a `Capture` step recorded `Succeeded`, at the step's site when it answered in that process, and compare it with `status.captured`. When they differ, the run MUST stop with `TokenMissing` before the step, which keeps its state; the message names the value and its object, MUST NOT print either value, and names [docs/runbooks/abandon-run.md](../docs/runbooks/abandon-run.md). A site that gives no answer is not read, and the step's message MUST say so. Checked by unit tests.

10. Each read that goes through the sites MUST start the checks of all its sites at once, then read the sites in the Workload's order, each once its own checks ended. These reads are: the plan's read and the read after the confirmation, each search for runs, the read before the first Failover step, and the read of the other sites. The first site in the Workload's order whose check or read fails MUST end the read with its error, and the read MUST end the checks still running at the other sites before it returns. Each site MUST get the checks that Requirement 5's table gives it, no more. A check that ends because its read ended, or because the run was interrupted, MUST NOT count as a check of the site. The progress lines of the checks MUST come grouped by site, in the Workload's order: a site's lines go out once the checks of every site before it ended, and are held back until then. Checked by unit tests.
11. A read of a site's objects, a get or a list, MUST be repeated when it gets no answer, or an answer 5xx or 429, with the pauses of the site's checks (Requirement 5), up to as many reads in all as the site gets checks: 1 for a site that gets 1 check, else 3. This holds for each read of Requirement 5's table that reads objects, the compare of the captured values (Requirement 9), a `Capture` step's read, and the read of an object's hold before a `Patch` step ([RFC#0005] Requirement 11). Any other failure, such as a 403 or a 404, MUST NOT be repeated. Each repeat MUST print a progress line, and so MUST an answer after one. A read whose tries ran out MUST fail with its last error and the count of reads, and MUST NOT count the site as giving no answer. An interrupt during a pause MUST stop the run before the step, which keeps its state. A `Wait` step's read and the read of a site's cluster identity ([RFC#0003] Requirement 19) repeat on their own and are not repeated again. Checked by unit tests.
12. Before each check of a site, and before each step of a run at a site, Tack MUST obtain the credentials of the site's kube context: it runs the context's credential plugin when it has one and its credentials are not cached, with no time limit, and sends nothing to the site. That time MUST NOT count toward the check's 5 s.
    - A process MUST run one credential plugin at a time, and a plugin keeps that turn until it ends. A context without a plugin MUST NOT wait for the turn.
    - The end of the command, such as by an interrupt or a signal, MUST end Tack's wait for credentials, for the turn and for the plugin, and MUST NOT count as credentials that cannot be obtained.
    - A read that starts the checks of its sites at once (Requirement 10) MUST first obtain the credentials of each of its sites, one at a time, in the Workload's order; so MUST the checks that start with a run (Requirement 5), in the order of the steps.
    - Wherever Tack obtains credentials, it MUST print a progress line once they took more than 2 s.
    - A site whose credentials cannot be obtained MUST NOT count as giving no answer. Each check of the site in that process MUST fail with an error that names the kube context and says the site is not counted as lost, and Requirement 5's refusals apply. A run whose step's site's credentials cannot be obtained MUST stop with `StepFailed` before that step.

    Checked by unit tests with credential plugins that take longer than a check, by a test that sends SIGTERM to a tack process whose plugin waits, and by hand on kind with a plugin that prompts on the terminal.

# Design

A site loss with Git down, then both back:

| # | Event | Ledger |
|---|---|---|
| 1 | `tack run --mode site-loss --to b` with site a and Git down | Hold at b; a's steps `Deferred`; b promoted; state `Waiting`, `GitUnreachable` |
| 2 | Site a answers again, still primary; `tack resume` | state `Stopped`, `FencedSiteIsPrimary`; a's steps stay `Deferred`; nothing changed at a |
| 3 | `tack resume` again, without `--fence` | the same as 2 |
| 4 | `tack resume --fence a` | a held and fenced; state `Waiting`, `GitUnreachable` |
| 5 | Git answers again; `tack resume` | commit, verify, release at a and b; state `Succeeded`; follow-up `Rebuild` for a |

If site a returns after the commit, Flux at a applies Git, which already declares b primary, and so fences a. A later `tack resume` holds and releases a, because Hold accepts the run's commit as what Flux applied there ([RFC#0003] Design).

# Limitations

| Limitation | Trigger to revisit |
|---|---|
| While the run waits for Git, held objects stay held: Flux applies nothing to them, including unrelated Git changes. | A long Git outage. |
| A site cut off from the operator's host looks lost and stays primary until Flux applies the run's commit or Tack fences it. Confirm and fence it first ([site-loss runbook](../docs/runbooks/site-loss.md)). | A fence that does not need the site's API, or a second vantage point that Tack reads. |
| A lost site whose API still answers (a load balancer's 503) or whose credential plugin fails during the loss does not count as lost, and the plan refuses. | A site loss that Tack refused this way. The way on: [docs/runbooks/site-loss.md](../docs/runbooks/site-loss.md#when-tack-refuses-the-lost-site). |
| A server name that does not resolve counts as no answer, even when the kubeconfig names the wrong host. | A live site read as lost because of a wrong name. |
| A site that comes back after the run succeeded is fenced by Flux from Git. Tack does not watch for it. | A controller. |
| A site that turns primary during a `Wait` goes unseen until the next step; the reads of Requirements 6 and 9 run before steps, not during one. | A controller, or a site observed to turn primary during a run. |
| A site that gives no answer to the read of the other sites does not stop the run (Requirement 9): a cut-off `from` promoted again by hand gives two primaries. | An old primary observed to run as primary again after its demotion, while cut off. |
| `--fence <site>` for a site the run fences after the promotion leaves it and `to` both primary until the run declares the new primary there ([RFC#0004] Requirement 6). | The first three-site deployment. |
| Each silent site costs up to about 30 s of checks, all at once (Requirement 10), in each plan read, search for runs and run start. | An outage observed to grow this way. |
| A blip in a read or write that Requirement 11 does not repeat fails the step; `tack resume` runs it again ([RFC#0002]). | A failure from a blip after its site's check, in one of these reads or in a write. |
| A plugin that never ends holds every plugin-using site's checks and steps until tack is interrupted. Use a context that needs nothing of the lost site ([site-loss runbook](../docs/runbooks/site-loss.md#when-tack-refuses-the-lost-site)). | A plugin observed to hang during a site loss. |
| Credentials that expire inside a step are obtained inside that request, with no line, and an interrupt does not end the wait. A second signal ends tack ([RFC#0009] Requirement 14). | A run observed to wait inside a request for a credential plugin. |
| In a `SiteLoss` run, the base is the revision Flux last applied, even when Git answers; a branch that moved since stops the run with `GitChanged` after the switch. | An observed `GitChanged` after a site loss. |
| With three or more sites, sites where Flux last applied different revisions stop a `SiteLoss` run with `GitChanged` in Hold, before the switch. | The first three-site deployment. |

- Cut-off site: the plan notes it (Requirement 2). A deferred `Routing` step there leaves `Succeeded` silent on routing ([RFC#0002] Requirement 7).
- No answer to the read of the other sites: in a `Planned` run a cut-off `from` promoted again by hand then gives two primaries; with `from` down, a resume promotes `to` on purpose ([no-primary-after-demotion](../docs/runbooks/no-primary-after-demotion.md), option 1).
- `--fence <site>` after the promotion: such a site can be a primary third site. Its writes that `to` lacks are lost to `to`; the run records a `Rebuild` follow-up.
- Silent sites: the same cost falls on the first read of the other sites in a `Planned` resume. A site lost between a check and its read fails the read, without counting as lost (Requirement 11).
- Not repeated (Requirement 11): Flux's reads in `Hold`, `Reconcile`, `VerifyGit`, `Release` and `VerifyNoop`, Strait's in `Routing`, the ledger's own reads, and all writes but the ledger's ([RFC#0003] Requirement 5). In `tack status --context` and `tack abandon` before it asks, a blip fails the command.
- Credential plugin: one that waits for an identity provider lost with the site is an example (Requirement 12). The interrupt ends Tack's wait, not the plugin, which client-go runs with no context. Ctrl-C reaches it; a signal to tack's pid alone does not.
- Credentials that expire inside a step: such as between the polls of a `Wait`; Requirement 12 covers the start of a step. The same holds in a request to a site whose plugin still runs, such as the ledger write that records a stop.
